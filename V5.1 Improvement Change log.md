# V5.1 Improvement Change log

## Long tool calls outlast the turn timeout — 2026-11-11

| Group | Type | Change | Summary | Status |
|---|---|---|---|---|
| Providers | Bugfix | Long Tool Calls No Longer Time Out The Turn | A command running inside one tool call, such as a long build, sends nothing until it ends, so the provider turn timeout stopped the turn while the command was still working. An open tool call now holds that timer: one that declares its own timeout (Claude Code Bash, OpenCode bash) is not counted as silent until that timeout has passed, and any other gets the new Tool call limit setting (default 2 hours) from its start. The latest deadline wins when several are open, the normal timer resumes with the result, and a hung command still stops, with a notice saying a tool call exceeded its limit. All six providers' structured chats, locally and over SSH, use the one shared decision. A native CLI View turn, which has no tool events, now uses the Tool call limit as its busy-time ceiling instead of the turn timeout. | In review |

## Chat save stalls — 2026-11-10

| Group | Type | Change | Summary | Status |
|---|---|---|---|---|
| Performance | Performance | Atomic Writes Stop Scanning The Directory | Every durable write listed its whole directory twice and inspected each entry while holding the process-wide write lock. The listing now happens at most once per directory every ten minutes, and names are checked before any file is inspected. On the Windows build host, 100 rewrites of one file beside 4,000 entries fell from 2,647 ms to 300 ms, and re-saving 100 chats in a 4,000-entry chats folder from 1,826 ms to 599 ms. Abandoned temporaries are still removed after 24 hours, only for the destination being written. | In review |
| Chat | Bugfix | Streaming Answers Reach Disk While They Stream | Each chunk pushed the save half a second further away and discarded any save in progress, so an answer that never paused was not written until it finished. A stream is now written within two seconds of its first unsaved change (longer for very large transcripts, at most thirty seconds), and a later save request can no longer postpone one already due. After three seconds of unbroken streaming into a 30 MB chat, 22,200 of 30,000 streamed bytes were on disk, where before none were. | In review |
| Performance | Performance | Tool And Plan Updates Save In The Background | Each tool-call status or plan update from ACP providers and Claude Code wrote the whole transcript on the interface thread, about 340 ms for a 30 MB chat. These display updates now schedule the background save: twenty updates held the calling thread 0.04 ms in total. Saves whose result gates an action, such as prompt markers, queue admission, turn settlement and stop, stay synchronous. | In review |
| Chat | Bugfix | Mismatched Queue Journal No Longer Blocks A Chat Forever | A queued-input journal whose chat file had been restored, synced or touched outside UAM held the chat permanently: sends and saves were refused and restarting read the same files. When the journal still extends the queue revision the chat file carries, it is bound to the file again at load, its input stays held and visible, and nothing is sent until the user resumes it. A journal for a different queue revision still holds the chat; see the open decision. | In review |
| Chat | Bugfix | One Parked Save Result No Longer Stops Other Chats Saving | A finished background save result for a chat that was being skipped, for example while its initial publication was unconfirmed, counted as running work and stopped every other chat's background save for as long as the skip lasted. Only work that is still running now counts. | In review |
| Chat | Bugfix | Failed Chat Saves Are Reported And Back Off | A transcript that could not be saved was retried every second with no notice. The first failure for a chat now shows once in the status line and writes one diagnostic line, retries back off from 1 s to 60 s, and the forced save at quit records a chat it could not write. A notice at quit itself is an open decision. | In review |
| Performance | Performance | Background Saves Stop Re-reading The Chat File | Each burst of background saves read and parsed the whole chat file to find its unchanged rows. The rows of the two most recently saved chats are now kept and reused. The interface-thread share of a 30 MB background save measured 4.9 ms for its longest poll, so the per-row comparison was kept as the check that a chat is never marked saved with unsaved changes. | In review |
| Chat | Bugfix | Stream Saves Are Spaced And Cannot Starve | Review follow-up. Tool and plan updates could rewrite a small transcript ten or more times a second, and an update to a row that was not the last one was never written until the turn ended. Rewrites of one transcript are now at least half a second apart, an older snapshot is published whichever row changed, and it never replaces a summary value written since it was captured. The interface thread no longer compares transcript rows while output is streaming. | In review |
| Chat | Bugfix | Chat Save Failure Records Follow Their Chat | Review follow-up. A deleted chat left its failure record behind, so the status line never cleared and its transcript stayed in memory; the status blamed disk space for saves refused for other reasons; and a burst of failing saves jumped the retry wait to 60 s. Records are dropped with the chat, the wording no longer asserts a storage cause, and only the scheduled retry lengthens the wait. | In review |
