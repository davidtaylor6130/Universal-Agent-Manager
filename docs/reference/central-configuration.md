# Central provider setup

> Engineering reference retained from the trial base (`3a7c8477`, 2026-10-16). This records implementation detail and historical verification, not full feature acceptance. Start with the [feature guide](../README.md); its agreements and [documented corrections](../documentation-review.md) take precedence over stale claims here.

Configure shared resources in Settings > Central Setup, then enable them. UAM installs those resources when a provider starts in Chat or CLI View, including workspaces on SSH hosts. Changes apply to the next launch. Existing running sessions keep their setup until restarted.

OpenCode's progressive MCP control uses `central_provider_configuration.mcp_overrides` with canonical provider `opencode-cli`, the exact execution-host ID, the UAM setting key `opencode-progressive-mcp` and `kind: "preference"`. `setProviderMcpConfiguration` validates provider/host ownership, persists the candidate with rollback on failure and returns the saved boolean as `progressiveMcpDiscoveryEnabled` in host-bound status; it is a configuration receipt, not proof that a running CLI uses Code Mode. Preference entries and requests carry `kind: "preference"`; ordinary server overrides omit it. The native parser, frontend projection and setter retain that distinction, so a user server with the same identifier stays independent. Unset retains the previous enabled default. `PrepareProviderConfiguration` uses `ShouldEnableOpenCodeV1ProgressiveMcp` to combine this choice with the existing exact checked-version admission before emitting `openCodeCodeMode`; format-1 compatibility and explicit executing-host/per-launch environment precedence stay intact. Neither this hint nor `openCodeUamControlDeadline` defines V2 capability or session/location server registration. Central configuration already participates in pending-launch ownership capture. CLI View uses the same predicate before its no-setup shortcut, and terminal control-only setup retains the discovery override while discarding shared resources. [User-facing agreement](../settings/providers.md).

**V2 discovery capability lead — Needs verification:** the [pinned upstream MCP schema](https://github.com/anomalyco/opencode/blob/a517687fde98a7329ada3ae644a01a9fc6c4e99e/packages/schema/src/mcp.ts#L22-L59) defines optional `codemode` booleans for both local and remote server configurations, with an enabled native default. Schema presence does not establish effective discovery, permission behavior or connection proof. Task-0835's captured-definition registration remains independent and does not set this field or register the synthetic preference key. Future preference wiring requires separately checked V2 capability/effective evidence; this lead does not extend the V1 gate or add a UAM manifest/status field.

Instructions can come from the text field or absolute paths on the desktop. UAM adds the selected agent's instructions and an index of installed skills and agent definitions. Every provider can read the installed files. UAM also reads the workspace's AGENTS.md on the executing computer. Nested workspace instructions continue to follow each provider's own rules.

On the desktop, use Edit beside a saved instruction file to change its contents inline. New paths must be saved in Central Setup before editing. Save file replaces the existing file atomically and retains its permissions; it rejects files changed outside UAM, links, invalid UTF-8, NUL bytes and files larger than 2 MiB. Failed saves retain the draft. These edits apply to subsequent provider launches, including SSH launches that receive the shared file. Remote-host-specific instruction paths remain separate.

Skill folders may contain one SKILL.md or several child skill folders. UAM copies each skill's scripts, references and other files. The existing Skills library is included too; imported SKILL.md entries retain their supporting files while the original source folder is available. A library entry without its original folder remains a Markdown skill. Paths to resources in the instruction index point to the installed copy on the executing computer.

Global agents stay in UAM's existing agent library. The default agent and UAM tools switches affect new chats. Explicit choices in existing chats are retained. Per-provider model, permissions and other defaults remain in Settings > Defaults. Selecting a read-only agent restricts native CLI launches to Plan mode.

Settings > MCP Servers includes an Add MCP server wizard for connection details, execution host, workspace scope and secret references. Review and save once to configure all six providers. Existing entries can be edited, enabled, disabled or removed. The UAM MCP service is built in and has its own new-chat default and current-chat switch. The same page includes native instructions, instruction-file paths, skill folders and agent selection. These resources use provider launch configuration, not user-message text. Advanced JSON remains available. HTTP/SSE endpoints currently must use localhost. Saved MCP entries apply on the next launch even when Central Setup is disabled. Leave workspaceDirectory empty to apply a server to every workspace. An empty executionHostId applies to all hosts; a specific host id restricts it to that computer. Workspace settings override global servers with the same name, and host settings override equally scoped general entries. Executable paths and referenced environment variables must exist on the executing computer. HTTP and SSE URLs refer to that computer's localhost. Controller secret values are never copied to SSH hosts.

Set each SSH host's instructions in Settings > Remote Hosts, as inline guidance or a legacy instruction file path on the remote computer. `PrepareProviderConfiguration` builds launch configuration for every SSH launch whose host has instructions (`execution_hosts::HasInstructions`), and CLI View's no-setup shortcut in `PrepareCliProviderHandoffAsync` checks the same predicate. When central setup applies to the launch, including a control-only launch that replaces a globally disabled configuration with an empty enabled one for UAM tool servers (not in Antigravity structured Chat; this discards the per-provider `shared-setup` overrides, which otherwise turn setup on or off for one provider on one host), it appends inline guidance after the skill index; the helper's `provider_setup::Apply` then appends the workspace AGENTS.md (not for Codex, OpenCode or Copilot, which load it natively) and the legacy file, which it reads only when no inline guidance is saved, followed for Claude by any existing `--append-system-prompt` text. With central setup off, the manifest sets `hostInstructionsOnly`: `AGENTS.md` holds only the inline guidance, the legacy file is still appended, and `Apply` skips the workspace AGENTS.md. `remote::ResolveHostContext` returns recalled project memories for `SendQueuedPromptIfReady` and still reads a legacy file each turn so an unreadable file stops the turn. Host instructions stay out of prompt text except for providers whose `DeliversHostInstructionsInFirstPrompt` is true (Gemini Chat, where include-directory memory depends on folder trust): `PrepareProviderConfiguration` leaves the text out of that launch, and `ChatSession::host_instructions_delivery` records the native session and text digest last delivered, so `SendQueuedPromptIfReady` adds the text only when they differ. Every other route (Claude image turns, native steers, managed results, Codex goal turns) writes to the same provider process and needs no delivery of its own. `RunnerClient::ProviderConfigurationLocation` asks the helper's `configuration.location` request (capability `providerConfigurationLocation`) where a bundle installs: a `hostInstructionsOnly` bundle always uses the private `~/.uam/provider-setup/<digest>` folder, and other bundles use `<workspace>/.UAM/provider-setup/<digest>` unless that path contains a link or cannot be written, when they use the same private folder. `IsAllowedConfigurationDirectory` admits only those two locations at process start. Handoff context uses `context.location` the same way, falling back to the private `~/.UAM/context/<token>` folder; saved cleanup keeps the requested workspace path and `context.remove` clears both copies. A linked legacy host file is read through its real parent (`allowLinkedAncestors` on `context.read`), so a link above it is allowed and a link at the file itself is refused. A helper without the capability keeps the workspace folder. On SSH the helper's `PrepareSetupInput` adds Codex's instructions to the first setup frame and, after a `thread/resume`, also to a replacement `thread/start` if the saved thread is rejected. UAM sets Codex's `developer_instructions` without merging a value from the host's own Codex configuration. A `hostInstructionsOnly` manifest needs the helper's `hostInstructionsOnlyConfiguration` capability, and Gemini receives that text under its first configured context filename so `AGENTS.md` is not added to the names it loads from the workspace. Gemini's private runtime folder contains an empty `.git` directory, the boundary that stops its upward context walk from loading the bundle's own `AGENTS.md` as a second copy. The [Remote Hosts page](../settings/remote-hosts.md) owns the user-facing order. An unreadable file, missing executable or missing secret variable stops setup with a clear error.

UAM writes shared copies to its data root under runtime/provider-setup locally, and under .UAM/provider-setup in each remote workspace or, when a host-only bundle or an unusable workspace calls for it, under ~/.uam/provider-setup on the host. These directories belong to UAM. It does not overwrite workspace or provider home configuration. Resource manifests include checksums; interrupted remote uploads resume with missing files only. An older SSH helper must be updated before it can accept central setup.

Resource bundles allow up to 4,096 files, 2 MiB per file, 32 MiB total and a 512 KiB manifest. Codex limits combined central instructions to 64 KiB on macOS/Linux and 12 KiB on Windows so its launch arguments remain within OS limits. Put larger reference material in skills. Symbolic links inside skill assets are rejected. UAM exposes skills through an instruction index, so providers can use their scripts and references even where the CLI has no session-only skill directory option. This does not add slash commands to every provider.

UAM tools use a separate capability for each Chat or CLI session. Stopping a terminal ends its authority without revoking a concurrent structured chat's capability. Remote tools use the existing SSH MCP relay. Built-in Build and Plan agents can list the central skills and read their installed files through UAM tools. Custom agents retain their approved skill list. The skill_read tool accepts an optional relative asset path. Permission and approval rules continue to apply.

Antigravity loads managed instructions and MCP configuration from an isolated additional directory. Tool execution follows its native policy; headless discovery can succeed while calls remain denied. Use its terminal for interactive approvals. UAM never changes the provider's global or workspace configuration to bypass permissions.
