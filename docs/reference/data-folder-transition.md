# Data-folder transition contract

Task-1629 implements native pending selection and a guarded stopped-profile transaction. The [storage agreement](../settings/storage.md#application-data-folder) owns the outcome and the [data authority agreement](../architecture/source-of-truth.md) owns every retained record. Source implementation, disposable verification and David's acceptance remain separate. The live Settings restart control and native restart/recovery bridge remain disabled by `kTransfersValidated=false`; no real profile has been migrated.

## Preference and bootstrap ownership

`Application::InitializeState` captures the original external `UAM_DATA_DIR` before exporting its effective root. An external override bypasses the preference but cannot bypass a retained handoff fence. Without an explicit choice the existing OS app-data, temporary and final relative-data fallback order stays unchanged. Version 1 `selection.json` under `<default-root>/.data-folder-control/` stores source, pending destination, revision, originating operation and phase; it never selects a destination by itself. The bootstrap stays at the original default location through subsequent folder changes.

The service retains an independent bootstrap lock and the active profile lease. The production platform root-lock primitive pins the directory, refuses linked/reparse/hard-linked or foreign marker files, and acquires ownership without truncating or rewriting any marker; historical PID text is diagnostic only. Typed retained leases revalidate directory and marker identity before transition/selection publication; marker replacement holds further changes. Directory identity witnesses detect replacement without reopening Windows' exclusively owned lock file. Every choice/cancel writes `intent.json` with before/after records and `publishing`, then the selection, then an exact `acknowledged` receipt. Missing, conflicting or uncertain acknowledgement holds further preference writes. Backups, timestamps and destination contents are never routing authority.

Trusted-main-frame CEF actions `getDataFolderSettings`, `chooseDataFolder` and `cancelDataFolderChoice` require native revision/action identity and remain outside companion dispatch. Async workers capture the service and leases, not mutable AppState. Settings distinguishes current and pending folders, uses the native picker, confirms the selected path and supports cancellation. A lost response remains visible through remount until its exact operation is observed at a different revision; the action ID is acknowledgement correlation, not replay permission. Native data waits are bounded; the picker has no artificial user deadline. `restartReady` stays false while live activation is gated. The connected restart confirmation submits only the observed revision to native `restartToApplyDataFolder`; a response never claims completed migration. An uncertain restart request survives Settings remount and holds further folder changes until the application reopens.

## Stopped transaction and restart

`DataFolderTransition` and platform `DataFolderTree` implement these phases:

1. **Arm.** Verify the exact saved choice, active lease, source identity and separate empty destination. Capture the destination directory identity. Settings selection, arming (including an already armed retry) and stopped activation share identity-based exclusion in both ancestor directions against the current root, original bootstrap/default root, all historical sources and all passive snapshots, including a just-rolled-back image not yet promoted into history. Pin the bootstrap identity and revalidate retained identities and destination ancestry before publishing a choice, promoting ownership history or creating destination lock markers; repeat separation after destination ownership without reading Windows’ exclusively locked marker. A rejected overlap leaves inventories, receipts and pending revisions unchanged; unavailable retained identities hold publication. A moved or retargeted destination cannot reuse its armed identity to bypass separation. A different or uncertain existing transaction refuses. A confirmed active root can become the source of a subsequent transfer; all historical source snapshots, locks and receipts remain retained in the bounded ownership chain.
2. **Quiesce and fully exit.** The trusted native restart route arms the transaction and requests a distinct supervised restart. Application shutdown stops/joins existing import, cleanup, memory, save, log, cache and companion writers and requires successful settings/task/save barriers. A provider already running at shutdown has no generic confirmed-stop receipt and therefore cannot qualify; unresolved remote/process/recovery markers also hold. Only full normal child exit with the confirmed data-folder exit code lets the supervisor mint the stopped-handoff marker. An ordinary restart, crash, timeout or frontend acknowledgement cannot mint it.
3. **Own before profile writes.** The successor acquires the current root and stable bootstrap locks, then nonblockingly acquires the destination and pins both identities before copying. Independent UAM-control requests, shell-action publication, Computer Use helper storage and helper-cache installation share a reserved writer lease; transfer takes it exclusively on both roots and retains the freezes on historical sources and passive copies. A busy independent writer refuses before copying. It never waits while owning the source. The source remains authoritative across process exit; there is no live copied destination or inherited lock handle during this gap. Startup reacquires and verifies retained roots before opening profile writers. Both current transaction leases, every historical source lease and every rolled-back passive-copy lease stay owned for the active profile lifetime. Another bootstrap process or an override cannot open a fenced rollback source. No uncertain selected root falls back to another database.
4. **Inventory and copy.** Charge discovered entries against one 100,000-entry budget during directory enumeration, before retaining/sorting listings across the depth-64 walk, and stream regular files in 64 KiB chunks. Verify same opened objects, size, hash, exact modification times and POSIX file permissions. Retain modification times in the logical inventory, set them through the opened destination handle and verify exact precision after sync; an unsupported timestamp representation holds the passive copy. This preserves the repository's summary-overlay freshness and queue-journal base-revision rules without inventing a newer summary or rebasing authored input. At opening and every IO admission, explicitly match the IO directory handle to the attribute witness retained before the open; restoring a directory name after a swap cannot pair an owned witness with another profile handle. POSIX IO uses retained directory descriptors with no-follow `openat`, `mkdirat` and `renameat`; Windows retains ancestors without delete sharing and refuses reparse points and hard links. Reject links, hard links, special/unreadable files, overlapping roots, foreign destination content, replaced directories, unknown free space and inadequate capacity. Exclude only the owned bootstrap, live root/writer lock markers and handoff metadata. Preserve primaries/backups, overlays, queued-input journals, memory, media, ledgers, organisation and recovery receipts byte for byte before any supported relocation. Retain partial copies on failure; do not delete or merge them.
5. **Validate owner boundaries.** The owning SettingsStore relocation maps only its internal markdown-store directory and preserves unrelated setting bytes. The owning ChatFolderStore also refuses local workspace bindings into the source, while preserving external and remote bindings. Unsupported root-bound settings/JSON references, including opaque command strings (including absolute executables with arguments) embedding the old root, or populated managed worktrees refuse before copying; external resource targets are never followed or copied. Structured inspection is bounded to 32 MiB per record. Duplicate keys at any object depth refuse the entire structured record before copying; the repository's first-key parser and the transfer library's last-key parser must never select different pending authority or references. Strings containing authored JSON text remain ordinary strings. The chat storage guard inspects JSON primaries and recovery backups and refuses prepared/dispatched input, any queued `managed_turn` marker (including null or malformed identity) and unresolved remote execution, including independently retained active-turn/delivery IDs, delivery payloads, modern interaction responses, legacy singular response fields when the modern array is absent, and pending compaction even when process flags are false while preserving ordinary authored queues and all historical delivery facts. It neither rewrites a journal nor infers nondelivery. Existing startup recovery holds unprepared retained queues. Provider/native identities and historical root witnesses stay unchanged.
6. **Prepare and activate.** Version 2 `transition.json` records bootstrap/source/destination, retained directory identities, source/destination logical digests and physical object witnesses, originating preference revision, transaction ID and phase (`armed`, `staging`, `verified`, `starting`, `active`, `rolledBack`). Before the first staging publication, durably fence both root names with their source/destination receipts while retaining both writer freezes. An armed record whose source receipt differs from its exact prior receipt, or has any unexpected handoff metadata, refuses startup/reopen/cancellation; an incomplete early fence cannot be mistaken for an untouched source. Each change first publishes `transition-intent.json` as `publishing`, then the exact primary and phase archive, then an exact `acknowledged` intent. Bounded reads validate each opened file and every retained parent name through read completion. Combined receipt/acknowledgement admission retains and revalidates both file witnesses and their common metadata-directory identity; replacing that directory cannot mix an old receipt with a new acknowledgement. The paired reader normalizes the already-selected control path so the final relative default fallback remains supported without changing routing order. Bootstrap transition and acknowledgement use the same paired-reader primitive, retain the current primary's object witness and revalidate through startup/direct reopening/external-writer admission. A renamed or replaced primary cannot be admitted using previously read bytes and an unchanged acknowledgement. Root receipts record the same transaction, role, identity and digests, each with its own exact write-ahead acknowledgement and bootstrap locator; readable receipt bytes alone cannot authorize rollback or independent writers. Independent writers holding the shared profile lease must also verify the matching final bootstrap transaction, exact acknowledgement, root identity and digests before admitting an active destination or restored source; releasing a failed desktop owner cannot bypass an uncertain final publication. Older/missing locator metadata remains held without inferred upgrade. Rehash source and passive destination before `starting`; acknowledge destination ownership before loading settings/history or starting writers. An unknown primary, archive, root receipt or acknowledgement retains ownership and refuses success. `starting` and unmatched intent refuse startup without fallback.
7. **Retain and recover.** Later active launches reacquire all source locks and verify their immutable inventories and active receipts. Destination changes after activation are legitimate and never get overwritten from the source. A confirmed passive `staging`/`verified` transaction can roll back durably, preserving all source and destination files and retaining acquired leases. A passive inventory digest persists with rollback, and later launches/choices reacquire and validate those passive owners too. Normal startup refuses writers against a passive snapshot; explicit native `--uam-data-folder-rollback` can perform only that proven pre-activation rollback before profile startup. Armed-only follow-up cancellation refreshes the still-current source receipt to the cancellation identity before final bootstrap acknowledgement, without changing historical/passive receipts; first-ever cancellation leaves a plain root plain. Restored-source startup, direct opening, repeated rollback and later arming require the exact acknowledged source/rolledBack receipt, directory identity and both transaction digests. Older prior receipts never admit a new transaction. Only an acknowledged receipt-free cancellation with no prior transfer, retained chain or passive snapshot may leave the root plain; unexpected metadata holds it. Unknown publication or possible destination startup stays held. After `starting`/`active`, rollback requires a separately verified reverse transaction; reopening a stale source is never success. Source cleanup remains outside this task.

The retained bootstrap refuses foreign files, interrupted temporaries or more than 256 metadata entries before exclusion from copying. The bootstrap schema is strict and bounded (128 KiB per transition/intent, ownership-chain depth 16); unrecognized records refuse rather than upgrade or guess. Transition and root acknowledgement phases must be strings; malformed phase values refuse startup, external-writer admission and rollback without throwing or repairing the record. A migration-enabled release still needs scoped Claude/UI review, full desktop integration and Windows verification. Legacy helpers without the writer protocol have no proven quiescence, and linked helper-cache bundles remain unsupported inventory; neither is silently excluded or treated as safe. The current live gate must remain closed until validation is adequate. This implementation adds no provider removal, release, installation or real profile permission.

## Disposable validation

Additional cases cover connected preference/startup activation, repeated changes and fresh-owner reacquisition, foreign receipts, explicit passive recovery, prepared-input refusal, byte-exact authored queues and unknown active publication on reopen.

`UAM_DATA_FOLDER_TESTS_ONLY=ON` builds the same transaction/IO sources and cases without CEF, desktop, helpers or provider processes. Its inert test adapter uses the same non-destructive production root-lock primitive and deterministic fixture IDs. The fixture links the actual ChatRepository serializer, summary loader and queue-journal reconciliation. Only provider-native identity dispatch is replaced with a fail-closed inert adapter for an already-normalized synthetic identity; the production adapter still dispatches to the same runtime normalizer and is compile-checked separately. No provider operation or real profile is used. A fault injected after final preflight swaps the destination marker to a source-file symlink/hard link; the regression verifies refusal, retained source bytes and recovery records. Additional cases cover exact timestamp copying and actual repository overlay/journal loading, false-process-flag remote markers in primaries/backups, deterministic metadata-directory replacement, bootstrap primary rename/replacement during external/startup/direct-open admission, legacy pending-response fallback with settled-format precedence, actual repository-coupled null managed-marker refusal in primaries/backups/journals with retained safe cancellation, duplicate top-level/nested execution keys checked against the real repository JSON parser, and a capture/open/restore directory swap, missing/malformed/stale restored-source receipts and acknowledgements across passive rollback and active/restored follow-up cancellation, the receipt-free plain-cancellation exception, name-bound leases, foreign marker bytes, released-owner unknown staging/active/rollback publication, armed follow-up cancellation and its uncertain-receipt/final-publication intervals, absolute command references and an actual 100,001-file directory refused during listing. Platform process-service dispatch is compile-checked alongside application/CEF units; full desktop/platform runtime integration remains separate validation. Supervisor cases use only their own executable and temporary count files to distinguish ordinary, confirmed-folder and unconfirmed-folder restart. Frontend cases exercise selection, rejection, cancel, override and lost acknowledgement.
