# Performance suite

`scripts/perf_suite.py` measures the twelve user-facing areas the public [ADEmark](https://github.com/zqkra/ademark) comparison uses (speed, weight and tokens), with methods as close to it as practical, so a performance change can cite the same workload before and after. ADEmark's published results appear only as reference figures; UAM does not run or integrate with that harness. It reuses the timed native cases (their `[TIMING]` and `[SIZE]` lines), the frontend performance suite and the packaged app's existing `[performance]` log lines, and drives the packaged app through a deterministic fake provider; it adds no gate. Budgets stay in the tests, as [testing](../engineering/testing.md) describes. Real model token counts need a live provider and are never measured, so token rows report only what UAM adds to a request.

## Pieces

Each piece merges its figures into the `--out` file, so a change can rerun only the piece it affects. Python 3 with the standard library is enough; the `ui` piece needs `npm --prefix UI-V2 ci` first.

```bash
python3 scripts/perf_suite.py fixture /tmp/uam-perf-data                       # inspect the synthetic data root
python3 scripts/perf_suite.py --out Builds/perf.json native Builds/agent/uam_core_tests
python3 scripts/perf_suite.py --out Builds/perf.json ui
python3 scripts/perf_suite.py --out Builds/perf.json app Builds/agent/universal_agent_manager.app
python3 scripts/perf_suite.py --out Builds/perf.json driven Builds/agent/universal_agent_manager.app [--only typing]
python3 scripts/perf_suite.py report Builds/perf.json                          # markdown against tests/performance_baseline.json
```

On Windows, after `vcvars64.bat` and an app build, use `python` with `Builds\agent\Release\uam_core_tests.exe` and `Builds\agent\Release\universal_agent_manager.exe`; on the shared build box run the pieces inside its test lock, one at a time, with `TEMP` on F:. Run `app` and `driven` only from a signed-in desktop session: a process started over SSH or by `Win32_Process Create` runs in session 0, without an interactive desktop, where CEF window, GPU and compositing timings do not represent a user's machine. On the build box, start them through a scheduled task created with `/IT` (runs only in the logged-on user's session) and deleted afterwards. `app` records `windows_session`, `driven` records the Windows session or macOS GUI session and whether it is interactive, and the report warns about either.

| Piece | Measures |
|---|---|
| `native` | Each case alone in a fresh process: state-push work on 2,000- and 5,000-chat installs (unchanged, one chat changed, large loaded chat changed), streaming push cost, the 2,000-chat memory poll, a cold 10,000-message history page, a cold 1,000-chat catalogue, and the bytes UAM adds to a request (UAM-Control and Computer Use MCP tool schemas, prompt text wrapped around "hello"). |
| `ui` | Runs `npm run test:performance` with `VITE_UAM_PERF_TIMINGS=1`, which makes `expectWithinBudget` print each timing. Loop indices fold into one label (p50, p95, max). Exits with the suite's own result. |
| `driven` | The packaged app on the fixture with a fake provider, driven through Chrome DevTools: new thread, first word, long thread, typing lag and RAM under load with five agents streaming, and per-thread memory. Each scenario runs on its own fresh launches (`--runs`, default 3) and `--only` reruns one; see below. |
| `app` | Writes a fresh fixture and starts the packaged app on it with an allowlisted environment: fixture home, system-only `PATH`, no tokens, API keys or provider configuration paths. The fixture turns every provider off for this computer, so chats and history still load but no account allowance, version sweep or CLI probe reads the machine's real credentials. Cold start is launch until the UI logs its first native bridge reply on the new data root; relaunch is the median of three later launches, each after a forced stop (SIGTERM to the macOS crash supervisor, `taskkill /F` on Windows), not a clean quit. After a 30 s settle, idle CPU is the process tree's CPU time over 60 s (percent of one core) and RAM at rest is its macOS `phys_footprint` or Windows private working set. Slow poll ticks (≥ 50 ms, with per-stage maxima) and slow state-patch serialization come from the log the app already writes. |

## Driven scenarios

`scripts/perf_driven.py` starts the packaged app on a fresh copy of the fixture with OpenCode turned on and every other provider off. Every provider executable on its `PATH` is the fake ACP peer from `tests/companion_native_smoke.py`, so no real CLI, account or token is ever used: it answers at once and, for a prompt containing "stream check", streams a fixed reply (prose, a code block and a diff) two words per delta every 25 ms, about 80 tokens per second. The script drives the app through Chromium's stock `--remote-debugging-port` switch, which the app already passes to CEF, with input events dispatched through the browser's input pipeline (mouse clicks, key presses with real key codes, wheel events). A trigger's time is its input event's timestamp in the page (a click, dispatched on release, or the Enter keydown), cleared when each wait is armed; an end is the frame after the condition first holds in the DOM. Methods follow the published ADEmark definitions where practical:

| Metric | Method (per run; a metric is the median across runs) |
|---|---|
| New thread | From the open seeded short chat: click New chat, then Create chat with the defaults; Create's click to the new chat's composer enabled and painted. Median of `--samples` (6). The dialog's open time is `new_thread_dialog_ms`. |
| First word | In each new empty chat, the Enter that sends "stream check" to the first streamed word painted. Median of 6. `first_word_request_ms` is Enter to the fake receiving the prompt. Includes starting the fake's process on the first prompt; UAM's own log times that launch. |
| Long thread | From the short chat to the 2,000-message chat until its newest 50-message page is painted (UAM opens it there); then 20 wheel events at 60 Hz toward the top, counting frames that took over two idle frame intervals while they arrive (`long_thread_scroll_gaps`: over 33 ms at 60 Hz, over about 67 ms in an RDP session at 30 frames per second), with the worst gap, the scroll's median frame and the idle interval (`long_thread_refresh_ms`). Median of 5. |
| Typing lag p95 | Five new chats each send "stream check" 2 s apart; the last stays in front. Sixty letters are typed into its composer, one every 250 ms ±20 %, each from its keydown to the frame after its echo; no echo within 2 s is a miss (`typing_missed`). |
| RAM under load | During that run, the app group's footprint is sampled for `--load` seconds (180) as fast as the platform tools allow (target 4 Hz; about 1 Hz on Windows), except while letters are typed, so the sampling tools do not load the typing probe: p95, with the peak beside it. |
| Per-thread memory | Five new chats with a live fake session that has answered one prompt, then fifteen more: (median app-group footprint over a `--rest` window (60 s) at twenty − the same at five) ÷ 15. The live fake processes are counted in `per_thread_live_agents`. |

The app group is the app's own processes (main, CEF helpers and its own stdio servers), measured as in `app`; the fake provider and its shell are excluded, as the reference excludes agent subtrees. The fake's process start and reply speed are not a real agent's, so first word and the streams load only what UAM does with them. In this mode the fake reports an OpenCode version from before native compaction metadata (1.17.20), so UAM skips the per-send query of OpenCode's own database, which a real current OpenCode adds to first word. Each run records the Windows session (id, name such as `rdp-tcp#0`, state) or macOS GUI session and the GPU process state; a run waits while its Windows session is not Active and is discarded if the session stops being Active during it. An RDP session can use another render path and frame rate than a local console, and the report says so.

While a driven app runs, any local process can control it through the DevTools port, as it could any Chromium started with that switch: Chromium binds the port to 127.0.0.1 only, the script picks a free port, and the app runs on a disposable data root with the `app` piece's hermetic environment and is stopped at the end. A normal launch never passes the switch.

The fixture is 2,000 chats across 20 workspace folders and six providers, twelve short messages each, with one 2,000-message chat; it is synthetic. Because providers are off, idle figures exclude provider version and allowance refreshes a real install with providers on would run.

## Reading the report

The first table has the twelve metrics beside the committed baseline and the published reference figures (T3 Code 2.74 and the leading apps; bare Claude Code CLI for tokens). The RAM-at-rest references were taken with five threads open, which `ram_rest_5_threads_mb` matches; UAM's `ram_at_rest_mb` has none open. `*` marks an in-process frontend figure standing in for an end-to-end row (no CEF, IPC or paint) and names what it measures, and `†` marks only what UAM adds to a request. A stand-in is narrower than its row: typing lag comes from input events with at most one chat streaming, not five agents, and the long-thread figure is the bounded 50-message first page UAM renders for a 2,000-message chat. Component figures follow, named by unit suffix. Treat a difference as real only when repeated runs on the same machine agree; hosted runners move by tens of percent.

| Metric | Covered by |
|---|---|
| Cold start, relaunch, RAM at rest, idle CPU | `app`, end to end |
| New thread, first word, typing lag, long thread, RAM under load, per-thread memory | `driven`, end to end; without a `driven` run, the report falls back to the `ui` stand-ins for new thread, typing lag and long thread (empty chat to usable composer; input to committed draft; 2,000-message history page) |
| "hello" and real-prompt tokens | `native` request overhead only: UAM-Control tool schemas plus prompt text wrapped around the typed prompt, at about 4 bytes per token; text sent separately or at session start is not counted, and real counts need a live provider |

## CI and baseline

Pull requests into `uam/v5.2-performance` that change something other than documentation, notes or the iOS app run a report-only **Performance report** job on macOS ARM: `native` and `app` on that run's built test binary and packaged app, merged with the timings the Frontend job recorded, then `report` into the job summary and a `uam-performance-report` artifact. It runs with whatever inputs exist even when an upstream job failed or was skipped (a frontend-only change has no native or app figures), and its measuring steps may fail without failing the job, so the check stays green. The job does not run `driven`, and its figures only indicate: performance numbers for a change come from local runs on one machine, before and after. `tests/performance_baseline.json` holds figures from the Windows build box with the machine, revisions, commands and session in its `meta`: `native` and `ui` from their recorded revision, and `app` and `driven` (medians of three, per-run values under `meta.packaged_app`) from a later revision, run in David's signed-in RDP session with no compile or other test running. An RDP session presents about 30 frames per second, which bounds frame-based figures. A report against a baseline from another machine says so, and its Δ is only indicative. Replace the file in the pull request that intentionally moves the figures, from the same machine. `tests/perf_suite_test.py` checks the parsing and that every named native case still exists.
