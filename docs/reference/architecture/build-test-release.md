# Build, test and release

> Engineering reference updated from `uam/v5-improvements` (`e28ba717`, 2026-10-16). This records implementation detail and historical verification, not full feature acceptance. Start with the [feature guide](../../README.md); its agreements and [documented corrections](../../documentation-review.md) take precedence over stale claims here.

The repository builds a C++ native app and a React frontend. CMake configures the native target, invokes the UI build and packages the resulting assets. The source-tree `UI-V2/dist` is not the packaged output.

## Flow and invariants

Use `npm --prefix UI-V2 ci`, then the requested UI checks. Configure CMake only inside `Builds/` (or an accepted CLion `cmake-build-*` directory); package outputs live under the build tree. Native tests use the custom framework in `tests/core_tests.cpp` plus focused test sources registered by CMake. UI tests use Vitest. Keep build outputs and generated frontend files out of source changes.

Reuse the task's build folder and dependencies between edits. `cmake/ui_build.cmake` tracks frontend inputs and emits `index.html` only when they change; native-only builds reuse the existing frontend. Its diagnostic timestamp is generated during an actual UI build, so unrelated CMake regeneration does not invalidate it. `cmake/package_inputs.cmake` keeps resource-only and runner-only changes connected to desktop copying and signing. The desktop package receives only `markdown-store/bundled/`, kept at `markdown-store/bundled/` beside the UI resources; `cmake/check_packaged_markdown_store.cmake`, registered as CTest `uam_packaged_markdown_store`, compares the built app's store with that source set and fails on any extra or missing file. macOS and Windows archives zip this build output, so the check covers both. UI, dependency-lock, feature and presentation-version changes still invalidate the frontend. A failed UI build removes its entry point so the next build retries.

App sources compile once into two object libraries: `uam_core_objects` (shared by the app, `uam_core_tests` and the connected handler fixtures) and `uam_app_objects` (CEF handlers and app-only services, shared by the app and the handler fixtures). Both copy the app's final compile settings. `runner_proxy.cpp` and the platform PTY stay per target because tests compile the proxy with the development runner version and the handler fixtures replace the PTY. `uam_core_tests` precompiles `tests/test_harness.h`, which every core test includes; its non-test sources skip the precompiled header.

Make/Ninja builds automatically use an installed `ccache` unless a compiler launcher was explicitly set. With ccache 4.8 or later CMake passes `base_dir` set to the source root, so separate worktrees using the same build-folder name share cache hits, and `sloppiness=pch_defines,time_macros` so precompiled-header users remain cacheable. The changing remote-runner source fingerprint lives in a generated header included by `runner_main.cpp` alone; other helper objects retain reusable compile commands. Release artifact validation and checksums remain enabled on packaging builds.

The macOS packaging script sets Linux cross-build `CMAKE_AR` and `CMAKE_RANLIB`,
including their C/C++ compiler-specific variants, to the `cmake/zig-ar.sh` and
`cmake/zig-ranlib.sh` wrappers. They forward each argument unchanged to Zig's target-aware
archive tools, using `UAM_ZIG` when supplied and `zig` on PATH otherwise. Reconfiguring
an existing helper folder also loads `cmake/zig-archive-tools.cmake` through
`CMAKE_PROJECT_INCLUDE` after cached compiler metadata, so cached host-tool variables
cannot silently override the selected archive tools. This relinks static archives without cleaning
or recompiling unchanged source objects. Host macOS archive indexing is not compatible
with the Linux ELF objects; Windows cross-builds continue using MinGW-w64's archive tools.

For focused native checks, build `uam_core_tests` and pass exact names to `scripts/run_native_tests.py`; `--list-tests` on the binary reports the compiled inventory. The `uam_check_core` target runs that complete inventory in batches across two separate processes, validating that every requested case passes exactly once. Processes isolate environment variables and singleton state; individual timing budgets and assertions remain unchanged. `UAM_TEST_TIMINGS=1` reports per-case durations on direct binary runs. The original serial `ctest` registration remains available. When using `uam_check_core` as the final core gate, exclude `uam_core_tests` from the subsequent CTest run to avoid executing the same inventory twice. Build all required test targets before running the remaining gates. Full commands are in [AGENTS.md](../../../AGENTS.md).

Unrelated CEF handler fixtures use `tests/cef_handler_fixture.h` to construct the real handler through its private test seam before either usage-history or account-allowance service is created. Configuring a private provider command or avoiding allowance actions does not isolate the ordinary constructor, which starts background readers. These fixtures exclude usage actions; usage tests require explicit isolated services. The public application constructor retains its existing startup behavior.

Windows executables (the app, `uam-runner`, `uam_core_tests` and the CEF handler test executables) embed `src/uam_long_paths.manifest`. Besides long paths, it declares Windows 10 support. Without that entry, Windows reports version 6.2 (Windows 8) to the process in a signed-in desktop session, including kernel32's file version. Chromium then hits `NOTREACHED()` in its client-hint platform-version code, and CEF crashes about 4 seconds after start (`libcef.dll`, `0x80000003`). Background SSH sessions do not apply that version lie, so they hide the crash. The core case `WindowsManifestDeclaresWindows10SoCefSeesTheRealVersion` fails when the entry is missing, because Windows then reports a pre-Windows 10 version to every session type.

The supported release slice has six provider implementations and the React/CEF, ACP, terminal, workspace and memory paths. Do not add excluded engines or remove a provider without explicit direction. Update the root V5 log in the same implementation commit and retain review/user acceptance flags until they are actually complete.

## Build flags

`cmake/build_features.cmake` declares the provider and feature options and normalises each to 0/1 once. `UAM_FEATURE_DEFINITIONS` and `UAM_PROVIDER_DEFINITIONS` carry those values to the app, runner and test targets, and `src/common/config/build_features.h` stops compilation when a definition is missing instead of defaulting it on. `cmake/ui_build.cmake` passes the same values as `UAM_FEATURE_<NAME>=0|1`; `UI-V2/src/config/featureDefines.ts` turns them into Vite `define` constants (`__UAM_FEATURE_<NAME>__`) and rejects any other value. `buildFeatures.ts` exports them, so guarded branches, provider metadata, logos and settings sections are removed by the bundler. A Vite plugin turns an excluded provider's logo and SSH-only stylesheets into empty side-effect-free modules, `postcss.config.js` drops selectors and custom properties named after an excluded provider or feature, and builds without phone access omit the companion manifest link, manifest and service worker. Where a chunk cycle keeps an imported constant opaque, the define is used directly with a comment.

Native exclusion uses per-provider and per-feature source lists in `CMakeLists.txt` for the app and the runner. `provider_ids.h` gives an excluded provider a placeholder id that no saved data can carry, and lists only included providers in its id, alias and version tables, so shared comparisons stay valid while the real id leaves the binary. Usage history roots, Markdown Store import roots, account allowance readers, the OpenCode model catalogue and runner requests are compiled per provider. Bridge routes for SSH, routing, remote recovery, computer use, phone access and OpenCode configuration import exist only when their flag is on, so excluded actions are unknown. Small inline no-op hooks (Claude quota waits, Antigravity and OpenCode usage scans) keep shared callers unchanged. `provider_ids::IsRetainedExcludedProviderId` is true only in a reduced build, for a well-formed id that build does not include: central MCP switches, provider availability, chat defaults, memory worker bindings and shell actions keep such entries through load and save (an interface save of the central configuration carries them over), runtime lookups use included ids only, and shell actions naming one are neither installed nor run. The active, default new-chat, host-default and permission-reviewer choices use an included fallback at runtime; `AppSettings::excluded_provider_selections` remembers the saved choice and `SettingsStore` writes it back while the fallback is still selected. Excluded ids are kept as saved: canonicalising their aliases would put the excluded provider's names back into the binary, and a full build canonicalises them on load. The runner rejects the placeholder id. Usage accounting and coverage rows written by a full build load in a reduced build with the excluded providers' records skipped, so they are neither counted nor shown and the saved data stays intact for a later full build. The Gemini computer-use policy ships only with Gemini and computer use, the local-network privacy key only with phone access, and an SSH build recreates `Resources/remote` on each package step. Restricted macOS release links of the app and runner add `-Wl,-dead_strip -Wl,-x` (`UAM_RESTRICTED_BUILD`), because both are otherwise linked without dead-code stripping and keep local symbol names.

`scripts/check_build_flag_leaks.py` scans printable ASCII, UTF-16LE and UTF-32LE strings of the app and runner (with the machine's source and build folder spellings replaced, so `__FILE__` paths neither leak nor make residue machine-specific; `--local-path` adds folders for outputs copied from another machine), packaged resource names and text, and `UI-V2/dist/**` for each disabled flag's names, ids, logo names and action names, and checks the remote helper folder. Interface and resource matches fail unless `scripts/build_flag_leak_allowlist.json` excuses them with a reason, an optional path, a pattern tested against the token around the match (up to 60 characters either side, stopping at quotes, separators and operators, so neighbouring minified code cannot excuse it) or an exact identifier, and a capped budget. Native matches are excused only by `scripts/build_flag_native_residue.json`, which lists per executable file name and flag the exact text around each reviewed match and how often it may occur, so a new or changed string fails even after another is removed; `--record-residue` adds new matches for review and leaves the gate failing until their flag has a reviewed reason, and a failing native CI row uploads that candidate file. Native rows whose residue is not yet recorded run with `continue-on-error`. App builds also fail when the interface bundle is missing or SSH is on without a runner. Packaging rules (expected executable, helper folders) also run when no flag is disabled, such as `UAM_PACKAGE_REMOTE_RUNNERS=OFF` alone or `UAM_RUNNER_ONLY=ON` with every provider. `tests/build_flag_leak_gate_test.py` covers the gate, `uam_build_flag_profile_tests` compiles a Claude-only, features-off profile with `settings_store.cpp` to check the id tables and that settings with excluded providers survive a load and save, `uam_build_features_require_definitions` proves `build_features.h` refuses missing definitions, `tests/ui_build_incremental_test.py` covers normalisation, and `.github/workflows/build-flag-leaks.yml` builds every single-flag and single-provider profile: bundles on each relevant pull request, native apps on schedule, manual runs or the `build-flags` label. The default all-provider test target is the only supported native test configuration.

## App icon

`scripts/make_app_icon_art.py` draws the flat artwork (`assets/app_icon.png`) and `scripts/compose_macos_icon.swift` turns it into the approved icon tile (`assets/app_icon_macos.png`) and `app_icon.icns`. `scripts/make_windows_icon.py` generates `assets/app_icon.ico` from that tile with the 16, 20, 24, 32, 40, 48, 64, 96, 128 and 256 pixel sizes; each PNG entry records the tile's SHA-256. `src/uam.rc` embeds the `.ico` as `IDI_APP_ICON`, and the CEF window and taskbar icon load the same tile copied beside the executable. After changing the artwork, run on macOS with Pillow installed: `python3 scripts/make_app_icon_art.py`, `swift scripts/compose_macos_icon.swift assets/app_icon.png assets`, then `python3 scripts/make_windows_icon.py`.

CTest `uam_app_icon_resource` (`tests/app_icon_resource_test.py`) fails when the `.ico` misses a size or was not generated from the current tile. On Windows it also reads the built executable's icon resource and requires the same images. Ninja tracks only `#include` in resource scripts, so CMake names the `.ico` as an object dependency of `src/uam.rc`; without it, incremental Ninja builds kept the previous icon. Explorer may still show a cached icon for an existing path until its icon cache refreshes.

## Local macOS signing

Set `-DUAM_MACOS_SIGNING_IDENTITY=<40-character identity SHA-1>` to sign the app and its owned helpers with an available certificate from `security find-identity -v -p codesigning`. CMake rejects a missing identity and stops on signing failures. The default `-` keeps ad-hoc signing available for machines without a certificate. A stable certificate requirement lets macOS retain privacy grants across rebuilds after the signed app receives its initial grant; changing from ad-hoc signing can require consent again. Existing entitlements are preserved and a valid vendor-signed CEF framework is verified without being resigned. An unsigned CEF framework, as shipped for Intel, is signed before the helpers and main executable because codesign rejects a bundle executable while nested code is unsigned.

## Separate manual test bundles on macOS

A separately named copy must also have a distinct bundle identifier and a distinct `UAM_DATA_DIR` when it needs to run alongside the normal application. The existing data-root lock remains enforced: a second process targeting the regular application's live database exits before creating a window. A renamed bundle alone does not isolate that database.

Build the native executable and `UI-V2/dist` of a test bundle from the same commit. Swapping only the frontend into an older bundle mixes native and React behaviour: a native binary from before integrated window controls keeps the system title bar. Through `--remote-debugging-port`, on macOS `outerHeight - innerHeight` is `0` for the frameless window and 32 when a system title bar is present.

For private manual-test packaging, set a test-only `CFBundleIdentifier` and `CFBundleDisplayName`, and put the absolute test data-root path in the bundle's `LSEnvironment` dictionary. [Apple documents this environment setting for Launch Services launches](https://developer.apple.com/documentation/bundleresources/information-property-list/lsenvironment); direct command-line runs need the environment set explicitly. Re-sign the outer test bundle while preserving entitlements and verify its nested signatures. Keep the production build and normal application bundle unchanged.

A history-dependent manual test needs a populated profile: copying only `settings.txt`, `folders.txt` and `providers.txt` produces empty workspace counts and does not establish sidebar acceptance. With the test app closed, take a per-file consistent snapshot of saved chat JSON into its private data root, retain folder membership, titles, pins and complete transcript messages, and verify the written transcripts against the source snapshot. Existing snapshot chats must use the supported `imported_read_only` flag; remove queue payloads, remote recovery/control capabilities, temporary cleanup ownership, provider handoff state, agent-run and goal execution state, and disable memory/control on those copies. Preserve the nonempty `agent_run_id` and `goal_owner_chat_id` visibility markers for internal chats while retaining `imported_read_only` and omitting the run ledger; clearing those markers incorrectly exposes hidden transcripts in the sidebar. Never copy live queue outboxes, runtime directories or agent-run journals. Native session identifiers may remain as read-only import ownership metadata. Regenerate summary caches from the sanitized snapshot with matching source sizes and message counts rather than mixing stale source caches into the test profile. This is a saved-history snapshot, not a global transaction against the running production database; new test chats and imports remain independent. Verify a real Launch Services launch, the private data-root log entry, populated sidebar counts, selection of an existing conversation with rendered history, and the connected backend before calling the test bundle ready. Static signature and resource checks alone do not establish manual-test readiness. Re-signing with the test bundle identity changes the executable signature bytes; compare unsigned scratch copies to establish unchanged executable code.

The opt-in remote OpenCode first-message case requires explicit alias, workspace, executable and resource-directory inputs plus `UAM_REAL_REMOTE_OPENCODE_SAVED_MODEL` and `UAM_REAL_REMOTE_OPENCODE_EXPECTED_MODEL`; the latter identify the stale saved spelling and its advertised canonical model. It has no operator-specific model default and remains unexecuted when any required input is absent.
