# Permissions and notifications

> Engineering reference retained from the trial base (`3a7c8477`, 2026-10-16). This records implementation detail and historical verification, not full feature acceptance. Start with the [feature guide](../../README.md); its agreements and [documented corrections](../../documentation-review.md) take precedence over stale claims here.

The native permission layer decides whether structured provider tool requests need a user response. The UI displays those requests and returns an explicit decision. App-wide notices currently have multiple presentation paths; a single notification system is an agreed target, still pending implementation.

## Flow and invariants

ACP permission handlers classify requests and consult per-chat approval mode, command auto-approval, global computer-use policy and any configured reviewer. The plan mode has a read-only ceiling. The frontend answers through `resolveAcpPermission` or the relevant computer-use action. Keep the original request identity attached to each response and fail closed when policy or reviewer state is unavailable.

AI Review uses Claude's native `auto` mode or Codex's confirmed native `auto_review` setting when active; residual native prompts remain user decisions. Other structured requests can use the configured provider reviewer. Its approval, like every automatic approval, selects the single offered `allow_once` option or Codex's exact `accept` decision id (`AutoApproveOptionId`); automatic denial selects the single `reject_once` or Codex `decline`. Labels are never read, and zero or several candidates leave the request for the user or send Cancel. Outside captured read restrictions, Codex permission grants use `turn` scope unless the user explicitly selects the offered `acceptForSession` option; a captured read-only turn cannot grant session-wide authority. Generic ACP `rawInput` preserves any valid JSON value, including strings, arrays and null, while native request parameters remain objects; malformed, oversized or sensitive review input stays manual. Reviewer admission and verdict delivery require the same runtime incarnation and request ID, and each actual process start renews that incarnation. Plan and managed read-only ceilings still apply. Codex reviewer workers disable shell tools and web search, use the read-only sandbox and reject tool-bearing output. These restrictions do not disable every MCP or provider tool; broader isolation remains an unsupported capability, so the worker is not described as fully text-only.

## Captured read response boundary

The implemented final guard checks captured agent-read and goal-review restrictions before the public manual resolver or shared automatic response helper constructs, persists or delivers a decision. Provider adapters classify typed denial and one-time permission choices; labels cannot authorize a persistent grant, and captured automatic approval prefers the offered one-time choice. Command checks use the ephemeral `execution_command` populated from a typed native command field, never the display content or reason fallback. Only supported read operations and recognized non-action questions can receive one-time approval. OpenCode's native repeated-call question requires the known producer metadata shape, with stronger pattern and tool-link checks on full HTTP snapshots; this does not attest arbitrary trusted plugins. Ordinary Plan exit remains a separate current-request transaction with native confirmation.

Frontend option projection uses the same policy decision while leaving the native pending option vector and request fields untouched. A filtered display is not delivery authority: stale or forged responses still pass the final backend check. Captured saved-response replay first normalizes the fresh native permission, then compares the complete saved JSON with the provider encoder for an admissible current choice or cancellation. The encoder receives explicit immutable pending state, without temporarily replacing the live request. Pending cancellation admits only the exact native cancellation response.

A different saved response retains the ordinary reused-ID conflict unless a captured resolver owns the current pending request. Permission replacement requires the previous reply to fail the current ceiling and the new reply to pass; question replacement requires provider preparation of the fresh answer. Copilot rejects its reserved implementation choice under read-only review before treating other text as feedback. Replacement preserves queue bounds, saves synchronously before delivery and restores the complete previous receipt vector on save failure. The captured guard, command provenance, automatic one-time selection, decoded replay, atomic replacement, OpenCode question identity and Copilot hidden-choice refusal have protocol and integrated native verification plus scoped source-review closure. The CEF gate passed after restoring its required explicit application-bundle environment; this does not establish desktop journey acceptance. Desktop automation could not establish a visible window (`cgWindowNotFound`), so actual offered-choice and journey acceptance remains inconclusive. Live-provider, Windows, SSH and user acceptance remain pending.

If persistence succeeds but permission-response delivery fails, the safe saved choice remains in the recovery queue. Retrying the same choice or reconnecting can deliver it; an attempt to substitute another already-safe choice retains the unresolved-ID conflict. This is a known optional usability follow-up, not permission to weaken the captured ceiling or rewrite an unresolved safe decision.

The [literal command filter](../../../src/common/security/read_only_command.h) admits bounded supported command forms and refuses unsupported operators, substitutions and command options. Risk-tier classification in `command_safety.h` calls it for its Allowed level rather than keeping a second list. Typed native command fields are the sole command source; generic display content and reasons do not supply execution authority. Each pending request captures a `ReadScope` (workspace, provider-reported working directory, data root, local or remote) in `ApplyCommandSafetyDecision`, which every provider adapter calls before saved-response replay. Path operands and path-valued options resolve with `weakly_canonical` locally (lexically for remote workspaces) and compare case-insensitively on macOS and Windows. Admitted `git diff`, `git log` and `git show` require both explicit `--no-ext-diff` and `--no-textconv`, log/show also `--no-show-signature`, and status `--ignore-submodules`, with protocol verification covering the filter. `TrustedExecutable` resolves the admitted name against the `PATH`/`PATHEXT` captured from UAM's environment, emulating `cmd.exe`'s working-directory-first search on Windows; remote hosts are not resolved. `ReadCommandEnvironment` adds `GIT_PAGER=cat` and `PAGER=cat` to every structured provider launch and, locally, appends `core.fsmonitor=false` after any inherited `GIT_CONFIG_COUNT` entries. Admitted commands still trust the provider's own search path where it differs, other repository configuration and index refresh. Optional controls such as disabling pagers or optional locks are deployment hardening, not new command-admission requirements. The filter does not enforce an operating-system sandbox. Native terminal commands and provider operations that bypass UAM callbacks retain their native control boundary.

## Launch configuration ceiling

A launch has a read ceiling when its chat is in Plan; read-only agent and goal-review launches are mapped to Plan before argv, environment and setup requests are built (`LaunchHasReadCeiling`). Structured routes, inspected against the installed CLIs on 2026-11-12:

- **Claude Code 2.1.322:** `--setting-sources ""` loads no user, project or local settings (so no allow rules, hooks or plugins) and `--strict-mcp-config` keeps only UAM's MCP servers. A local launch receives the authentication and routing keys of the user's `settings.json` (`apiKeyHelper`, `awsAuthRefresh`, `awsCredentialExport`, `forceLoginMethod`, `forceLoginOrgUUID`) and its restrictive `permissions.deny`/`ask` rules through `--settings`, redacted from launch diagnostics, while its `env` values go to the process environment rather than the command line. An SSH launch cannot read the remote file first, so it keeps standard sign-in only. Project and local deny rules are not carried; managed settings still apply. Claude restarts on a permission change, so a live switch into Plan relaunches with these arguments.
- **Gemini CLI 0.67.0:** a ceiling launch passes `--admin-policy` with `gemini-plan-ceiling.toml`, a Plan-only copy of Gemini's own Plan and read-only rules. Admin tier outranks workspace and user policies, settings `tools.allowed`, `--allowed-tools`, trusted MCP servers and saved approvals. Because the copied read and plan-file allows also sit in the admin tier, a user or workspace rule denying one of those read tools no longer applies in Plan. The flag replaces any `adminPolicyPaths` from settings for that launch, so Default launches omit it. A ceiling launch is refused on SSH hosts, which cannot receive the file, and locally if the file is missing. Gemini ignores `--admin-policy` when system policies exist; those managed policies then decide. Hooks remain native.
- **OpenCode (V1 ACP):** `OPENCODE_PERMISSION` keeps `*: ask`. A ceiling launch adds the `plan` agent's whole permission object to inline `OPENCODE_CONFIG_CONTENT` (merged with the user's own local value), asking for every known tool with Task and Computer Use denied, because agent-level rules are merged after the global ones. It also sets `OPENCODE_DISABLE_PROJECT_CONFIG=1`, dropping repository config, agents and plugins. Custom tool patterns in the user's global agent config that sit alongside its own `*` rule are not overridden; the V2 bridge drops this agent override and relies on its evaluation guard. V1 live behaviour needs verification.
- **Copilot CLI 1.0.109:** `--deny-tool=shell`, `--deny-tool=write` and `--deny-tool=memory`; Copilot documents that deny rules win over every allow, including saved approvals, `--allow-tool` and `--allow-all-tools`. Every structured launch sets `COPILOT_ALLOW_ALL=false`. Saved approvals for MCP tools are not denied.
- **Codex** applies its read-only sandbox per turn, and **Antigravity** auto-denies anything needing approval in Plan; neither gains a new structured route here.

CLI View maps a read-only agent to Plan whatever central configuration or UAM control says. Codex adds `--sandbox read-only --ask-for-approval on-request` (replacing any kept sandbox or approval option, which Codex refuses to repeat), Gemini `--approval-mode plan`, both before any positional `--`, and Claude, Copilot and Antigravity keep their native Plan options. OpenCode's terminal has no Plan option UAM can set across V1 and V2, so its CLI View refuses Plan and read-only chats. `ClassifyPermissionFlag` treats bypass spellings (YOLO, skip-permissions, `-y`, approval `never`, `danger-full-access`, `bypassPermissions`, allow-all) as always removed and refused for CLI View, and grant spellings (`--allowedTools`, `--allow-tool`, `--allow-url`, `--settings`, `--setting-sources`, `--policy`, `--admin-policy`, `--mode`, `--profile`, `--autopilot`, `--assisted-approval`, `--dangerously-bypass-hook-trust`, `--permission-mode`, `--approval-mode`, Codex `-a`/`-s`/`-c` approval, sandbox and permission values) as removed under a ceiling; both include `=` values, split and variadic values, attached short values (`-sdanger-full-access`, `-csandbox_mode=…`) and single-dash long forms, and stop at a bare `--`. Removing `--policy` or `--settings` under a ceiling can also drop a user's own restrictive rules in them. Computer Use uses `AttachableForLaunch`, so Plan launches neither attach nor pre-allow its tools, including the setup-request servers.

Residual limits: Gemini and OpenCode switch modes in place, so a process launched outside Plan keeps its launch configuration (without these ceiling settings) after a live switch into Plan until the next launch; read-only agent and goal-review turns are launched in Plan. A running Codex process launched outside Plan likewise keeps any Computer Use attachment until relaunch.

## Notifications

The agreed notification direction routes app-wide messages through the notifications panel and one shared transient alert. Existing separate notices remain until that work lands. UI presentation follows the [design language](../../ui/design-language.md); settings controls follow [settings rules](../../ui/settings.md).

`UI-V2/src/services/updateCatalog.ts` normalizes the first 10,000 characters of UAM and managed-provider release bodies into optional plain-text `releaseNotesExcerpt` values capped at 500 characters. Provider notes come from exact official release tags matching the npm or Homebrew version, with duplicate versions sharing a request and drafts or mismatched tags omitted. Failed optional notes preserve independently obtained update versions; the existing 15-second deadline covers both version and note requests, with five provider groups active at most. Validated caching and local/remote update projection preserve each installation method's own excerpt. GUI rendering remains pending.

## Provider-bound agent imports

OpenCode Markdown imports support only a flat permission subset: `edit: deny` is required, with optional `bash: ask` or `bash: deny`, and import requires read workspace access. Nested or path-pattern rules, aliases, merges, duplicate keys and other security fields remain rejected. Literal and simple quoted top-level keys are recognized; escaped or complex keys and unsupported indentation fail before security classification. Source descriptions do not establish a universal no-write guarantee: `bash: ask` retains its native approval semantics.

The canonical ordered `openCodePermission` policy travels inside the immutable agent Markdown snapshot. Generic edits preserve it even when an older frontend DTO omits it, and cannot widen or change it; replacement imports cannot strip or change the existing binding. Provider-only metadata omission still requires acknowledgment. Import validates the definition before atomic publication.

A bound policy can launch only through the local structured OpenCode ACP isolated adapter. SSH, central-native setup, provider preferences, terminal launches and other providers reject it rather than falling back to a weaker representation. Both adapter config and native-agent policy retain the source edit/bash rules plus task and computer-action denials, without a generic permissive wildcard. Existing generic agent adapters keep their previous behavior. Inherited `OPENCODE_CONFIG_CONTENT` is rejected for a bound policy when invalid, non-object, larger than 16 KiB, or containing agent, default-agent or legacy-mode overrides; the value is neither rewritten nor logged. Compatible permission-only and MCP-only inline configuration remains supported, with the bound native-agent policy retaining precedence. This is a scoped launch guard, not general inline-configuration sanitization.
