# React and CEF transport

> Engineering reference retained from the trial base (`3a7c8477`, 2026-10-16). This records implementation detail and historical verification, not full feature acceptance. Start with the [feature guide](../../README.md); its agreements and [documented corrections](../../documentation-review.md) take precedence over stale claims here.

The React app runs inside the native CEF window. React sends action envelopes through `window.cefQuery`; C++ validates and dispatches them. Native state and terminal output return through `window.uamPush`.

## Flow and invariants

At startup the one-shot `getInitialState` pull is the only full state; it applies when its `stateRevision` is equal to or newer than the store's, because a partial `statePatch` from the poll loop can arrive first at the same revision and must not leave Collections, workspaces and provider identities empty (#622). Native stamps each `statePatch` at revision + 1 while `getInitialState` serialises the current revision, and the reply and pushes use separate IPC paths, so a newer diff-only patch can still overtake the snapshot. React never applies that older snapshot over newer patch data: until a full state has hydrated it re-requests `getInitialState` after 100, 300 and 900 ms, resetting to the first delay whenever a stale reply is newer than the previous stale reply but never exceeding eight pulls per chain (Retry starts a fresh chain), and a reply at or above the store's revision hydrates and cancels any pending re-pull. Both native handlers run on the CEF UI thread, so this is IPC ordering, not locking. If the re-pulls stay behind or hit the cap, or the pull fails, returns an invalid state or throws while applying, `bootstrapStateError` drives the [startup error notice](../../ui/interface-recovery.md); Retry starts a new bounded pull, and errors arriving after hydration are ignored.

After hydration, native does not resend a built patch, so React repairs a loss itself. This relies on two native facts: every published diff, including a corrective one, is stamped exactly the last revision + 1, and a snapshot at revision R contains every patch up to R because both are produced on the CEF UI thread. A patch whose revision is not exactly the last applied revision + 1, a push the sanitiser rejects when it was or may have been a state message, and an exception while handling a push each request one full `getInitialState` pull, and the pull logs its reason once to the console. Gapped patches still apply, because their fields are current. Requests within 100 ms coalesce behind one timer or in-flight pull, and successive pulls are spaced at least 1 s apart, doubling to 30 s while gaps keep arriving; the spacing resets only after a minute without a gap, so a recurring fault between clean patches costs at most one full serialisation per spacing step. A failing pull stops after five attempts; the next patch tries again at the current spacing. Patches keep applying during the pull, so approvals and turn state never wait for it, and copies are kept (up to 512). When the reply arrives, a snapshot at or above the store's revision is applied, a same-revision one included because it is complete. A snapshot behind the store (its reply overtaken by later patches) is composed with the kept copies newer than it and published as one store update, so subscribers never see the older revision. If a full `stateUpdate` arrived during the pull and is newer than the snapshot, the snapshot is dropped and the gap counts as closed only when the copies after that full state run contiguously to the store's revision, and is pulled again otherwise. It is also pulled again when no newer full state arrived and the copies cannot rebuild the store's revision exactly. A reply that does not arrive within 10 s counts as a failure and a late one is ignored. A resync keeps this window's chat selection when that chat still exists, including a deliberate empty selection, because a click whose `selectSession` is unacknowledged must not jump back. Loaded history pages, open search navigation and retained outbox history follow the same full-state rules as bootstrap, and composer drafts, outgoing rows, scroll position and open dialogs live outside the store fields a full state writes. Settings shown optimistically before their save is acknowledged can briefly show the snapshot's value until that save's patch arrives. A change lost as the very last patch before the stream goes quiet is detected only by the next patch.

`UI-V2/src/ipc/cefBridge.ts` wraps request/reply transport. `UamQueryHandler` maps action names to handlers, which call app services. `StateSerializer` returns initial state; `cef_push` sends `stateUpdate` or `cliOutput`. The store registers the push callback at module load, before React effects, so the first native push is not lost. Keep action payloads and responses explicit and version-compatible across both ends.

Native text clipped to a byte limit (titles, errors, diagnostics, stderr tails) is cut on UTF-8 code-point boundaries with `uam::strings::Utf8Prefix`/`Utf8Suffix`. As a backstop, `getInitialState` and state pushes replace any remaining invalid UTF-8 with U+FFFD instead of failing; `getInitialState` logs that a replacement happened without the text. CEF accepts bridge messages only from the trusted bundled page and main frame. Keep bridge work asynchronous when a handler can block. For a new action, update the native dispatch/handler, frontend action caller and relevant transport tests together.

`RunAsyncCefQuery` defaults to `TID_FILE_USER_BLOCKING`. CEF currently serves that lane and `TID_FILE_USER_VISIBLE` from one shared foreground thread (observed 2026-10-26) as separate sequences, and runs queued user-blocking work first. Chat history pages stay user-blocking; read-only Git/SVN status (`getVcsCommitStatus`, `getChatWorktreeStatus`, reference-context capture) spawns subprocesses and uses `TID_FILE_USER_VISIBLE` (`kVcsStatusThread` in `vcs_handlers.cpp`). A status read that has already started still delays a page until it returns. On 2026-10-26 the live opening of a 136 MiB, 27,000-message synthetic chat waited about 300 ms behind two equal-priority Git status reads; `VcsStatusSubprocessReadsYieldToChatHistory` guards the priority split. Give new background or automatic subprocess and network work a lower priority than history reads.

Sidebar hover/focus warm-up (`prefetchSessionMessages`, #624) reuses the ordinary `getChatMessages` loader. A later non-forced load of the same chat joins the warm-up's in-flight promise while it is still the latest request, instead of superseding it and restarting the native read (each native read invalidates the previous one), as long as the chat's identity, saved digest and message count still match; the join moves the read marker to the warm-up so the open keeps showing loading or its failure. Warm-ups send `background: true`, which runs a cold page read on `TID_FILE_USER_VISIBLE`, so an explicit open's user-blocking read starts before queued warm-ups (one already started still finishes first). An open that joins its own chat's warm-up sends `promoteChatHistoryRead`, which posts the still-queued read to `TID_FILE_USER_BLOCKING` as well (`CefRunOnceTask` runs it once), so it does not wait behind queued status reads. `SessionItem.performance.test.tsx` measures, with a simulated 400 ms single-lane native read, a click after a 300 ms hover against a cold click, and an unhovered click while two warm-ups are pending. A warm-up read that has already started still runs to completion, so an explicit open of another chat can wait behind at most that one read; the lane ordering relies on CEF's observed shared-thread behaviour and must be rechecked after a CEF upgrade.

## State push cost

While runtime state changes, each `Application::PollTick` (every 16 ms while the selected chat is busy, otherwise 50, 250 or 1000 ms) rebuilds the compact fingerprint and `cef_push` diffs it against per-slice baselines. Changed chat summaries, selected or background, publish at most every 100 ms per chat; a new pending permission or user-input request, or a new CLI launch identity, bypasses that window. Poll ticks rebuild the fingerprint at most once per 100 ms window (`PushRuntimeStateUpdateIfChanged`) and defer other changes inside it to the window's end. A chat summary publishes at the first rebuild after its own 100 ms window, so with a rebuild just before that window ends it can land just under 200 ms after that chat's previous publish; the window never rebuilds more often to shorten this. A new pending permission or user-input request or CLI launch identity, and provider compatibility, model catalog, model discovery, folder availability or remote host health changes, rebuild on that tick; bridge handlers keep using the immediate `PushStateUpdateIfChanged`. A tick without other changes rebuilds only after a deferred summary's window elapses (`DeferredStatePushDue`), and the poll scheduler shortens its next delay to that moment; a deadline that passes inside a rebuild window moves to the window's end, so the scheduler sleeps rather than polls and the final state reaches the frontend within that same bound. A summary deferred by a bridge handler's push between ticks is flushed by the already-scheduled tick instead, up to 250 ms later while a runtime is active or 1000 ms when idle. PNG icon data URLs are reused until the asset's size or modification time changes, and slice baselines compare JSON structurally instead of re-dumping it. Live tool calls still inline up to 64 KB of content because subagent summaries, managed-launch correlation and history fallbacks read it directly from the push. `PerformanceStreamingStatePushTick` measures 63 chats with PNG folder icons, one selected streaming chat with 30 × 50 KB tools and two background streaming chats.

Poll ticks compare chat summaries by digest, not JSON. `state_serializer` writes each compact summary field by field through one body that either builds the JSON or feeds a 64-bit digest, so every field the summary writes also enters its digest; a single changed short fixed-length field always changes it, and any other change (long text, which enters only as its hash, or a change in field count) collides with a probability of about 2^-64. A poll tick digests every idle chat without allocating JSON and builds JSON only for chats whose digest moved since their last push; chats with a live ACP session are built as JSON and digested from it, because they change on most ticks. A changed digest whose JSON equals the pushed summary publishes nothing. Patched chats carry the PNG icon data URL and managed subagent count that `stateUpdate` carries, including after catalogue hydration. `PushStateUpdate` (used by tests) and `StatePatchForTests` seed the digest baseline from the state they push, so the next tick publishes no chats; in production the frontend loads full state through `getInitialState`, whose `StateSerializer::Serialize` path and Refresh are unchanged and are not covered by these measurements, and the first poll tick publishes every chat once to set the baseline, as before. `StatePushPublishesEverySummaryInputChange` checks that chat fields, retained, selected and discarded-prompt transcripts, goals, unseen and routing state, restored routing reservations, native session IDs, managed runs, folder directories, Computer Use runtime state, a CLI terminal, queued and direct prompts, Claude quota continuation, a model catalogue refresh, the global memory default, a PNG icon, live ACP sessions and chat addition and removal publish exactly the affected chats once. A pending UAM-control approval on a stopped chat is not covered by that test. `PerformanceLargeCatalogStateFingerprint` reports an unchanged tick across 1,000 and 5,000 chats with six providers, 20 folders and eight retained 200-message transcripts.

Loaded transcript digests are reused by revision stamp. `ChatSession::messages` is a `RevisionedVector` (`src/common/models/revisioned_vector.h`): every way to reach its elements for writing (non-const element access, iterators, `data`, the mutating members, conversion to a mutable vector) first takes a fresh process-wide stamp, copies keep the stamp and a moved-from value is empty with stamp zero, so equal non-zero stamps mean equal content. Reading through a non-const chat restamps too, which costs one rehash and is counted: a `[performance] State pushes recomputed N stamped value(s) whose content had not changed` line, at most once a minute and with separate totals for loaded transcripts and live tool call lists, shows stamps being defeated by such reads. Only state pushes trust a stamp (`StateSerializer::StampedCacheMode::Trust`); message pages, handler replies and every other caller compute from the transcript and store nothing. The one write a stamp cannot see is through a reference, pointer or iterator kept from before the digest was read, so pushes are reconciled: a push that starts three seconds or more after the last verifying push runs in `Verify` mode, recomputes every digest it would have trusted, repairs a difference and writes one `[desync]` line naming up to five chats. After a trusting push the poll loop owes that verifying push even when no stage reports a change (`StateReconciliationDue`), and `CapPollDelayForDeferredStatePush` wakes it when the interval ends; the push can then wait out one 100 ms rebuild window, so a write that bypassed its stamp is published about 3.1 s after the push that missed it. New code must not keep a `Message&`, pointer or iterator across a state push and write through it afterwards; take it again from the chat. A consumer that wants to know whether a transcript changed compares `messages.revision()` values: equal and non-zero means unchanged, different means it may have changed.

Two more values are reused by the same rule, trusted only inside a push and recomputed and compared by the verifying push. A live ACP session's `tool_calls` is a `RevisionedVector`, and its serialized tool calls are reused while that stamp is unchanged, so a streamed token does not rebuild every tool call's content; the summary that is published still carries them all, and its size still follows the turn. Model catalogues are keyed by `ProviderModelCatalogService::Generation()` together with the provider profiles, folders, execution hosts and checked CLI versions read outside the service: while that key is unchanged a push omits the `providerModelCatalogs` slice and reuses each scope's compact fingerprint. The service's mutex is a `GenerationMutex` whose lock types enforce the count: a const member function can only take `Read`, any other code must take `Write`, which advances the generation, and `Poll` uses the one variant that may declare it changed nothing. A new input to a catalogue snapshot that lives outside the service must be added to `CatalogInputs` in `state_serializer.cpp`; workspace paths resolved on disk are deliberately left to the verifying push. Chat summaries themselves have no revision: a push still digests every visible chat, because a summary reads well over a hundred chat fields plus session, terminal, run, routing, memory and settings state that are written throughout the code with no single place to count a change.

Two transcript containment trials were measured in headless Chromium (200-message fixture, three runs each) and not adopted. `content-visibility: auto` on settled rows halved streaming layout time (24.8 to 14.2 ms per 30 updates) but moved settled text by 1 px (about 8,000 changed pixels per dark or light capture). `contain: layout` on the transcript changed no pixels but did not reduce side-panel layout time (208.9 to 215.7 ms per three open/close cycles), because the transcript's own width still changes every frame.

No stable latency budget is defined for the full bridge. `UI-V2/src/test/interactionBudgets.ts` sets a 250 ms budget for its explicitly covered frontend interactions; do not generalize it to all IPC calls.

## Terminal output polling

`PollCliTerminal` runs on the UI thread every 16 ms for a visible attached terminal, so per-poll work must stay independent of how much provider history the machine holds. Resolving the Gemini history directory can walk every project under `~/.gemini/tmp`, so it runs only when the 1.25 s native history refresh is due. A macOS PTY read returns at most 1 KB and the next read returns would-block until the writing process is scheduled, which limited output to one read per poll. An attached macOS terminal therefore waits for more output for about 5 ms at most per poll after its first read, through `WaitForCliTerminalOutput`, within the 32 KB per-poll byte budget and a limit of 32 reads. Background terminals and platforms without that override do not wait. Known gaps against [keeping blocking I/O off the UI thread](../../architecture/code-structure.md): this wait is a bounded blocking `poll` on the UI thread, about 28% of a poll while a writer keeps output arriving, and a refresh still resolves the directory there, once for the terminal and again for each running terminal on that provider each time load owners are captured. A PTY reader thread and a background resolve would remove both. `TerminalPollSkipsGeminiProjectScanBetweenHistoryRefreshes` checks that polls between refreshes do not scan, `AttachedTerminalPollDrainsMoreThanOnePtyReadPerTick` checks bytes read from the PTY and `AttachedTerminalPollDrainWaitStaysBounded` checks the wait limit.

## File review presentation

`RepositoryDiffDialog` keeps the fetched patch unchanged for unified view and copying. `UnifiedDiff` omits Git/SVN patch framing before the first split text hunk while preserving rename and permission metadata; metadata-only changes retain their headers. Source gutters use hunk ranges, and new/deleted files leave the opposite side empty. The preamble regressions live in `UnifiedDiff.test.tsx`.
