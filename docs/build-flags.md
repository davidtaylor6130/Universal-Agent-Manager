# Build flags

Build flags let an organisation deliberately exclude providers and capabilities that affect its policy: each provider, SSH execution, phone access and computer use. Exclusion means the resulting application and its shipped content contain no mention, entry point or usable implementation of the excluded capability: remove its settings, selectors, help text, assets and capability-specific packaged components rather than displaying a disabled option. Saved data must not reactivate it. Enabling it again requires knowingly building a version with the flag enabled. This is the product requirement; hiding UI alone does not satisfy it.

| Capability | CMake flag | Interface bundle | Native application and runner |
|---|---|---|---|
| Gemini | `UAM_ENABLE_RUNTIME_GEMINI_CLI` | Implemented | Partial |
| Codex | `UAM_ENABLE_RUNTIME_CODEX_CLI` | Implemented | Partial |
| Claude Code | `UAM_ENABLE_RUNTIME_CLAUDE_CLI` | Implemented | Partial |
| OpenCode | `UAM_ENABLE_RUNTIME_OPENCODE_CLI` | Implemented | Partial |
| Copilot | `UAM_ENABLE_RUNTIME_COPILOT_CLI` | Implemented | Partial |
| Antigravity | `UAM_ENABLE_RUNTIME_ANTIGRAVITY_CLI` | Implemented | Partial |
| SSH | `UAM_ENABLE_SSH` | Partial | Partial |
| Phone access | `UAM_ENABLE_MOBILE_COMPANION` | Implemented | Partial |
| Computer use | `UAM_ENABLE_COMPUTER_USE` | Partial | Partial |

Any CMake spelling (`OFF`, `0`, `FALSE`) means the same exclusion everywhere: CMake normalises every flag once and passes the same 0/1 value to native code, the remote runner, tests and the interface build. At least one provider must remain enabled; the first enabled provider in the order above is the default. `UAM_RUNNER_ONLY` builds only the remote runner with the same provider exclusions, and `UAM_PACKAGE_REMOTE_RUNNERS=OFF` packages only the current platform's helper without leaving earlier cross-platform helpers behind.

Settings and records a fuller build saved for an excluded provider stay on disk as inert data: provider availability, MCP switches, chat defaults, memory worker bindings, shell actions and usage records keep their entries when a restricted build loads and saves them, no runtime lookup ever matches them (a shell action for an excluded provider is neither installed nor run, and a worker binding that names one falls back to the chat's own provider), and a build that includes the provider again finds them unchanged. Single choices that must name a usable provider (the active provider, the default new-chat provider, each host's default and the permission reviewer) use an included provider instead while the build runs, and saving keeps the original choice as long as that fallback is still selected. Full builds still reject unknown provider ids.

Chats and sub-agent runs a fuller build saved for an excluded provider do not exist in a restricted build. They never enter its chat list or run ledger, so no chat list, count, search result, export, sub-agent list, phone view, notification, bulk action, folder deletion or cleanup shows, changes or deletes them, and their files stay on disk unchanged for a build that includes the provider again. Import and deletion still treat the native sessions and workspaces those chats own as owned. Deleting a folder in a restricted build keeps its hidden chats, which a fuller build then shows outside that folder. Branch, sub-agent, temporary and goal chats under a hidden chat, and runs under a hidden run, are hidden with it whatever their own provider, and a build without OpenCode also hides older OpenCode chats saved without a provider name. The interface shows no label, placeholder or "unavailable" text for any of them. Inside a chat that remains, a turn an excluded provider answered before a handoff shows no provider. An excluded provider's shell actions, memory worker bindings, cached model lists and usage prices are likewise kept but never shown or used, and saving the interface's shell-action and price lists keeps them unchanged. Memory library entries learned from a hidden chat remain in the library.

**Implementation: Partial.** The interface bundle drops an excluded provider's metadata, name, logo, settings page, model labels, usage colours and provider-specific branches, and an excluded feature's settings pages, controls, labels, manifest and service worker; an automated scan of every single-flag and single-provider bundle finds no remaining name outside reviewed exceptions. SSH and computer-use builds still carry their internal state-field names, with no label, control or request. Native builds compile only included providers' sources, register only included features' bridge actions, list only included providers' history, import and allowance sources, and never read an excluded provider's configuration folders. Shared runtime, settings, state and diagnostics code still contains names of excluded providers and features, so native artifacts do not yet meet the zero-mention requirement: the macOS Claude-only build with SSH, computer use and phone access off links and packages without the excluded helpers, policy files or companion resources, and restricted macOS release builds now drop unreferenced code and local symbol names, but its executable still holds 626 such names (1,879 before stripping), mostly diagnostics and error text, configuration keys and C++ type names in shared code, and the bundled Markdown Store copies skill text that names providers. A runner-only helper without OpenCode and Antigravity compiles none of their sources and still holds 134 names from shared runner code. A Claude-free build with every other flag on links on macOS and Windows and keeps 54 Claude strings in the macOS app and 23 in its runner, and 42 and 22 in the Windows app and runner; each is recorded exactly for review. Other native profiles are not yet recorded, and the restricted apps have not been launched.
