# Phone access

Phone access connects a browser or the [native iPhone client](phone-native.md) to the main UAM device through its shared authenticated companion interface. Users explicitly turn publication on or off and connect through the configured route; the main device remains responsible for chats, providers and execution. Both clients use the permitted companion interface rather than acquiring the desktop’s unrestricted native bridge. Disabling publication stops access, and a desktop build without phone support contains no serving entry points. Phone access does not require a UAM account or cloud service.

A phone request that would let an agent do more waits for the user on the main device instead of applying: raising a chat's permission level above Default, leaving Plan, changing the chat's UAM agent, turning on UAM Control, changing provider chat defaults, creating a chat that starts above Default or outside Default/Plan, turning on or changing an MCP server, or changing a provider option that carries its permission, approval or sandbox mode. The phone is told to confirm on the desktop; the desktop asks Allow or Deny naming the chat and change, and a reloaded or new desktop window still shows requests that are waiting. Allow applies it as the user's own change; Deny or five minutes without an answer drops it, and at most eight wait at once. Lowering a level, entering Plan and other phone actions apply directly. The companion cannot answer its own request. **Implementation note:** the native CLI terminal opened from the phone is the provider's own interface, so a mode switched inside it is not intercepted.

The connection token is kept in the operating system's credential store (macOS Keychain, Windows Credential Manager), one entry per data root, never in a file under the data root. An existing plaintext token file is moved into the store on the next start, keeping the same token so paired phones and browsers stay connected, and the file is then deleted; if the store refuses it, the file stays in use and UAM logs that. The companion server also refuses phone and automation requests from programs UAM itself started, such as provider agents and terminals, other than its own HTTPS proxy. **Implementation note:** a macOS Keychain item trusts UAM's own signed binary, so another program reading it asks the user; an ad hoc signed build may ask once after each update. Windows Credential Manager entries are readable by any program running as the same user. The process-tree refusal is implemented on macOS and Windows; a program that detaches from UAM's process tree (for example with `nohup`, `setsid` or `launchctl`), one started outside UAM, or a request that reaches the companion through its own HTTPS proxy address is not recognized, so the credential store remains the main protection. The development launcher's `UAM_COMPANION_TOKEN_FILE` override remains a file and cannot be rotated from Settings.

Revealing a pairing code issues a new token, and Regenerate token issues one without revealing it; Copy token copies the current token and changes nothing. After a new token, the running server refuses the old token from its next request. The credential is shared, so every other paired phone or browser must then pair again. The native iPhone client reports the rejected token and offers Pair again; the browser companion tells the user to log out and connect with the current token.
