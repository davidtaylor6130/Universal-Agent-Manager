# Automation API

The automation API lets another program, such as an n8n workflow, start a UAM chat in an allowed workspace. It is served by the [phone access](phone-access.md) companion server, so it is only reachable while Phone access is on and UAM opens no additional network listener. It is a narrower interface than phone access: its tokens are separate from the companion token and cannot use the companion API, and the companion token cannot use this one. Like phone access, it refuses requests from programs UAM itself started, such as provider agents and terminals. [Schedules](#schedules) are not network requests: they run inside UAM whether or not Phone access is on.

## Tokens

Tokens are created and revoked in [Automation settings](settings/automation.md). Each has a trust level, an allowed workspace list and the most Git access a request may ask for. The token is shown once, when it is created; UAM stores only its SHA-256 hash, and the desktop settings actions that manage tokens are not available to the phone. Every request re-reads the token file, so revocation applies to the next request. A revoked token cannot create chats or read status; chats it already created are kept, and a waiting one can still be started or deleted by the user.

Each token expires after the lifetime chosen when it was created: 30 days, 90 days (the default) or one year. An expired token is refused with 401 and a message saying it has expired. Regenerate, on the desktop only, replaces a token's secret while keeping its name, trust, workspaces, Git ceiling and chats, and restarts its lifetime. The old secret is refused from the next request, including status polls of chats it created, and the new one is shown once. Neither the companion nor the automation API can regenerate, create or revoke tokens. Tokens created before expiry existed receive the 90-day default, counted from the first time UAM reads them after the upgrade.

## Requests

`POST /automation/chats` takes `Authorization: Bearer <token>` and a JSON body of at most 256 KiB, and is refused if it carries a browser `Origin`.

| Field | Required | Meaning |
|---|---|---|
| `prompt` | Yes | First prompt, up to 128 KiB. |
| `workspaceId` | Yes | A UAM workspace folder ID on the token's allowed list, shown on the token's row in Settings. |
| `providerId` | Yes | A provider available on the workspace's host. Antigravity is refused; see below. |
| `maxIterations` | Yes | Integer from 1 to 200; see below. |
| `gitPermission` | Yes | `commit` or `pr`, no more than the token allows. |
| `modelId`, `title` | No | Otherwise the provider default and a generated title. |

An unknown, malformed or expired token returns 401, a workspace or Git permission outside the token returns 403, an invalid field including a missing `maxIterations` returns 400, an oversized body 413, a workspace that cannot be isolated or a provider that is unavailable 409, and 16 open chats for one token 429. None of these creates a chat, a worktree or a provider process. A trusted chat that is created but cannot start returns an error naming the chat, which stays waiting for the user. A successful response is `{"chatId": "...", "status": "running"}` for a trusted token, or `"awaitingApproval"` for an untrusted one.

`GET /automation/chats/<chatId>` returns `status` (`awaitingApproval`, `running`, `completed`, `blocked`, `paused` or `stopped`), `iterationsUsed`, `maxIterations` and `gitPermission`. `iterationsUsed` is the count the cap checks: reviewed iterations plus automatic resumes not yet reviewed. `blocked` includes a chat whose worktree preparation failed after the send was accepted. A chat created by a different token reads as not found. Status is polling only: UAM makes no outbound callbacks or webhooks. The API does not return transcript content.

## Chat behaviour

Every automation chat is requested with its own Git worktree, and the request is refused if UAM cannot isolate that workspace ([the same rule as started chats](providers/uam-tools.md)). An SSH workspace turns out to have no Git repository only at launch; the provider start is then refused rather than run in the shared directory. A trusted token's chat starts immediately. An untrusted token's chat appears in [Active Chats](sidebar/active/active.md) as **Waiting for approval**, without Done or Snooze actions. Its prompt is shown as a message marked Not sent yet, with a question card beneath naming the token, iteration cap and Git access and offering **Start chat** on the desktop; there is no composer until it starts. Until the user starts it, sending, the structured provider process and CLI View are all refused. Start chat turns it into an ordinary chat in place: the prompt shows Sending and the sidebar shows Working through worktree and provider start, and the prompt becomes a normal message once the provider has it. A refused start returns the chat to waiting rather than losing the prompt; a workspace that fails after the start was accepted keeps the prompt as held input to resume.

`maxIterations` caps the chat's [goal](chat/goals.md) loop, and the lower of it and the Settings cap applies, including to stalled-loop resume and to any later goal in the chat, such as one the model creates with `goal_create`. Automation chats always use the Default permission mode, ignoring a more permissive Settings default, so commands and edits still ask the user. **Implementation note:** `gitPermission` is enforced at the request against the token's ceiling and stated to the agent in the goal objective, so the visible message stays the prompt that was asked and every continuation repeats the policy; UAM does not block a Git command itself, so Default-mode approval is what stops an unapproved push. A provider that answers its own permission prompts (Antigravity) is not mediated by that approval, so requests for it are refused until a Git-aware gate exists.

A chat an automation chat starts with [`chat_create`](providers/uam-tools.md) or a branch of one stays under the same token: it keeps the iteration cap, Git permission, worktree requirement and secret refusal, and never the approval hold. A started chat's first prompt states the Git policy. These chats count against the token's 16 open chats, so a new `chat_create` is refused while the token is full, revoked, expired or unreadable, and for a provider that answers its own permission prompts; a retry with identical arguments still returns the chat it already started. A chat an automation chat started, and any branch of it, counts as open for as long as it exists. Any other chat under the token counts while it waits for approval, has an active goal, or has a turn waiting to be sent or running; a launch that failed after acceptance counts only while a turn is running or waiting for the user, because it otherwise waits for the user rather than the token. Status remains limited to the chats the token created itself; a chat started or branched from one reads as not found.

## Schedules

A schedule is a stored `POST /automation/chats` request that UAM runs itself on a local timer. Schedules are created, edited, paused and deleted only in [Automation settings](settings/automation.md) on the desktop; neither the companion nor the automation API can reach them. A trigger is either an interval from 15 minutes to 7 days, counted from when the schedule was created, last edited or resumed, or a local time on chosen weekdays. Each run starts a new chat; sending a message to an existing chat is a later slice. Runs need no listener, so they happen whether or not Phone access is on, but only while UAM is open (David, 2026-11-23).

A schedule is its own credential: the trust, workspace and Git access chosen for it in Settings, kept only inside UAM and never expiring, while external tokens keep their expiry (David, 2026-11-23). No token can read the chats a schedule starts. Every run otherwise goes through the same checks as a request: the required fields, the workspace, the iteration cap, worktree isolation, provider availability, the refusal of Antigravity and the 16-open-chats limit, which counts each schedule separately. A schedule that starts chats straight away starts its chat at once; otherwise the chat waits in Active Chats for **Start chat**, as an untrusted token's does, and the waiting card names the schedule.

A run is saved as run before its chat is created, so a crash or restart never runs the same time twice. A run noticed more than 5 minutes after its time, because UAM was closed or the computer slept, is missed: each schedule either skips missed runs or runs once for all of them. A paused schedule does not run, and resuming it does not run the times that passed. Editing its trigger starts its timing again from the edit; an edit that keeps the trigger, such as a new prompt or name, keeps its timing. If the computer's clock is set back, an interval schedule whose next run is more than one period away starts its timing again from the new time, and a weekday schedule takes the next time its trigger gives from the new clock. Weekday times follow the computer's time zone and daylight-saving rules: a time runs at most once a day, so the repeated hour when clocks go back does not run it twice, and a time skipped when clocks go forward runs once just after the change. Saving a schedule also makes the run's worktree-isolation and provider checks, so one that could not start is refused when it is saved; settings changed later are caught at the run. If UAM stops during a run, its next start checks the chats: a chat of that run still waiting is marked for the user and waits in Active Chats for **Start chat**, a running one counts as started, and otherwise the row reports the interrupted run with one notification titled **Scheduled run interrupted**. A run that cannot start records its reason on the schedule's row and raises one notification, titled **Scheduled run did not start** when no chat was created and **Scheduled chat did not start** when its chat was created but could not start; a schedule that keeps failing for the same reason is not announced again until the reason changes. The diagnostic log records the schedule, the outcome and the chat, never the prompt.

## n8n example

Use an HTTP Request node to `POST https://<phone-address>/automation/chats` with a Header Auth credential of `Authorization: Bearer <token>` and this body, then a Wait node and a second HTTP Request node to `GET .../automation/chats/{{$json.chatId}}`, looping back to the Wait node until `status` is `completed`, `blocked`, `paused` or `stopped`.

```json
{"prompt": "Fix the failing parser test.", "workspaceId": "<folder-id>", "providerId": "codex-cli", "maxIterations": 5, "gitPermission": "commit"}
```
