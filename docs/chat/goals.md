# Goals

A goal is explicitly requested continuing work with recorded progress and, when specified, a budget. UAM-managed goals use the global Goal token budget in Settings → Goal loops as their default; zero means unlimited. A goal-specific budget written in an explicit `/goal` command remains an override, and the saved goal payload retains its budget field. UAM should retain its state across interruptions and distinguish active work, waiting for the user, blocked work and achieved completion. Automatic continuation must remain bounded by the user’s instructions, stop conditions, permissions and budget; ordinary chat input must not silently become a goal or automatically resume unrelated held input.

The configured [iteration cap](../settings/goal-loops.md) applies before any further UAM-managed worker continuation, including continuation after a transient blocker. Reaching the cap blocks the goal instead of starting another iteration; terminal blockers retain their own stop reason. Review-driven continuation and stalled-loop auto-resume both check this bound. A goal created through the [automation API](../automation-api.md) carries its own ceiling, and the lower of that and the Settings cap applies.

A chat with a goal shows a goal tab beside the composer workspace tab: the goal icon and truncated objective (full text on hover), then Edit goal (UAM-managed goals that are not complete) and Stop goal (active goals; pauses, so Resume stays available). Selecting the tab body opens the goal window, a modal dialog with the status, full objective, step and token-budget rows, the current, completed and remaining steps, and a footer with Pause or Resume and the Goal actions menu (Mark complete, Restart, Edit, Delete). Edit goal, from the tab or the actions menu, opens the same window in edit mode: the status, step and token rows and the step lists stay visible while the objective becomes an in-place text box that takes focus, and the footer becomes Cancel and Save (Ctrl/Cmd+Enter also saves). An empty objective or a failed save shows its error in the window and keeps the draft. Escape cancels the edit first (it does nothing while a save is in flight), then closes the window. Escape or the close button dismisses it and returns focus to the tab.

Provider integrations should let an agent inspect its chat’s current goal and request explicit goal creation through UAM’s permission boundary, while UAM supplies the objective, progress context and supported lifecycle controls. Native goals use a provider adapter where available; they must not start a second competing continuation loop or bypass user-owned pause, stop, budget or completion review. Shared goal inspection and approval-gated creation are existing routes, not proof of complete native lifecycle interoperability.

Antigravity goals use UAM-managed continuation in the chat's saved native CLI conversation, with isolated Plan reviewers whose native IDs cannot replace the worker's identity, including their single bounded JSON repair. UAM owns progress, completion review, iteration limits and observed step-token accounting, including reviewer consumption. Pause/clear/replacement cancels the matching owned turn after the control's durable receipt and retains unrelated held input. Direct controls save their intent before cancellation and restore prior goal intent if that save fails; CEF controls retain their asynchronous receipt boundary. Interrupted or missing usage holds budgeted continuation across restart; ordinary Resume preserves counters, while explicit Restart requires observed process exit for an interrupted local metered turn before beginning the existing fresh UAM budget/progress cycle in the same native conversation. Reported-step enforcement can stop after a step exceeds the allowance; it is not a provider hard token cap. Native `/goal` commands and unsupported provider-owned controls remain refused, without silently changing ownership or claiming native cancellation. The [runtime reference](../reference/antigravity-runtime-goals.md) and [native bridge dependency](../documentation-review.md#antigravity-native-goals) retain those boundaries.

Each UAM-managed review runs in a private session that lists no UAM tools: the reviewer only reads the workspace and answers in JSON, while the worker that continues the goal keeps UAM tools for subagents and questions. For a local Git workspace the review prompt includes a changed-file list (status, path and line counts, capped at 2 KiB) and names the Git reads the reviewer's read-only ceiling accepts, one command per call: `git status --short` and `git diff --no-ext-diff --no-textconv`. Plain `git diff` stays refused because a repository's external diff or text conversion settings can run commands. SSH reviewers get no list and run those commands themselves. With the [cheaper reviewer setting](../settings/goal-loops.md) on, outside small-model mode, reviews use the chat's reviewer model, then the provider's default reviewer model, then the provider's low-cost side-work model, and otherwise the chat model; a small model's malformed reply still gets its single JSON repair turn.

After a goal completes or blocks, an ordinary prompt in that chat carries the read-only goal state only when it differs from what the running provider process already received, so the state is sent once per change instead of on every turn; a restarted provider process receives it again once.

Continuation and review context may compact repeated objectives, task lists and empty state fields, while retaining distinct tasks, verification requirements, budgets and user stop conditions. Attached skill and computer-use context remains associated with the original authored inputs when requests are batched.

Generated small-model goals and their authored input share the complete initial admission save on local and SSH hosts before provider input. Goal preparation alone grants no delivery authority. Ready v3 small-model SSH delivery and direct steering additionally retain the exact goal owner, command and iteration through the full marker receipt and final check against saved process authority; changed or missing ownership refuses that continuation. The owner’s authoritative goal metadata can supply this scope while its transcript remains unloaded. Automatic small-model quota claim and settlement retain that full active-goal scope even when the provider runtime is absent; an objective edit does not inherit an earlier claim’s authority. Cold launch additionally retains that exact goal scope through its owned process/control save; legacy transport and native goal lifecycle controls retain their own publication boundaries and pending verification.

The first goal send includes the reference snapshots selected with the original authored submission, captured before goal creation waits. Automatic continuations must not borrow later composer selections. This follows [David's action-send contract decision](../documentation-review.md#referenced-context-action-sends) and the [composer context agreement](composer/attachments.md); implementation verification and acceptance remain separate.
Completed shared goal reviews and their single JSON repair count reported token usage once before UAM admits another repair or worker turn. Reaching the token budget holds the goal before applying a review decision, including a completion decision; unknown usage stays unknown and must not reuse an earlier turn’s count or infer tokens from response length. Cumulative usage requires a matching native session and a known starting total from adapter-validated receipts, or a newly created review context; replacement sessions cannot charge an earlier receipt, and startup retry begins a new receipt without assuming an empty native history. Replayed older cumulative snapshots cannot reduce already observed review usage, and display telemetry cannot establish a repair baseline. Cancellation and changed user controls retain their existing continuation gates. Native provider-managed goal budgets remain under their own adapter contract.

**Implementation note:** Reviewer accounting and cumulative-receipt corrections have focused native verification across all six adapters and independent source/test review; broader runtime/platform verification and user acceptance remain pending.

## Decision source

Each automatic goal decision records who made it, and the goal window shows it as Last decision. `model:<id>` means a reply from that reviewer model parsed as a goal review; nothing else may name a model. `filter` is a deterministic UAM rule: the iteration cap, the repeated next-prompt stop, the token budget or a hold on unknown usage. `fallback` means no model decision was available: a review still invalid after its repair, a review that could not start or be consumed, an exhausted stalled loop, a provider or connection failure, or a status reported by a native goal, which UAM did not review. When a rule blocks a goal after a model said continue, the rule is reported; pausing for queued user input keeps the model decision. Mark complete, marking blocked and Restart clear the source because the user replaced the verdict; a user pause and any hold that records no verdict of its own keep it, while a usage hold or native status records its own source. A goal saved before sources were recorded shows Unknown when it holds an earlier verdict or diagnostic, and shows no source otherwise; UAM does not infer one. The chat's most recent attention flag records its source the same way and the goal window shows it as Last attention flag, including after the flag is acknowledged; UAM raises every flag by a deterministic rule, whether from a turn end, a failure, a permission request or a tool update, so all report `filter`. Other goal updates that mark a chat unseen record no source.

**Implementation gap:** Only source tagging is implemented. The decision-model backends (hosted or local), the Choice, Score and Probability interface, the backend choice in Settings and the latency and cost measurements remain open under [#363](https://github.com/davidtaylor6130/Universal-Agent-Manager/issues/363). Permission AI Review keeps its own status and is not covered by this source field.

## Inspection

Goal inspection reports the selected goal’s saved execution owner (`uam` or `provider`) separately from its creator provenance and UAM’s lifecycle authority. Legacy records without a recognized execution owner retain the UAM default. Inspection preserves saved native commands and provenance without starting or transferring execution.
