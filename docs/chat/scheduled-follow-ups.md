# Scheduled follow-ups

An agent can ask UAM to wake its own chat later, for example to check CI in 30 minutes, with the UAM `schedule` tool ([UAM tool connection](../providers/uam-tools.md)). It gives a delay from 1 minute to 24 hours and a short note of up to 500 bytes. When the time comes UAM sends the chat one message carrying the note, through the same path as a [pull request watch](pull-request-watch.md) message, so a busy chat gets it after its current turn. Only the chat that asked is woken, so the tool needs no approval and UAM accepts it in every permission mode (a provider in Plan mode may ask before calling it); the message runs under the chat's own agent and permission modes. Subagents, temporary side chats and goal reviewers cannot schedule follow-ups, because their turn ends with their task; the chat that delegated to them can.

## Limits and cancellation

A chat can have 3 follow-ups pending, and UAM 200 in all. Pressing Stop on the chat's running turn, marking the chat done (Done or Clear all in Active Chats) and deleting the chat drop its pending follow-ups. Once the agent has ended its turn as the tool tells it to, there is no turn to stop, so marking the chat done or deleting it is how the user cancels; stopping the provider session alone does not, as for pull request watches. A chat that was already marked done when the follow-up was set keeps it until it is marked done again.

## Delivery and restart

Follow-ups are local timers in the desktop app, kept in `chat_wakes.json` in the data folder ([source of truth](../architecture/source-of-truth.md)), so they run whether or not Phone access is on and continue after a restart. One that fell due while UAM was closed is sent once after the next start, and its message says how long ago it was really set. If the computer's clock is set back more than a day, a pending follow-up keeps its delay counted from the new time. Delivery is at most once: a follow-up is saved as being delivered just before it is sent, and one interrupted by the app stopping is not sent again. A message that the chat refuses is tried again every minute; after 30 refusals the follow-up is dropped and one entry titled **Follow-up dropped** in the [notifications panel](../ui/notifications.md) names the chat. The diagnostic log records the chat and delay, never the note.
