# Workspace actions

Workspace actions operate on the current chat’s workspace, including opening a configured editor or file manager and running configured shell actions. They must use the intended workspace and environment, and unavailable remote actions must be clear. Their available choices are configured under [Editors](../../settings/editors.md) and [Shell Actions](../../settings/shell-actions.md); this menu does not define separate editor or command settings.

The composer identifies the source workspace first, then its VCS branch or supported equivalent, consistently with the sidebar. A managed worktree uses the source workspace’s name on the same execution host; its actual working directory remains inspectable and is still the target of workspace actions. Branch selection must reflect the current workspace’s supported operations rather than a global bridge capability or saved branch label alone. Before the first message, a new chat whose [starting branch](../new-chat.md#starting-branch) differs from the checked-out branch shows that starting branch, with the checked-out branch on inspection, because its worktree will start from it, and keeps showing it when the checked-out branch cannot be read; a chat without a chosen starting branch shows the checked-out branch as before.

A pending switch can outlast the open picker. Its refusal or inspection error remains available beside the branch control after the picker closes, including when runtime activity disables the trigger; the error is announced and can be read by keyboard focus or hover without implying a confirmed revision change.

Keyboard selection of an SVN target moves focus to its explicit confirmation, without switching. Cancel or Escape returns to folder search, changing the search clears a pending confirmation, and moving keyboard focus out of the picker closes it. Errors wrap in full rather than relying on a hover title. A successful confirmation returns to the branch control when focus remains in the picker; focus moved elsewhere during the request is preserved. Folder options use the search field’s arrow navigation rather than adding a Tab stop for every child.

If a pending switch refuses after the picker closes, focus deliberately moved to another control stays there while the inspection warning remains available. A failed background dispatch releases the chat’s busy marker and existing request lease so a later attempt is possible, without sending a second failure response.

The Git picker supports validated editable local UAM-owned Git worktrees; a managed Git snapshot of an SVN source does not switch that source and directs SVN selection to the actual working copy; native ownership, runtime and save checks remain authoritative. Its branch list is newest commit first and lists branches checked out by other chats' worktrees last because they cannot be selected; SVN folder discovery keeps its discovered order because UAM records no per-chat SVN target. Creating a Git branch in a chat with no user message is never blocked in the picker: the name is validated, saved on the chat as pending and shown in the composer, and Git creates it from the same HEAD when the chat starts: the first message, a goal, or the CLI View terminal starting. A chat that is never used therefore leaves no branch behind. Creating a branch keeps uncommitted files as they are, so attachments or edits never block it; switching to an existing branch still needs a clean worktree. Choosing the checked-out branch withdraws the pending name without running Git, and an empty chat can always switch to an existing branch. If creation fails when the chat starts, the request is not sent and the error names the branch. A plain local SVN working copy instead offers repository-folder selection: enter an explicit repository-relative parent (for example `^/product/lines` or `^/`), discover its immediate child directories and confirm the chosen target before switching. The composer shows the current repository-relative path when verified, alongside its revision. A working copy at the repository root shows `^/`. This mapping is explicit input for selecting an existing folder and is not an inferred `trunk`/`branches` convention; only branch creation, below, reads the repository's layout.

**Create SVN branch…** in the same picker creates a branch where the repository's [layout](../../settings/version-control/svn.md) puts branches, for example `^/branches/<name>` or `^/shop/branches/<name>` beside a working copy in `^/shop/trunk`; the row appears when the layout gives a location for this working copy, and a branches folder that does not exist is refused when creating. Every time, it asks where the branch starts: the working copy (its repository path at its revision, the default) or **Trunk HEAD** (the layout's main line at the repository's newest revision, read just before copying). UAM writes an editable one-line commit message naming the branch and its source; the person can change it before **Create and switch**, and the next creation starts from the default again. The name uses letters, digits, dots, dashes and underscores; a name that differs from an existing branch only in letter case is refused, since the two collide in checkouts on macOS and Windows. A working copy of the repository root can only copy the main line, and the working-copy option says why. Creation is one server-side `svn copy` commit pinned to the source revision, then a switch of the working copy to the new branch through the guarded switch below, so the same eligibility, clean-state, ownership and runtime-stop rules, and the external-definition check on both the working copy and the source, refuse before anything is committed. UAM never creates a missing branches folder. It refuses a name that already exists, and a name it could not check because the branches folder could not be listed, and refuses copying the working copy when parts of it are at other revisions or when it deleted files in a commit after its revision, because the copy would bring those files back (copying trunk still works; updating first lets the working copy be copied). It confirms the commit from the repository log, then switches straight to the commit it made, so the size of the branches folder and later commits elsewhere in the repository do not affect it. If another branch of the same name appears at the same moment, svn puts the copy inside it; UAM says so and does not switch. Unlike Git, nothing waits for the first message: the commit is made when confirmed. When the copy fails, UAM still checks the log in case the server finished the commit, and says the branch was not created only when it is confirmed absent; the message then suggests checking the commit message, which repository hooks often reject. A refusal or failure is one notification through the [notification system](../../ui/notifications.md) and keeps the form filled in; when the branch was committed but the switch did not finish, the notification names the created branch, its revision and why the working copy stayed where it was. Success is reported as a notice and the composer shows the new branch's path and revision. Merging SVN branches, SVN branch creation in the new-chat selector and greyed-out reasons for unsupported systems are not built yet.

SVN selection requires the complete working-copy root to match its local workspace folder and have no other chat using that directory or an overlapping path, including retained source directories and separate worktrees. Workspace-directory remapping waits for an ongoing switch so another chat cannot begin sharing the working copy mid-switch. Dirty, ignored/untracked, conflicted, external, switched-child or changed working copies refuse switching. Full-copy verification includes sparse or excluded descendants; an incomplete or unverifiable bounded inventory refuses without expanding the copy. Stale discovery, repository identity changes and unsupported paths fail without an implicit checkout.

The native route stops an eligible idle runtime, takes the existing exclusive workspace lease, pins the discovered revision, preserves SVN’s ancestry check and verifies the final URL, revision, full inventory and clean state. Failed or uncertain operations report that the working copy needs inspection; they never force changes or attempt an automatic rollback. Remote, read-only, managed-run/goal and side-chat contexts retain their existing mutation limits. The separate [New chat](../new-chat.md) page owns the branch-creation selector; selected-worktree reuse already exists. See [SVN](../../settings/version-control/svn.md).

An SSH chat's workspace menu has no local editor or file-manager actions; it offers its terminal, **Attach remote directory** and **Move this chat to** a workspace folder registered on the same computer. Attach remote directory browses that host through its helper and adds the chosen directory as a [folder reference](attachments.md); nothing is copied, and the reference keeps the host's absolute path. Move this chat is available only while the chat is idle with no queued, pending or held input. The helper first confirms the destination directory exists on that host; then the chat keeps its history, goals and host, and its next provider session starts fresh in the new folder with the earlier conversation handed over. A chat is never moved to another computer, and a chat in its own Git worktree, or preparing one, refuses the move because the provider would keep working in that worktree. Any refusal leaves the chat's folder, workspace, worktree and native session unchanged and shows its reason in the menu. **Implementation: Needs verification.** Native fixtures cover the same-host move, the cross-computer and worktree refusals and held-input refusal; helper fixtures cover the directory listing both actions use and the refusal of a helper reply naming a relative or different folder.
