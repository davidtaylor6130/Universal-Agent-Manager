# Composer attachments

Users can attach files, images, folders and skills as visible context chips, inspect their identity and remove them before sending. The message must retain its selected context through send, save, retry and editing; silently omitted resources are a failure. Provider consumption and SSH delivery follow the [provider attachment agreement](../../providers/attachments.md), and skills retain their [supporting resources](../../providers/skills.md).

Typing `@path` (or `@"path with spaces"`) offers an explicit file-reference action; typing alone never reads the file. The action reads through the selected chat's native workspace/host file service and retains a text snapshot with its resolved path, workspace, host and capture time. A removable chip opens that captured text without rereading the current file. Snapshots share the four-reference limit and retain at most 16 KiB each, with truncation shown before sending. The authored message includes the captured text and attribution as quoted context, retains it after refusal and clears only unchanged acknowledged snapshots for the same chat birth while preserving newer references. A displayed path or quoted snapshot supplies no filesystem, VCS or provider-delivery authority.

Reference branch and Reference worktree capture the current native chat's observed named Git branch or configured Git worktree association without selecting, switching or creating either. Native capture carries the source chat/birth, host, resolved workspace and capture time, with branch and configured source/base details; a detached HEAD cannot supply a named branch, and an unconfigured worktree is refused. Results from a changed chat incarnation, host connection, workspace or association are discarded. The same inspectable/removable chips and snapshot bounds apply, and ordinary Send retains the captured observation even if the repository later changes. A worktree snapshot describes the chat's configured association rather than granting repository ownership or proving continued physical registration. The worktree-reference action stays focusable but unavailable until the chat has a configured worktree, and announces that reason to keyboard and screen-reader users; the native service still validates every capture. Chips with the same label are numbered by occurrence, skipping any number already used by a literal label, and the chosen number also appears in the chip's meta text so it survives truncation; the inspection dialog uses the same displayed name.

User-authored goal first-send and all three Claude Plan prompt choices retain the reference snapshots selected at the original Send, before goal creation or mode/permission waits. Later composer selections are reserved for the next message; generated plan Approve/Deny actions remain independent of the composer draft. A changed target chat/birth, provider, host or effective workspace before delayed dispatch requires a fresh submission; a branch/base label refresh for the same target retains the original snapshot. A stale Claude Plan notice closes while its unsent draft and references remain available for a fresh Send. Replacing a chat birth releases the abandoned submission's busy controls and asks users to check earlier input before sending again; its late completion cannot release a newer send or clear the replacement draft and attachments. Refused or unconfirmed prompt delivery shows a warning with recovery guidance. This follows [David's recorded contract decision](../../documentation-review.md#referenced-context-action-sends).

Snapshot inspection labels the source identity and capture time and provides named, scrollable captured text; it never rereads the source. Partial snapshots remain readable in every theme. Closing inspection returns focus to the chip, and removal moves focus to an adjacent chip or an available reference action. Repeated captures remain separate observations with distinguishable display and removal names, including filenames that already contain numeric suffixes; the displayed names never change captured identity or delivery text. Repository observations retain readable captured text.

**Implementation note:** File, branch and worktree snapshot source/render/authored-send routes are source-implemented, including the approved goal/Claude Plan behavior. Native CEF integration, Windows and live-provider verification, scoped Claude review and user acceptance remain pending in the [V5 log](<../../../V5 Improvement Change log.md>).

Attachment staging is user-visible work and remains independent of low-priority background file maintenance. Ordinary file bytes bypass optional native image-format probing; recognized images retain the existing bounded decoding, orientation and preview policy, while original attachment bytes remain unchanged. These rules apply to desktop, browser and native-phone callers and preserve the same workspace/SSH ownership checks.

Native iPhone HEIC/HEIF imports show two removable attachments before sending: the byte-exact original as a file and an orientation-corrected JPEG for agents to inspect. The JPEG has bounded pixel dimensions and encoded size; its metadata does not replace the retained original. Both attachments count toward the phone composer’s eight-file/20 MB limit and are added together or not at all. Photo-library and file imports use the same preparation, and malformed or unsupported sequences produce a recoverable error rather than silently dropping the original. Other supported image bytes remain unchanged.

Phone draft text edits save independently of retained attachment bytes. A missing or damaged saved attachment must surface a recoverable error and preserve the draft record; it must never silently restore an empty draft or revive a previously acknowledged message.
