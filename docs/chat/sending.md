# Sending and recovery

An idle Send or Resend is direct input, even when startup or restart takes time; only input waiting behind active work belongs in the visible queue. Outgoing direct input appears immediately as one message at a stable transcript position; pending, held and definitely failed input stays there with a muted dotted treatment and a hover- and keyboard-accessible explanation; definitely failed input is labelled Not sent as one line of error-tone text, without an icon, beside recovery actions that fade in on hover or focus but always keep their space. Held direct input with no transcript row or Retry route, such as input retained across an interrupted remote restart, joins the held queue so **Resume queue** can release it; otherwise Send refuses the held queue with no control to advance it. **Cancel turn** on the desktop stops only the running turn: queued input, with its text and attachments, stays in the visible queue and becomes held, locally and on SSH hosts (including while a disconnected host's stop is confirmed; **Resume queue** waits until that stop is confirmed, so the cancelled turn cannot run first) and for goal turns, so nothing sends after the cancel until **Resume queue** releases it or Remove deletes entries. While it is held, Send refuses new input with “Resume the held queue or remove its prompts before sending.” A queued prompt already dispatched as the cancelled turn keeps its transcript message instead of a queue entry. A cancel from the phone companion still discards the queue, because the phone has no Resume control; see the [open decision](../documentation-review.md#phone-cancel-and-the-held-queue). Raw queued input never keeps a settled remote turn marked as in flight, so it drains once that turn ends, and a held queue pauses only new input: restart recovery of an already-sent remote turn still prepares its workspace and reattaches. Admission means UAM retained the request; delivery is confirmed only by an exact matched native fact that the submitted input was fully written to provider input or accepted by the provider. Transcript materialization, processing state and unrelated output do not supply that confirmation. Existing recovery actions appear only when native delivery authority permits them; uncertain delivery or partial provider output must not be automatically replayed. Preserve the authored text, attachments, skills and selected agent during recovery. Display correlation follows the bytes the existing send path actually submits, including quoted context; identical attempts without matching native identity remain independently unconfirmed. Stopping work must distinguish an interrupted delivered turn from input known never to have reached the provider.

A send that gets no answer, such as a phone request timing out while the desktop is busy, may still be admitted, so it stays visible as unconfirmed rather than failed. An ordinary composer Send or Steer, on the desktop or the phone browser, is one submission with its own identity; pressing Send again on the retained, unedited draft with the same references, skills, attachments and action retries that submission, and UAM admits a submission once per chat. A retry of an admitted submission adds no second input: its reply names the earlier attempt, and every earlier unconfirmed row of that submission gives way to the admitted message. A retry while the first attempt is still being admitted is refused with "This message is still being sent. Check the chat before sending it again."; a refused, failed or unsaved send releases its identity, so a retry is a fresh admission. Any change to what the send carries, a confirmed send, or the chat already showing the attempt (its row or receipt, or a later turn having started) ends the submission, so the same words sent again are a new message and are delivered. The identity list lives in memory for one app run: after a restart a retry is admitted as new input, and the transcript shows whether the first attempt arrived. Goal sends (`/goal`, an armed goal and the provider goal command), Claude Plan-mode prompt submission, row Retry, Resend and queue actions, generated actions and the iOS app carry no identity and keep the earlier behaviour.

While a turn is running, Send follows the app-wide [Send during a running turn](../settings/chat-defaults.md#send-during-a-running-turn) preference. **Queue for next turn**, the default, adds the input to the visible queue without interrupting the turn. **Steer active turn** submits it once through the existing steering route ahead of already queued input, which keeps its order. Providers with native steering (currently Codex and Copilot) receive it in the running turn at its next safe boundary; for the others UAM stops the running turn and then sends the steer first, so the composer labels that action Interrupt and steer. A steer that finds the turn already finished starts as ordinary direct input, except while the provider's CLI version check is still pending, when the steer is refused and the draft and attachments are kept; and Claude Plan mode still asks how to proceed before a steer is sent, including a goal command, whose goal is created only after that choice. Keep planning sends the prompt without leaving Plan mode; Escape or a click outside the dialog cancels, so nothing is created or sent and the draft stays. The composer names the selected action on Send (and Enter) and keeps a labelled button for the other action in a reserved slot beside it, so swapping Cancel for Send does not move the toolbar; idle Send remains direct input. The chosen action also applies to goal commands and survives stopping dictation, which sends once dictation finishes. Either action keeps the draft and attachments until admission is confirmed. CLI View has no UAM Send, because its input goes straight to the native CLI, so the preference does not apply there; see the [open decision](../documentation-review.md#active-turn-send-in-cli-view).

Each new turn, whether direct input or a goal continuation, clears the chat's previous stop reason, so a later Stop, failure or lost process is never reported as an earlier idle timeout.

Queue admission prepares settings for its exact owning input under the [queued setting agreement](../providers/models.md#queued-setting-preparation), while retaining the raw queue until normal durable admission and delivery gates allow it to advance.

A retained message from failed startup must remain actionable: Retry checks that exact message and resubmits it only when native recovery confirms it was not delivered, while Remove checks and removes only the named retained input. If saved history is not in memory, the action reads and validates it first rather than leaving the controls permanently unavailable. Changed input, uncertain delivery or active conflicting work keeps the original intact and explains why the action did not proceed; checking or reopening history never retries input on its own.

When manual input cancels a quota wait, local admission may save the cancellation and retained input asynchronously whether its provider session is absent, stopped or starting. The full save must be acknowledged before reporting saved admission or releasing provider input; a failed save keeps any previous waiting record authoritative on disk and must not claim crash-durable cancellation. The same staged cancellation applies to an already-owned ready SSH session satisfying the existing v3 admission predicate; the delivery stage must still match saved process authority, the original input writer and the retained authored input. Ready sessions with unusable input retain their refusal semantics.

A ready owned quota continuation publishes its exact claim before one dispatch attempt, then publishes settlement and the retained continuation before provider input. Recheck the native conversation, agent, process and its saved SSH authority, pending controls and raw queue at both boundaries; a stale or failed receipt holds work instead of granting replay. Small-model quota continuation also retains the active goal owner, objective, budget and command revision through claim and settlement, including before a runtime exists; a missing or changed goal scope holds that continuation. Cold process and control authority must also commit with the retained input before one owned launch attempt; cancellation or a changed launch identity holds the input without treating the save as process creation. Refusal preserves older delivery facts, and attaching to an existing SSH process retains its exact saved requests and unknown input classification. Restart and unsafe Retry keep their separate ownership checks.

Raw queued steering must publish its queue retirement, retained input and exact control envelope together before transport. While that receipt is pending, append may retain later FIFO input but edits, removal, reordering and another steer wait. A refused save keeps the original queue identity and captured policy, linking it to the retained unsent row without truncating parent output; an uncertain write retains the committed envelope and never restores replayable raw input.

Saving a managed request and creating its child are separate outcomes. The validated saved-parent receipt associates that originating action with its actual recorded row; it does not confirm provider delivery or grant child controls. If the parent request was saved but delegation later fails, keep that request once in history, clear only its submitted draft and show the delegation error. A failed or unconfirmed parent save retains the draft; it must not be presented as an accepted child or automatically replayed.

A retained direct input is shown as Sending only while native admission or delivery is actually pending. On an SSH chat whose host runs remote protocol 3, the helper's receipt for the exact prompt delivery is the write fact: Sending ends when it arrives, not when the provider turn completes; the receipt confirms the exact message also when it arrives after a reconnect or an app restart. While a helper receipt is owed, it is the only proof of that delivery: neither output nor a completed turn stands in for it. Otherwise a turn counts as delivered when the provider normally completes that turn's own prompt (the matching request, not a cancelled turn and not a late completion of another one); output alone never does, since it can come from a background task or an earlier turn. Older hosts have no receipt, so Sending lasts until the turn ends; after an app restart during a turn, a provider whose own-request proof was held only in memory (generic ACP, Codex) no longer confirms that message, so its marker stays. Delivery not confirmed is shown for a sent message with no write fact, no receipt and no such completion, such as one whose provider exited during the write. Every message dispatched from this version on is stamped as tracked, and for those only a write fact, a receipt or that completion clears the marker, whatever follows the message. For older messages without the stamp, the marker is hidden only when the same provider's response directly follows the message and ended normally; an interrupted or stopped response, a response from another provider, or an answer to input sent later hides nothing. When the evidence is unclear the marker stays: a stale marker is preferable to a lost message shown as delivered. A response that is still streaming hides nothing. Hiding the marker this way is display only: what such a message allows (no Edit, Revert or delivery actions without a write fact) is unchanged, and the marker never permits, blocks or repeats a send. Loading its saved message row, or lacking a native known-unsent classification, does not by itself establish an active send; unresolved input remains visible, and Retry stays unavailable when loaded native state has explicitly withheld retry authority. Available explicit recovery actions still recheck native eligibility before changing input.

A failed workspace preparation preserves the input and stops automatic reconnect attempts. An explicit retry may resume after the workspace problem is resolved; a setup failure must not leave a scheduled reconnect preventing the user’s next recovery action. A failed pre-launch repository baseline is held the same way, including after restart: a lone first input offers Remove and an exact-receipt Retry that captures the baseline again once. A remote Send whose provider launch is given up before the provider starts keeps its message as unsent. Retry appears on that message when it is the chat's first message or its provider session can be resumed, also after UAM restarts. It does not appear on a chat with earlier messages and no provider session, such as just after a provider switch, where a new Send still works. Input queued behind it stays held for Resume or Remove, and Retry appears only once that input is removed; resuming that input first leaves the earlier message unsent. On an SSH chat, a prompt staged for delivery whose connection closes before it is written (its delivery marker saved or still being saved) returns as one interrupted unsent message and the chat stops working, instead of waiting for a receipt nothing can still deliver; no prepared copy of it stays in the queue, and input queued behind it is held for Resume or Remove rather than turned into interrupted messages. A prompt that never reached the connection keeps reconnecting with growing delays for about a minute, so a short network loss recovers by itself, then returns in the same way with the error shown. The minute restarts whenever the connection gets as far as completed session setup or a reattach, so a connection that sets up and then closes before the write on every cycle keeps retrying, at up to a minute apart, and is not returned by this limit; Stop ends it. A prompt with no message of its own, such as a goal turn, is not kept as unsent: its goal is blocked with the error. A prompt that may have been written keeps reconnecting to the same remote process, with growing delays up to a minute while the connection keeps closing, and is never written as a second prompt.

Authored composer Send, goal first-send and pending Claude Plan prompt submission freeze their selected quoted snapshots at the original Send, before asynchronous goal or mode/permission operations. Only unchanged submitted snapshots for the same chat birth clear after admission; newer context is preserved, and a changed target chat/birth/host/workspace before delayed dispatch is refused. Snapshot metadata remains historical quoted input, never delivery/retry or workspace-control authority. Generated plan Approve/Deny actions remain independent of the composer draft, following [David's recorded contract decision](../documentation-review.md#referenced-context-action-sends).
