# Sending and recovery

An idle Send or Resend is direct input, even when startup or restart takes time; only input waiting behind active work belongs in the visible queue. Outgoing direct input appears immediately as one message at a stable transcript position; pending, held and definitely failed input stays there with a muted dotted treatment and a hover- and keyboard-accessible explanation. Admission means UAM retained the request; delivery is confirmed only by an exact matched native fact that the submitted input was fully written to provider input or accepted by the provider. Transcript materialization, processing state and unrelated output do not supply that confirmation. Existing recovery actions appear only when native delivery authority permits them; uncertain delivery or partial provider output must not be automatically replayed. Preserve the authored text, attachments, skills and selected agent during recovery. Display correlation follows the bytes the existing send path actually submits, including quoted context; identical attempts without matching native identity remain independently unconfirmed. Stopping work must distinguish an interrupted delivered turn from input known never to have reached the provider.

Queue admission prepares settings for its exact owning input under the [queued setting agreement](../providers/models.md#queued-setting-preparation), while retaining the raw queue until normal durable admission and delivery gates allow it to advance.

A retained message from failed startup must remain actionable: Retry checks that exact message and resubmits it only when native recovery confirms it was not delivered, while Remove checks and removes only the named retained input. If saved history is not in memory, the action reads and validates it first rather than leaving the controls permanently unavailable. Changed input, uncertain delivery or active conflicting work keeps the original intact and explains why the action did not proceed; checking or reopening history never retries input on its own.

Saving a managed request and creating its child are separate outcomes. The validated saved-parent receipt associates that originating action with its actual recorded row; it does not confirm provider delivery or grant child controls. If the parent request was saved but delegation later fails, keep that request once in history, clear only its submitted draft and show the delegation error. A failed or unconfirmed parent save retains the draft; it must not be presented as an accepted child or automatically replayed.

**Implementation: Partial.** Eligible fresh direct input retains its captured invocation through pending workspace preparation and full-save acknowledgement, and Stop conserves captured policy when conversion to interrupted history cannot fit the existing bounded carrier. Send/Unsent findings, broader recovery coverage and live acceptance remain open in the V5 log. See [provider-session reference](../reference/architecture/provider-sessions.md#undelivered-authored-input) and the [V5 change log](<../../V5 Improvement Change log.md>).

A retained direct input is shown as Sending only while native admission or delivery is actually pending. Loading its saved message row, or lacking a native known-unsent classification, does not by itself establish an active send; unresolved input remains visible, and Retry stays unavailable when loaded native state has explicitly withheld retry authority. Available explicit recovery actions still recheck native eligibility before changing input.

A failed workspace preparation preserves the input and stops automatic reconnect attempts. An explicit retry may resume after the workspace problem is resolved; a setup failure must not leave a scheduled reconnect preventing the user’s next recovery action.
