# Pull request watching

A chat can watch a GitHub pull request. UAM then reads the pull request in the background and, when something happens on it, sends the chat a short message so the agent can act: fix a failing check, answer a review or resolve a conflict. The user or the agent starts and stops a watch, and each watch belongs to exactly one chat. The behaviour follows pull request watching in [T3 Code](https://github.com/pingdotgg/t3code) (MIT licence), adapted to UAM's chats and tools.

## What wakes a chat

A watched chat is woken when a check fails or is cancelled, when checks wait for a maintainer's approval or action, when the required checks pass (or all checks, if none is required), when no check has reported 15 minutes after a push, when someone else comments or reviews, and when the branch starts to conflict with its base. Comments and reviews from the signed-in GitHub account never wake it; if that account cannot be identified, no comments are reported until it can. News is told once: a check that is still failing, a comment already reported and a conflict already reported stay quiet until something new happens, and a push starts the check and conflict news over for the new commit. Checks that were still running when the required ones passed bring one more message when they all finish.

## Reading GitHub

One service in the desktop app reads GitHub for every chat, through the user's signed-in `gh` command; UAM never reads, stores or logs the token. Reads run on a background thread and never on the interface thread. The service looks for due pull requests once a minute. A watched pull request is read every 2 minutes. A linked pull request that no chat watches is read every 2 minutes while it is being updated, every 5 minutes once nobody has updated it for 30 minutes and every 15 minutes while closed; one that is merged, or closed for over 24 hours, is not read again. A pull request GitHub cannot find is asked for again every 15 minutes. Chats that watch the same pull request share one read. Each request carries the `ETag` of the previous answer, so GitHub answers an unchanged pull request with "not modified", which does not count against the rate limit. A rate limit pauses all reads until the time GitHub names and is not a failed read. Chats on an SSH host are watched from the desktop too, so the remote computer needs no GitHub access.

## When watching ends

Watching ends when the pull request is merged or closed (the chat gets one final message saying which, then no more), after 10 messages in a row that brought only comments (a guard against bots answering each other; check, conflict or push news resets the count), after 8 failed reads in a row, when the user presses Stop on the chat's turn, when the user marks the chat done (Done or Clear all in Active Chats) and when the agent or the user stops it. Deleting the chat removes its links. A subagent's chat and a temporary side chat cannot start a watch. Stopping keeps the pull request linked to the chat and keeps what was already reported, so watching it again does not repeat old check or conflict news; comments made while nobody watched are not reported later. Unlinking removes the row and forgets what was reported.

## In the sidebar

A chat with an active watch stays in [Active Chats](../sidebar/active/active.md) between wakes, however long the pull request is quiet and even if the chat was marked done before the watch started. Its row reads **Watching PR** while no turn is running; a running turn shows Working and a question or failure still shows its own status. When the watch ends the chat follows the ordinary Active Chats rules again. Marking a watched chat done ends its watches, so Done and Clear all still clear the row.

## Starting and stopping

An agent calls the UAM tools `pr_watch` and `pr_unwatch` ([UAM tool connection](../providers/uam-tools.md)). In the chat, **Watch pull request…** in the workspace menu asks for a pull request link or `owner/name#number`. Each linked pull request has a row above the conversation with its state (Open, Merged, Closed, Not found or Checking), its title, counts of failed, running and passed checks shown as icons with numbers, a conflict mark, an eye button that stops or resumes watching and a button that unlinks it. The row also says when GitHub's rate limit paused reading or GitHub could not be read. Only `github.com` pull requests can be watched.

## Delivery and restart

A wake is one message in the chat that lists what changed with links to the checks and comments, for example the failed check names or the first 200 characters of a comment. If the chat is busy, the message waits in the chat's queue and is sent after the current turn. Each wake also adds one entry to the [notifications panel](../ui/notifications.md) that names the pull request and the chat; ending a watch because reads kept failing, or because the chat kept refusing messages, adds an entry without waking the agent. Watches, what each chat was told and any message not yet accepted by the chat are saved in `pr-watches.json` in the data folder ([source of truth](../architecture/source-of-truth.md)). After a restart the watches continue, old news is not repeated and an unaccepted message is delivered. Pressing Stop, marking the chat done or stopping the watch also drops a message not yet delivered, including the final merged or closed one. A message that the chat refuses is tried again every minute; after 30 refusals the watch ends with a notification.

Nothing has been checked against live GitHub or with a live provider, and review and David's acceptance are pending. Known gaps: a wake is sent through the structured send path, so a chat used only in CLI View may refuse it; each read takes the first 100 checks, comments and reviews, so reviews after the hundredth are not seen; a wake is admitted like a message the user typed, so it holds a subagent result that was waiting to continue the chat and cancels a Claude quota wait; the phone clients show no row.
