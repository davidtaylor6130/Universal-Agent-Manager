# Chat lifecycle

Users can create, select, rename, delete and pin chats without losing another chat’s history or runtime state. Deletion must respect related chats, native-history ownership and workspace ownership, show progress for meaningful background cleanup, and report incomplete cleanup honestly. A deletion whose commit is refused keeps its recovery record, which completes the deletion at the next start. Until then only what that deletion owns is unavailable: its chats can be selected, read and stopped but not changed, and nothing new can be placed in its workspaces. The record is set aside so everything else stays usable, including deleting other chats and workspaces and starting another deletion; the next start completes every record that was set aside. If the record cannot be set aside, later deletions wait for that restart. No deletion outcome leaves the whole application waiting for workspace deletion. Selecting a chat must restore its own saved context without sending a prompt. Selection changes no chat data, so it is not refused by a failed settings write, a worktree operation running on that chat or a pending workspace deletion; a remembered selection that could not be written is carried by the next settings save. Closing or deleting the open chat leaves a stable empty or next-chat view; background terminal and native-history refreshes never open a chat on their own. Display organisation does not determine whether a provider process is running. A chat can also start another top-level chat through the UAM [`chat_create`](../providers/uam-tools.md) tool, within the caller's own permissions; the new chat shows which chat started it.
