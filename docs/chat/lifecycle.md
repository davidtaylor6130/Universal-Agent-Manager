# Chat lifecycle

Users can create, select, rename, delete and pin chats without losing another chat’s history or runtime state. Deletion must respect related chats, native-history ownership and workspace ownership, show progress for meaningful background cleanup, and report incomplete cleanup honestly. A deletion whose commit is refused keeps its recovery record, which completes the deletion at the next start: only the chats and workspaces in that deletion stay unavailable until then, and nothing new can be placed in those workspaces, while every other chat and workspace remains usable. No deletion outcome leaves the whole application waiting for workspace deletion. Selecting a chat must restore its own saved context without sending a prompt. Selection changes no chat data, so it is not refused by a failed settings write, a worktree operation running on that chat or a pending workspace deletion; a remembered selection that could not be written is carried by the next settings save. Closing or deleting the open chat leaves a stable empty or next-chat view; background terminal and native-history refreshes never open a chat on their own. Display organisation does not determine whether a provider process is running. A chat can also start another top-level chat through the UAM [`chat_create`](../providers/uam-tools.md) tool, within the caller's own permissions; the new chat shows which chat started it.
