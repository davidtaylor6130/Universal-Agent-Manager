# Native session import

Native import discovers conversations from an included provider and lets the user import eligible history into the correct workspace and execution environment. Discovery is not execution or permission to resume work. Preserve supported text, tools, attachments and native identity, prevent duplicates/deleted-session resurrection and reject confirmed empty content. Authored text, attachments, reasoning, plans and tools qualify; setup-only text, whitespace and compaction/interruption markers alone do not. Unknown, failed or incomplete histories stay retryable, and confirmed-empty sessions can become eligible after receiving real conversation content. Ownership and deletion state must be rechecked before publication, including background startup choices. Discovery failures name the provider, native session and SSH host so a repeating failure can be traced without guessing.

[Chat Data](../settings/chat-data.md#native-provider-histories) supplies an explicit fresh controller-local scan through the same staged review and selected-import path, retaining unregistered absolute native workspaces for explicit assignment. Startup and explicit review both plan one new local workspace, named after the folder (a linked worktree takes its main checkout's name), for each existing absolute local directory that no workspace owns; histories in the same directory share it, nothing is saved until a selected import publishes, and declined or tombstoned histories plan nothing. Relative, empty or missing local paths are not planned (startup drops them; explicit review leaves them for assignment), remote histories are discovered only inside registered host workspaces, and portable bundles carry no workspace path. Assignment stages only the original native workspace and publication rechecks the selected folder plan alongside existing ownership, input-provenance and deletion guards. A scan cannot replace an active discovery/import, and decisions from a previous scan generation cannot apply to its replacement. Cached review alone does not start another scan. Bounded discovery details must retain an accurate omitted-issue total through staging and review, including when other providers have already filled the detail limit. All six provider readers feed this path; Antigravity retains explicit [storage-format and completeness limits](../reference/antigravity-native-history-decision.md).

The user's [import filters](../settings/chat-data.md#import-filters) exclude matching titles and folders from every discovery and from publication.

Startup import policy: startup offers only sessions with recorded activity within the startup age limit, for every provider. The limit defaults to 30 days until the user saves a value; 0 turns it off, and a saved value, including 0, is kept. Older sessions are left alone rather than declined, tombstoned or deleted, so explicit Chat Data discovery still lists and imports them: it rescans local histories without the limit and adds the remote sessions startup held back to its review. Held-back remote sessions last only for the current app session; after a restart, startup scans the remote hosts again. Age uses the latest time the provider's history reports during discovery; local Codex discovery reads only up to the first user message, so it uses the later of the session start and the rollout file's last write. A session exactly at the limit is still offered. A session with no readable time is still offered. Startup also leaves out sessions that still have OpenCode's generated name, exactly `New session - ` or `Child session - ` followed by OpenCode's millisecond UTC timestamp, whatever their age and even with the age limit off, in the same way: not declined, and still listed and importable through explicit discovery. Any other title is offered, including "New session" alone, and so is a local OpenCode session with no stored title, which discovery names from its first message. OpenCode is the only provider with a generated default name: the others title a session from its content ([decision](../documentation-review.md#startup-import-untitled-sessions)).

Remote startup scans run off the app thread, one worker per SSH host and at most four hosts at once, so an unresponsive host does not hold up the others. Each host's folders share one runner connection for the scan. If a host cannot be reached, UAM tries once more a few seconds later; if that also fails, the host's remaining workspaces stay pending and are retried automatically in the background (after one minute, then at doubling intervals up to 15 minutes) without leaving the review, and one notice names the host, the reason and the workspaces it will retry. A host that was already unavailable when the scan started is reported once. Remote OpenCode history checks the CLI version on that host and uses the matching list and export commands. Only the last non-empty line of the version output counts, so a wrapper's own version printed first is ignored; output without one clear version sends no history command. The checked version is reused for that host, command and folder for the rest of the app run, and checked again after a history command fails. A version UAM has not verified is refused with that reason, once per host. An untitled remote OpenCode session is valid and is named `Session <id>`.

## Sub-chats

A provider's own sub-agent sessions import as [sub-chats](subagents.md#catalogue-and-navigation) of the chat that spawned them. They are never separate top-level chats and never merged into the parent's transcript. A sub-chat is not listed for review: it follows its parent's decision. Importing a parent also imports the children its history names, into the parent's workspace; declining a parent, or leaving it unselected, leaves its children alone and does not decline them. A child whose parent is not in UAM and not in the scan is not offered.

A chat that is already in UAM, imported earlier or started in UAM, gets its missing sub-agent sessions only from a scan the user starts in [Chat Data](../settings/chat-data.md#native-provider-histories): that scan imports them as linked sub-chats without listing them, under the same rules. A startup scan never adds them ([decision](../documentation-review.md#native-sub-chat-import)).

A child is linked only on exact native evidence: the parent session that the child's own record names (Codex, OpenCode), or the child reference on the parent's spawning tool call (Claude Code, Gemini, Copilot). The provider, execution host and workspace must also match. Titles, timestamps and nearby messages are never used. Where the parent's tool call records the child's ID, that tool call opens the same sub-chat. A nested child keeps its own native parent where the provider records one: a Codex child of a child shows beneath that child, while Claude Code and Gemini record every sub-agent against the root session.

Scanning again imports nothing twice, and a deleted child stays deleted. A child that an earlier import saved as an ordinary chat gains its parent link when a later scan finds both, with its history and title unchanged. A child's history is read only when its parent is imported, under the same size and time limits as any other history. A child that cannot be read, or whose own record names a different parent, is reported by name while the parent and its other children still import. The startup age limit and the import filters apply to the parent, not separately to its sub-chats.

**Implementation: Needs verification.** Source is integrated with focused native tests on synthetic fixtures for Codex, OpenCode, Claude Code, Gemini and Copilot; live provider, SSH and packaged-app verification and acceptance remain pending. Known gaps: the manual-scan backfill covers controller-local chats only, and skips a parent the user moved out of the workspace that owns its directory; SSH scans cover only OpenCode and Codex, so Claude Code, Gemini and Copilot children on SSH hosts are not imported; Antigravity children are not linked; a Gemini child with inline images is reported and left to an explicit open; a child that runs in a different directory from its parent is not imported; an OpenCode child's own sub-agent sessions are not imported; a parent with no recorded start time cannot be linked, so its children are left out; and at most 64 children per parent are read. Per-provider evidence is in the [child session reference](../reference/native-child-sessions.md).

## Discovery media lifetime

Parsed inline originals acquired during discovery require a bounded producer cleanup owner before batch admission. Copies retained for startup selection, retries or partially prepared batches must preserve that owner until their last use; cancellation, refusal and abandoned results retire the encoded payloads on a worker. Failure during retention or later mapping must keep already acquired originals under that same cleanup owner. Producer capacity remains independent of batch capacity so pending choices cannot prevent their own import. Exhausting scan-wide payload or metadata admission must report a discovery error; omitted candidates must not become a successful complete scan or a confirmed-empty receipt. This cleanup owns only its parsed payloads: it grants no authority to delete provider/user source files, another operation's originals or acknowledged published originals. The controller-local Gemini discovery route carries this ownership through retained payload copies; broader platform and user acceptance remain pending.

## History recency

Untargeted reconciliation compares validated instants rather than timestamp spelling when choosing between differing histories of equal length. Explicit offsets retain their full supported fractional precision; malformed or unknown timestamps cannot authorize replacing saved text. Legacy local display timestamps use the controller’s current timezone as a compatibility assumption, with invalid civil times and exposed daylight-saving ambiguity treated as unknown. These old records contain no original timezone, so this assumption cannot reconstruct changed-zone or foreign-backup history, or certify every political offset fold. Existing count precedence, identity, revision, deletion and live-work checks remain required; time alone grants no ownership. Duplicate snapshots of one native conversation retain UAM-owner and count precedence; differing update and creation timestamps follow this known-instant ordering before the existing metadata tie rules. Exactly equal timestamp values retain those established tie rules. This policy does not change explicit-refresh authority or establish correctness of every remaining sorting and recency consumer.

## Refresh metadata recency

Explicit refresh may adopt the scoped native messages under its existing count, ownership and save rules while retaining a later saved UAM metadata timestamp. Compare known instants when advancing that metadata; equal or unknown ordering retains the saved value and spelling. An empty saved value may be initialized from a valid incoming timestamp. This metadata rule does not veto message adoption or authorize another session, workspace or execution host. Remaining recency consumers require their own verification.

## Saved history read failures

A saved summary does not establish that its messages were read successfully. When reconciliation needs saved messages and that read fails, refuse the affected import or open operation, retain the saved conversation and active draft, and report a retryable failure. Never present an unread summary as a successfully loaded empty conversation. Restoring access allows a fresh guarded retry; previously completed native-link saves retain their established ownership.

## Remote refresh publication feedback

A clean native ownership or saved-history refusal before publication must say that this refresh was not saved, retain current history and offer a fresh guarded refresh. When publication or its final acknowledgement cannot be confirmed, direct the user to reopen the chat and inspect current history before retrying; a failed acknowledgement does not authorize rollback or another publication attempt. Use native typed publication observations for this distinction rather than interpreting diagnostic text, and retain committed-history warnings. A failed explicit refresh uses the notice title “History refresh failed” and labels its saved-history read action “Reload history”; that action reads saved history without starting another native refresh or resending input. For the same still-current owner after an unconfirmed publication, ordinary recovery reads observe a bounded page of the current saved primary, rechecking identity and physical revision before display; they do not adopt it into the live native chat or acknowledge originals, and an unreadable or changed snapshot stays a failure. Normal selection recency and validated transcript eviction must still allow a fresh guarded read. Recovered image previews and deferred tool output resolve from that displayed saved history with matching detail identity, page digest and physical revision, retaining original ownership checks; they must not fall back to the old live transcript. These reads serve the user’s current action rather than idle background work. An unavailable recovered image preview offers “Retry preview”, retaining its saved-history binding and bounded native capacity; retrying reads only that preview, and replaced or closed views reject late results. Successful guarded return-to-latest reads also clear obsolete failure context. The [separate visible refresh entry-point decision](../documentation-review.md#remote-refresh-entry-point) remains open.

## Remote refresh ownership and capacity

Loading normalizes legacy parent and branch-root values in live state, such as an unparented root named by its native session ID or a parent named by its owner's native ID, without rewriting the saved chat. An explicit remote refresh treats that saved owner as unchanged only when its saved lineage normalizes to the current live lineage across the current chat collection, and then saves the normalized lineage; any other saved difference still refuses. Explicit remote refreshes reserve their own bounded capacity, so slow remote reads cannot occupy the capacity shared by local branch, managed-run and metadata preparation; when the remote budget is full, the refresh reports that it is busy. Explicit remote Gemini refreshes, which use this budget, have two slots per SSH host within a total of four for all hosts, and each read runs on its own thread, so a slow or unresponsive host's reads do not delay another host's read: a refresh is reported busy when its host's slots or the total are full, and is refused rather than queued. A refresh's later preparation and save steps still use the shared file queue. Opening a passive SSH child with inline images uses the same per-host slots and its own thread for the read. Other providers' remote refreshes take no slot, have no slot limit and still read on the shared file queue, so they can wait behind each other. Starting a helper install or update on a host stops that host's in-flight history and child refresh reads for every provider and frees any slots they hold; other hosts' reads continue. Two unresponsive hosts can still fill the total until their bounded reads time out.

## SSH history size limit

A Claude, Copilot or Gemini native history read through a host's helper is one snapshot of at most 64 MiB that must arrive within 60 seconds. Copilot's `workspace.yaml` counts towards the limit and every candidate file with that session ID is summed before its identity is checked, so a history of exactly 64 MiB can still be refused, and opening a child also reads its parent, so an oversized parent refuses the child. An oversized history is refused with that reason instead of being shortened: nothing is published, an existing saved copy and its originals stay as they were, and the same history can load once it fits. The child pane's refresh keeps its general notice and puts that reason under Technical details; other subagent open controls show general failure text, and the tool-details Open control shows nothing (known gap). Local Claude children use this same read limit; local Gemini children do not.

## Refresh query cancellation

Cancelling a native history query withdraws only its delivery. All history matters, so an admitted read of the provider's native history files and its guarded save to saved UAM history always finish before anything is delivered. These reads use local or SSH native files, not model calls or provider caching; the cancelled request receives no history, moves no selection and pushes no state of its own. A newer request for the same chat or child waits for the read already in flight instead of starting another, and the next request after a cancelled save serves that saved result without reading the provider again; later explicit refreshes read normally. While a refresh runs for more than a moment, the open chat shows a “Refreshing history” status divider with its elapsed time over its loaded messages, until the read has finished and answered (an empty pane keeps its loading skeleton); the interface waits up to five minutes for that answer instead of the ordinary 30-second saved-read bound. A late result is answered only to its own request, and every existing identity, ownership and revision check still decides whether it may be saved. Query cancellation never stops the provider turn, and handler shutdown or lost ownership still stop reads. Saved-only reads, such as managed transcripts, lose delivery the same way, and side-chat context preparation keeps its existing replace-on-new-request behaviour because it reads no provider history. [Decision record](../documentation-review.md#native-history-query-cancellation).

## Internal result input

Import and explicit refresh classify UAM-internal Codex result input as machine data only from the parent's retained, exactly scoped native turn and complete original input receipt. Unknown or ambiguous provenance and human copies on another turn remain user history. Preserve cumulative receipt DATA through refresh, save and reload without recreating execution authority. A changed primary or receipt snapshot invalidates an in-flight refresh rather than publishing stale classification.
