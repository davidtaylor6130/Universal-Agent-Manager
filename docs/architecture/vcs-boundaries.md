# VCS boundaries

Git and SVN commands, status parsing, revision semantics, path validation and publication rules belong behind VCS service/module interfaces. UI and bridge code request status, comparison or a selected operation without building repository command strings or duplicating Git/SVN rules. Keep shared workspace identity and ownership separate from backend details, and execute against the captured local/remote workspace. Never turn a Git checkpoint into an SVN publication or silently substitute a different repository operation.

**Current structure:** [VcsCommitService](../../src/app/vcs_commit_service.h) and [workspace context services](../../src/app/workspace_vcs_context_service.h) form existing boundaries; [VcsProvider](../../src/app/vcs_provider.h) is the extension point for later version-control work: `VcsCommitService` routes settings gates, availability detection, status, diff and commit through its Git and SVN implementations, which still live in the service file. Each system's static facts, including its display name, [capability list and read-only command allow-list](../../src/common/vcs/vcs_provider_declaration.h), are declared per system, and the literal command filter reads those allow-lists. History, one revision's patch, working-copy update and the relation of a branch to the path it was copied from (for the history graph) also go through the interface: the service checks the system's switch and its declared `History`, `Update` or `OriginComparison` capability, then hands the provider one command runner already bound to the local workspace or its SSH host, so a system implements each once for both. For a local chat in a UAM snapshot of an SVN working copy that runner is bound to the source working copy, recognised by `DescribeLocalSnapshotSource` with the rule snapshot creation uses, since the hidden Git copy has no SVN metadata; the status names the snapshot source with the SVN capabilities offered for it, and an SVN update of any other isolated chat is declined. SVN's implementation is [svn_history](../../src/app/svn_history.h); Git declares none of these yet and is declined with a clear message. The bridge sends the active system's capability names with each status, and the commit panel offers History, Update and the branch graph from that list rather than from the system's name. These requests carry the caller's request id so `cancelVcsRequest` can stop the client process. The chat branch picker's listing, selection check, switch recheck and switch go through the interface too: the bridge chooses the provider from the picker's `vcsType` id (anything else is Git), refuses creation for a system that does not declare `BranchCreate`, and asks the provider whether its choices are located (SVN: repository folders under an explicit parent, each selection carrying the working-copy context it was listed in) or named branches (Git). Git's implementation delegates to `GitWorktreeService`, SVN's to `SvnBranchService`; the bridge keeps only the wire format, runtime settlement, leases and the Git first-message pending branch. `ChatComparison`, `RevisionComparison`, `BranchList`, `BranchSwitch` and `WorkspaceIsolation` are declared but not yet read. Other Git and SVN work does not go through the interface yet: worktree and isolation operations remain in `GitWorktreeService` and the bridge handlers, the interface has no "open in" actions, the chat reference capture and the goal reviewer's change summary ask for Git by name, and repository context and route matching remain in `workspace_vcs_context_service` and `repository_route_match_service`. `ClassifyCommand` in `command_safety.h` keeps its own risk-tier list of Git and SVN actions, separate from the read-only allow-lists. SVN commands run through its argv-only `RunSvn` helper, and every local `.git`/`.svn` root walk goes through `paths::FindNearestVcsRoot`, so a Git repository nested in an SVN checkout is Git. Callers keep their own rules through its parameters: `VcsRootKinds::GitOnly` for lookups only Git can answer (linked-checkout resolution, Claude worktree discovery, chat baselines), and a custom probe where a caller needs more. Snapshot classification uses both, so an enclosing Git repository outranks a nearer `.svn`; its probe also recognises bare repositories, ignores empty `.git` folders, does not follow links and reports a marker whose status cannot be read as unknown. Registered-folder containment uses a probe to compare each ancestor before the marker check, so it stops at a match or at the nearest root, inclusive. Checks of one exact directory are not root lookups and stay as they are, and `RemoteWorkspaceHasGitMetadata` walks runner paths rather than local ones. Separate backend modules are the placement agreement, not an already-completed refactor. OS execution goes through [platform services](platform-boundaries.md), and workspace mutation retains leases, selected-path checks and save/recovery barriers. Document unsupported backend operations rather than simulating success.

[SvnBranchService](../../src/app/svn_branch_service.h) owns bounded explicit-parent discovery, working-copy/foreign-user validation, revision-pinned switching and branch creation (a layout-placed server-side copy pinned to its source revision and confirmed from the repository log, then a guarded switch straight to that commit with the folder switch's checks) through an injected platform command adapter. The layout lookup it shares with Settings is `svn_layout_lookup.h`. A runner that can be stopped must let the commands `SvnCommandChangesRepository` names (the copy commit and the switch) finish once started. Git defers a new branch for an unused chat to its first message and SVN commits at once; the provider says which (`DefersBranchCreation`), so the bridge never names the system. The SVN `VcsProvider` reaches it for the composer picker, building the same ownership scope from the bridge's worker snapshot. The existing composer bridge owns chat-incarnation/history checks, runtime settlement and its exclusive workspace lease; repository switching changes working-copy state without writing Git isolation metadata or changing the chat’s working directory.

The shared SVN scope builder projects every local chat’s active, worktree and retained source paths, with folder fallback, so bridge ownership checks are exercised through the service boundary. Full working-copy validation inventories recursive SVN metadata, including excluded nodes, before mutation and final confirmation; root depth and clean status alone are insufficient.
