# VCS boundaries

Git and SVN commands, status parsing, revision semantics, path validation and publication rules belong behind VCS service/module interfaces. UI and bridge code request status, comparison or a selected operation without building repository command strings or duplicating Git/SVN rules. Keep shared workspace identity and ownership separate from backend details, and execute against the captured local/remote workspace. Never turn a Git checkpoint into an SVN publication or silently substitute a different repository operation.

**Current structure:** [VcsCommitService](../../src/app/vcs_commit_service.h) and [workspace context services](../../src/app/workspace_vcs_context_service.h) form existing boundaries; [VcsProvider](../../src/app/vcs_provider.h) is the extension point for later version-control work: `VcsCommitService` routes settings gates, availability detection, status, diff and commit through its Git and SVN implementations, which still live in the service file. Each system's static facts, including its display name, [capability list and read-only command allow-list](../../src/common/vcs/vcs_provider_declaration.h), are declared per system, and the literal command filter reads those allow-lists. Capabilities are declared but no caller reads them yet. Other Git and SVN work does not go through the interface yet: branch, worktree and isolation operations remain in `GitWorktreeService`, `SvnBranchService` and the bridge handlers, and repository context and route matching remain in `workspace_vcs_context_service` and `repository_route_match_service`. `ClassifyCommand` in `command_safety.h` keeps its own risk-tier list of Git and SVN actions, separate from the read-only allow-lists. SVN commands run through its argv-only `RunSvn` helper, and every local `.git`/`.svn` root walk goes through `paths::FindNearestVcsRoot`, so a Git repository nested in an SVN checkout is Git. Callers keep their own rules through its parameters: `VcsRootKinds::GitOnly` for lookups only Git can answer (linked-checkout resolution, Claude worktree discovery, chat baselines), and a custom probe where a caller needs more. Snapshot classification uses both, so an enclosing Git repository outranks a nearer `.svn`; its probe also recognises bare repositories, ignores empty `.git` folders, does not follow links and reports a marker whose status cannot be read as unknown. Registered-folder containment uses a probe to compare each ancestor before the marker check, so it stops at a match or at the nearest root, inclusive. Checks of one exact directory are not root lookups and stay as they are, and `RemoteWorkspaceHasGitMetadata` walks runner paths rather than local ones. Separate backend modules are the placement agreement, not an already-completed refactor. OS execution goes through [platform services](platform-boundaries.md), and workspace mutation retains leases, selected-path checks and save/recovery barriers. Document unsupported backend operations rather than simulating success.

[SvnBranchService](../../src/app/svn_branch_service.h) owns bounded explicit-parent discovery, working-copy/foreign-user validation and revision-pinned switching through an injected platform command adapter. The existing composer bridge owns chat-incarnation/history checks, runtime settlement and its exclusive workspace lease; repository switching changes working-copy state without writing Git isolation metadata or changing the chat’s working directory.

The shared SVN scope builder projects every local chat’s active, worktree and retained source paths, with folder fallback, so bridge ownership checks are exercised through the service boundary. Full working-copy validation inventories recursive SVN metadata, including excluded nodes, before mutation and final confirmation; root depth and clean status alone are insufficient.
