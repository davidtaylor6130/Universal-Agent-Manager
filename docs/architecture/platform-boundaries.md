# Platform boundaries

OS-specific processes, PTYs, dialogs, paths, dictation, file-manager launches and application integration belong behind the platform interfaces. Shared application, runtime and bridge code asks for a capability through those interfaces instead of embedding macOS/Windows command strings, native handles or scattered OS conditionals. Put a missing operation into the appropriate interface and implement its supported platform routes; report unsupported capability explicitly. Keep process-tree ownership, cancellation and cleanup semantics consistent without pretending different OS guarantees are identical.

A caller that polls a stdio child for exit and reads its output must observe the exit before that iteration's nonblocking reads and act on the exit only once those reads return no data. Output written before exit is then already in the pipe, so a child that prints its result and exits immediately is not reported as silent, disconnected or failed without detail. Waiting for pipe EOF after exit is unnecessary for this and must stay under the caller's deadline, because a detached descendant can hold the pipe open. Windows requests 64 KiB output pipes instead of its default of about 4 KiB, matching the usual macOS and Linux capacity (macOS grows its 16 KiB default on demand; Linux defaults to 64 KiB), so a child blocks once per 64 KiB of unread output rather than once per 4 KiB and output that fits the pipe can be written in full before exit between a caller's polls. The Windows wait between polls remains a fixed timer-granularity pause, so this capacity, not the wait, is what keeps a bounded stop or exit drain from spending its deadline on repeated full-pipe stalls.

Background workers that the UI poll thread spawns start through `uam::platform::StartBackgroundThread` (or call `LowerCurrentThreadToBackgroundPriority` first) so they run below UI priority: macOS utility QoS at minimum relative priority, Windows below-normal and Linux nice 10. A thread already at or below that level is never raised. These are weighted, not strict, priorities, so a worker holding a lock the UI waits on still progresses (#647). Workers whose join or wait sits on a user-visible stop, flush or exit barrier stay at default priority, because a lowered worker gets no boost from a future or join wait: the chat-save reader, chat-save publication, baseline, prepare and queue writers (force and shutdown barriers), process stop and kill workers (a user stop must not be delayed), provider process creation for a staged ACP launch (the user is waiting for the provider to start), terminal native-media preparation and publication (the exit settlement waits up to 15 seconds for them), the OpenCode configuration refresh, worktree retention discovery and removal, OpenCode compaction sync and history queries, and goal-loop turn checkpoints. Cancellable `std::jthread` workers that are only joined after a stop request at teardown, such as model catalog, route match and CLI compatibility checks, are lowered deliberately. Native-import `publication_sync` is lowered because the UI only polls it with a zero-timeout wait. The detached waiter that drains cancelled native-history futures only sleeps and is left unchanged, as is the detached thread that reaps a stopped macOS parent-death watchdog, so a provider exit does not wait for the watchdog in the caller (often the poll). A thread the UI poll stops and joins must end every remote wait on that stop: its `RunnerClient` takes the thread's stop token through `SetStopToken`, as the UAM control relay does, because a join otherwise lasts the 45-second handshake or 15-second request of a host that is not answering (#870). A `std::packaged_task`, `std::async` or CEF worker task keeps its captures after its result is published, so a worker holding a lease or other ownership moves it into a body local, or the task drops it, before the result can be observed. Bridge requests that run a subprocess or talk to a remote host (Git, SVN and SSH work, including rollback, port and baseline capture) run on the query handler's four worker threads and complete on the UI thread; CEF runs each shared file lane one task at a time, so such work there would delay saved-history reads in unrelated chats. Creating or deleting a memory entry in an SSH workspace is such a request; the same request for a local scope stays on the UI thread, where it only writes a file. A local chat's work is keyed by chat and a remote chat's by host, so each keeps its order and an unreachable host occupies one thread. Requests not yet moved are a known gap: prompt and attachment preparation, repository route matching and saving remote host options still use the shared lanes.

**Current structure:** [platform services](../../src/common/platform/platform_services.h) provide process/terminal and other interfaces with platform implementations. Computer use and some feature adapters have their own platform-specific files; they should retain narrow interfaces too. This is a placement rule, not a claim that every existing OS branch has been migrated. Test common contracts and the affected OS implementation; a macOS fixture pass does not establish Windows behaviour.
