# Notifications

Chat lifecycle notices belong in the transcript; app-wide failures, warnings, completed system actions and update notices belong in the bell panel with one shared transient alert surface. Features must report through the shared path rather than adding independent popup systems. This is the agreed product direction recorded in the [decision record](../architecture/decisions.md). The implementation is source-integrated but not yet visually verified or user tested; review and acceptance flags remain pending; see the [archived V5 change log](https://github.com/davidtaylor6130/Universal-Agent-Manager/blob/1d4865fcb/V5%20Improvement%20Change%20log.md).

- Chat status notices (refreshing history, compacting, waiting on subagents, stopped/timeout and response interrupted) are inline transcript dividers, never composer-docked or tagged on a message. A turn stopped by a timeout uses a transcript Notice instead of the raw composer error: it names the limit and its value, says nothing was lost and, for a limit UAM owns, offers **Restart with +15 min**; Copy error retains the raw diagnostics. A [stream-watch](../providers/runtime-lifecycle.md#stream-watch) loop stop uses the same notice with the repeated content and **Restart**, labelled **Continue in new chat** when it re-runs the message in a branch chat. The notice waits until the stop's cancel has settled. A failed restart is announced as an alert outside the notice.
- The compacting divider shows its existing scene, label and elapsed time without a context-fill meter; verified summary text stays hidden during generation and appears only inside the collapsed completed or interrupted summary.
- Direct input keeps its stable message position in the transcript, with pending or definitely undelivered input shown as a muted dotted message with an accessible explanation and guarded recovery actions; direct startup or restart input must not be labelled as future queued work. Legacy rows retain original message positions and offer Retry only when native recovery permits it. A real future queue entry referring to the same input replaces the duplicate recovery row. Partial-output or uncertain-delivery turns remain in the transcript with an interruption divider.
- One notifications panel (the bell rail) holds every app-wide message: failures, warnings, completed system actions and available updates. The bell shows an unread count, and update notices are reported through this same system rather than a separate bottom-right notice.
- One shared transient alert (`TransientAlertSurface` in `AppShell`) uses one persistent, initially empty polite announcement region for each retained notice, without duplicate live announcements from the visible surface or no-fit description, and briefly shows each new message. Transient notices slide in from the bottom right inside the chat area, with the same gap from the bottom as from the right edge, never covering the bell or update buttons, and auto-dismisses after 5 seconds with a visible countdown that pauses while that notice is hovered or keyboard-focused, sliding back out the way it came before leaving the message in the panel. Available height stays below pane headers and window controls; long text scrolls in a keyboard-accessible region while actions stay visible. If the viewport cannot hold a readable message and its actions, a polite announcement directs users to the retained notification through the bell, which exposes that description and keeps its unread count. Each notice pauses only its own countdown while hovered or keyboard-focused. An open right-side panel suppresses the popup while each newly retained notice still announces once; closing the panel does not resurface or repeat it. The panel replaces the transient surface so it cannot cover that panel’s controls; focused dismissal or loss of usable space returns focus to the bell.
- Transient alerts stack rather than replace one another: every new notice enters at the bottom of the stack and pushes older ones upward, each with its own 5-second countdown; hovering or keyboard-focusing one notice pauses only that notice's countdown and drain fill while the others keep counting (focus left by a mouse click, as on `Copy message`, does not hold it once the pointer leaves, unless a key other than a Cmd or Ctrl shortcut is then pressed inside it), and the `Show N more` toggle holds none. The stack never exceeds 30% of the window height (nor the room below pane headers); when more notices than fit are showing, the oldest collapse behind a `Show N more` button at the top of the stack, which expands them into a scrollable list within the same cap and offers `Show fewer` to collapse again. Collapsed notices keep counting down and expire on their own, and never hold; revealing one shows its drain fill at the time already used; a notice that had keyboard focus when it collapsed hands focus to the `Show N more` toggle (or the bell). How many fit counts a multi-line notice, such as several updates, at its content height rather than as one row, including while it is still sliding in. A notice identical to one still showing (same message, tone and action, or the same update set) does not add a second toast: the existing toast moves to the bottom of the stack as the newest notice with the same slide-in, shows a repeat count such as `×3`, restarts its countdown (still held if the pointer was on it) and is announced again; the panel still records each occurrence. Distinct notices always stack. Each notice dismisses individually through its dismiss button or Escape while focused; its slot closes as it drops back toward the bottom so the others slide into place, and reduced motion or Motion Off shows and removes notices without movement.
- The update notice is plural-aware: one update reads `Update available: <name> <version>`; several read `N updates available` followed by up to three `<name> <version>` lines (four are listed in full; five or more end with `and N more`). Versions in the toast drop protocol/build suffixes; the bell row detail keeps every full version, separating updates with semicolons, and Review updates holds the full list.
- Notice text in the toast and the bell panel is selectable. Every error or warning notice, and any notice with detail text, carries a `Copy message` icon button (Copy, then Check on success) that copies the message plus its detail or error text through the shared `copyTextToClipboard` helper (native bridge in CEF, browser clipboard otherwise). Info and success notices without detail have no copy button.
- No feature-specific popups or toasts. Features report through `reportAppNotice` for completed or informational messages and `reportAppFailure` for failures (both in `utils/appFailure.ts`). A refused chat control (Stop, Cancel turn, rename, model, reviewer model, reasoning, speed, UAM agent or small-model mode) shows one `reportAppFailure` whose message names the control and then gives the backend's reason, such as “The chat was not renamed. The chat could not be saved. Try again.”, or “Try again.” when the backend gave none (the toast never shows a notice's detail, so the reason is in the message); the control returns to the last value the backend accepted, never reverting silently. A caller that already names the change, such as a slash command or a provider handoff, carries that reason in its own single notice instead. A stop or cancel that UAM is still confirming is in progress, not a failure, so it raises no notice. Refusal reasons are fixed wording chosen by the refusing handler: never the shared status line, filesystem paths, host names, tokens or raw exception text, which stay in the diagnostics log.
- Organisation operations offer no undo toast or organisation-undo shortcut; ordinary text-editor undo remains available. Failed changes are reported through the shared path.

The no-undo agreement concerns organization operations; it does not remove ordinary text-editor undo. [Sending](../chat/sending.md) and [compaction](../providers/compaction.md) own their behaviour; the notes here specify presentation. Do not describe the notification system as visually verified or accepted until the pending work is resolved. Update notices that still show install or check errors inline in the updates panel remain a target, not current behaviour.

The panel exposes unread state/counts, mark-all-read and individual dismissal; these change notification state without stopping the underlying task, deleting chat history or declaring a failed operation fixed. Actionable entries retain their relevant details and current confirmation rules.

Every panel entry shows a relative age as its accessible name, with its full local date and time supplied once through the tooltip description on keyboard focus or hover. Timestamps use the shared visible keyboard focus indicator. UAM records when the running shell first observes each notice identity, using a valid recorded failure time when available; reopening the panel, marking read and unrelated state updates do not reset that time. These times are local session metadata, not a durable notification history or a provider event time: resolving a source ends its retained timestamp, and a later recurrence or app restart is observed anew. The panel groups notices into Today and Earlier at local midnight, newest first within each group, while preserving warning/error cues and focused controls. Relative ages and groups refresh when the panel opens, every 30 seconds while the nonempty panel is open and when the window regains focus or visibility, without repeating announcements or changing unread state. A future recorded time displays Just now until the local clock catches up and stays out of Earlier.

## Choosing the surface

- **Needs the user's decision or input** (confirm a risky mode such as YOLO, choose between options, enter a value): a proper popup built from the dialog primitives (`ConfirmDialog`, or `Overlay` for forms), one task per popup, taking focus only when its chat is the one open.
- **Reports something that happened** (a warning, failure, success or "couldn't do that"): a system alert through `reportAppFailure` / `reportAppNotice`, which shows the transient bottom-right alert and keeps the entry in the bell panel. Wording names what failed and what to do next in plain language.
- **Inline `Notice` bar**: only for a persistent state tied to that exact place that stays true while the user works there (for example an unsafe setting beside its control, or validation next to a field). Never for a one-off event or a question.
