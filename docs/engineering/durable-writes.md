# Durable writes

Saved records (chats, settings, folders, memory entries, instruction files and their `.bak` companions) are written through `uam::io` in [`io_utils.h`](../../src/common/utils/io_utils.h): a complete private temporary sibling is written and synced (`F_FULLFSYNC` on macOS), then published, then the directory is synced before the write reports success. A failed save leaves the previous file in place; success is reported only after the commit. The [data authority agreement](../architecture/source-of-truth.md) owns which file is authoritative.

## Replacing an existing file

The first write of a file is a plain rename. Replacing an existing file uses an atomic exchange (`renameatx_np(RENAME_SWAP)` on macOS, `renameat2(RENAME_EXCHANGE)` on Linux, `ReplaceFileW` on Windows), which leaves the previous file at the temporary name for the `.bak` companion or the conditional publication evidence path.

Some volumes do not implement the exchange: SMB shares (`smbfs` reports `VOL_CAP_INT_RENAME_SWAP` unsupported), exFAT, NFS and some FUSE filesystems. When the exchange fails with `ENOTSUP`, `EOPNOTSUPP`, `EINVAL`, `ENOSYS` or `ENOTTY`, the volume (by `st_dev`) is remembered for the rest of the process and that replacement and later ones on it use a fallback:

1. Copy the previous file first to a fresh `.tmp.` sibling (or the reserved private evidence path for conditional chat publication), keeping its mode where the volume allows. The copy is synced when the save is durable; cache-style saves that skip syncing skip it too. A copy, not a hard link, so the previous file's identity and change time are untouched and the destination never gains a second link.
2. Sync the directory, then `rename(temporary, destination)`.
3. Move the kept copy to the temporary name, so callers find it exactly where an exchange leaves it; the caller then syncs the directory as usual.

Any other exchange error still fails the save without a fallback. If the installing rename reports an error, the destination's identity, size and modification time decide the outcome (identity alone is not trusted, because smbfs without server file IDs and exFAT can reuse an inode number after a rename): still the previous file, so the copy is removed and the save fails unchanged; the candidate, so the client reported an error after the rename landed and the save is complete; missing, so the copy is renamed back. Anything else fails held with the previous file kept: when the name is missing it becomes the `.bak` companion if none exists; otherwise it moves to `<name>.held.<token>`, which no sweep removes and which the error names, and conditional chat publication leaves it at its reported evidence path. A held failure keeps the previous file only; the caller decides whether to keep or discard its candidate.

**Weaker guarantee.** The fallback never exposes a partial destination, but it is only as atomic as the volume's own rename-over-existing: an SMB client or server may remove the old name before installing the new one. A crash between the two directory syncs can leave the copy under its `.tmp.` name (or the chat evidence name). The abandoned-temporary sweep removes `.tmp.` names at least 24 hours after the copy was made, and only when `AtomicWriteFileDetailed` next writes that path while it or its `.bak` exists. Callers that commit prepared temporaries through `CommitSyncedAtomicTemp` directly are not swept: memory entries, instruction files, chat primaries, summaries and indexes, chat folders, the agent-run ledger and the remote runner client. The `.bak` of a fallback save carries the time of the save, not the previous file's modification time. Choosing the data folder in Settings refuses network volumes; the default root and an external `UAM_DATA_DIR` are not checked. See [Storage](../settings/storage.md#application-data-folder).

**Implementation: Partial.** Fallback, capability cache and errno-injected cases (`tests/durable_replace_fallback_tests.cpp`) are in source and pass on Linux; the Linux runner build compiles the shared POSIX path. The macOS and Windows branches have been checked by reading only, and their compilation and the cases on macOS are pending CI. A save on a real SMB share and an exFAT volume on a Mac remains unverified, including whether instruction-file preparation (`fcopyfile` metadata copy) succeeds there.
