# Testing

Choose tests by changed behaviour and failure risk, not a required test count. A defect fix needs a focused case that exercises the actual failure and passes after the correction where practical; cover material failure, ownership, persistence and recovery boundaries affected by the change. Do not mirror implementation details, add trivial tests for wording-only edits, weaken assertions or delete failing cases to produce a green result. Documentation-only work uses navigation, coverage and consistency checks unless executable tooling changes require their own verification.

| Change | Expected verification |
|---|---|
| Native behaviour or persistence | Build the affected test target, run exact connected cases, then the required complete native inventory and remaining CTest gates after connected edits settle. Include round-trip/save-failure and stale-result cases where those boundaries change. |
| React/UI behaviour | Run focused regressions during iteration, then the frontend suite and production build; visually check changed states/themes and retain required Claude review. |
| Platform/provider/VCS adapter | Exercise the shared contract and affected adapter; explicitly report unavailable OS, authenticated CLI or remote acceptance. |
| Performance | Reproduce the costly path and measure the same workload before/after; preserve correctness and timing budgets. A smaller function or a passing build is not measured improvement. |
| Build/packaging/exclusion | Verify the affected configuration and resulting artifact, including shipped resources and excluded-feature mentions where applicable. |

The [performance suite](../reference/performance-suite.md) (`scripts/perf_suite.py`) collects these timings, the packaged app's startup, memory and idle figures on a synthetic 2,000-chat data root, the packaged app driven through a deterministic fake provider (new thread, first word, long thread, typing lag and memory with five agents streaming, per-thread memory) and UAM's request overhead into one report against a committed baseline and published reference figures. It is report-only, including its CI job on pull requests into the V5.2 performance branch that change code; a performance change cites its before and after figures from local runs on the same machine, with packaged-app figures from a signed-in desktop session.

Reuse one isolated build folder and installed dependencies. Run the connected checks first, batch related edits before the final broad run and repeat passed gates only after a new change, failure or unresolved concern. Exact commands and mandatory gates remain in [AGENTS.md](../../AGENTS.md). Pull-request CI runs the complete native core inventory on macOS ARM in four shards (`scripts/run_native_tests.py --shard I/N`, every Nth case, so the shards together run each case once); Windows runs on a pull request only for changes `scripts/select_native_tests.py` marks as platform-relevant, with the core cases mapped from the change split across four Windows shards, and pushes to the base branches run the full suite on macOS Intel and Windows. Release candidate tags run every platform and build-flag row before a final release. Hosted CI runs the native core inventory in two processes, except the cases with tight wall-clock budgets listed in `tests/ci_serial.txt`, which then run one at a time, each in a fresh process, so no other test process competes with them; add a case there when it asserts a sub-second real-time budget or depends on sleep or lease timing. A completion deadline that only bounds background work may scale from a calibration run of the same workload on that machine (for example the median of three saves and reloads of the fixture chat), keeping its fixed value as the floor. A per-input or per-poll budget stays fixed unless the case measures the blocking work it guards against on that machine, and then scales only to below one unit of that work (for example half the cheapest median of three fixture chat saves, reloads or resource reads), so a call that performs the work synchronously still fails. A completion deadline for a step the case repeats (for example a relaunch after a provider exit) may also scale from the time the case took to reach that repeat, keeping its existing deadline as the floor. A performance budget whose workload is mostly unavoidable file-system round trips may likewise allow twice the median of three runs of the same reads and plain unsynced writes on that machine, timed without the production writer under test and keeping its fixed value as the floor, so a durable sync per file still fails. CI reruns each failed case once in a fresh process; a case passes only if that retry passes, the retried names stay in the log, and budgets and assertions are unchanged. A case that fails and then passes on retry keeps the job green but stays visible as possible evidence of a race or intermittent bug: `scripts/run_native_tests.py` ends the log with a marked block listing each such case and its first-attempt failure line, adds a warning annotation per case and a job summary section under GitHub Actions, and with `--flaky-report PATH` writes the list as JSON, which CI uploads as a `flaky-native-tests-*` artifact only when a case flaked; quarantined cases are reported the same way with their issue. The connected handler programs (`ctest --repeat until-pass:2`) have the same one-retry tolerance without this report. The frontend performance suite (`npm run test:performance`) follows the same rule: when `CI` is set, Vitest retries a failed test once in the same worker, with budgets unchanged; the default reporter does not name a test that passed on retry. This tolerance applies only to shared CI runners, not local or acceptance runs. Cases listed with their tracking issue in `tests/ci_quarantine.txt` still run there, but a failure after retry is reported as quarantined instead of failing CI; remove the line when the issue is fixed. The CI documentation job also runs `scripts/check_docs.py`, the launcher cleanup check in `Mobile/Checks/start_desktop_cleanup.py` and the OpenCode V2 permission-plugin check; on macOS and Linux, CTest runs the three Computer Use stub-compile checks in `tests/`. The macOS test job configures with `-DUAM_BUILD_CONNECTED_HANDLER_TESTS=ON`, so it also builds the connected chat, goal and remote-refresh handler programs and runs them in a separate step, where a failed program gets one fresh retry; Windows CI does not build them. The build-flag leak gate (`.github/workflows/build-flag-leaks.yml`) checks every flag profile: its UI rows run on each relevant pull request, and its 38 native rows (19 profiles on macOS and Windows) are full application builds that run on relevant pushes to the V5 integration branch, release candidate tags, the weekly schedule, manual runs or pull requests with the `build-flags` label, so a profile that excludes a provider compiles and links without it. Scripts that need a running or packaged app, a paired token, Playwright or a cross-compiler remain manual. Record command, revision, result and limitations; distinguish reproduced baseline failures from new regressions, and never call a failing full gate passed because focused cases succeeded. Builds, tests and visual checks do not constitute user sign-off.

Every native test program verifies the state push caches. `tests/test_harness.h` turns on a mode in which each state push is followed by a full recomputation of the values pushes reuse by revision stamp or generation (loaded transcript digests, a live session's serialized tool calls, and the model catalogue slice with each scope's fingerprint); a difference is a write that bypassed its stamp, or a catalogue input missing from `CatalogInputs`, and would have left the interface stale. The core runner fails the case that caused it, and every test program exits with a failure if its total at exit is not the number cases provoked on purpose (`uam_test::g_expected_state_cache_divergences`). A case that counts or times a push's own work declares `WithoutStateCacheVerification`. Do not weaken or disable this check to pass a case: a divergence means production would show old content for about three seconds and log `[desync]`. The stamp rules are in the [transport reference](../reference/architecture/react-cef-transport.md#state-push-cost).
