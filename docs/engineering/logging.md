# Logging

Log events that help explain startup, provider/helper lifecycle, failed operations, permission/recovery decisions and meaningful state transitions. Include bounded diagnostic context such as operation/request identity, provider, host, outcome and elapsed time when useful; distinguish an error from a recoverable warning or expected lifecycle event in the message. Report one useful cause and its consequence rather than duplicating the same failure at every layer. Aggregate or rate-limit recurring failures, and keep ordinary rendering, polling, countdown ticks, token chunks and repeated unchanged status out of normal logs.

Do not log credentials, authorization headers, environment dumps, raw prompts/replies, file contents, skill/memory bodies, voice recordings, screenshots or unrestricted tool/protocol payloads. Paths, CLI arguments and provider error text can contain private information: minimize and sanitize before writing. Detailed temporary diagnostics need explicit scope, redaction and removal or an opt-in path; the logger's length limit does not sanitize secrets. A user-facing failure belongs in the shared notification/inline state too, not only a developer log.

Use the [existing diagnostic writer](../../src/common/utils/diagnostic_log.h), which bounds entries, queues writes and rotates files; avoid new independent log files or synchronous disk writes on the UI thread. Runtime diagnostics are not data authority, audit acceptance or durable delivery receipts. Keep development commands/results in `.UAM/AINotes/`, and factual implementation and acceptance disposition in the tracked V5 log.
