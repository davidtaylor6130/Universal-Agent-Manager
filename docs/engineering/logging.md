# Logging

Log events that help explain startup, provider/helper lifecycle, failed operations, permission/recovery decisions and meaningful state transitions. Include bounded diagnostic context such as operation/request identity, provider, host, outcome and elapsed time when useful; distinguish an error from a recoverable warning or expected lifecycle event in the message. Report one useful cause and its consequence rather than duplicating the same failure at every layer. Aggregate or rate-limit recurring failures, and keep ordinary rendering, polling, countdown ticks, token chunks and repeated unchanged status out of normal logs.

Do not log credentials, authorization headers, environment dumps, raw prompts/replies, file contents, skill/memory bodies, voice recordings, screenshots or unrestricted tool/protocol payloads. Paths, CLI arguments and provider error text can contain private information: minimize and sanitize before writing. Values the user typed into a [secret card](../chat/secrets.md) are scrubbed from every diagnostic line as a last safety net; that does not permit logging secret-bearing payloads. Detailed temporary diagnostics need explicit scope, redaction and removal or an opt-in path; the logger's length limit does not sanitize secrets. A user-facing failure belongs in the shared notification/inline state too, not only a developer log.

Use the [existing diagnostic writer](../../src/common/utils/diagnostic_log.h), which bounds entries, queues writes and rotates files; avoid new independent log files or synchronous disk writes on the UI thread. It owns two files in the data root, together at most about 11 MiB. `uam.log` holds ordinary diagnostics up to 5 MiB with one `.1` backup (whose age expiry is the storage retention setting), which on a busy install is only a few days. `uam-audit.log` holds storage and deletion audit lines written with `WriteAudit` (which also copies them into `uam.log`): lines older than 90 days are dropped when it opens and daily, the oldest go first past 1 MiB (if the file cannot be rewritten it keeps growing and the rewrite is retried hourly), audit copies that a stalled writer could not queue are counted in it, and each app run writes an opened and a closed marker. Use the audit channel only for rare records a later investigation must find, such as a chat primary's removal, never for routine traffic. Report a recurring timing as a periodic summary rather than a line per occurrence: `PollTick` writes one line with p50/p95/max for each stage for each minute that had a tick of 50 ms or more (and the partial minute at a clean quit), and a single tick only from 250 ms, at most every five seconds. A model-discovery session's routine protocol traffic (sent requests, successful results, launch and clean idle exit) stays in its in-memory diagnostics; its failures still reach the log. A failed chat save writes one line per failure streak, and the forced barriers at quit at most one more per chat, naming the chat ID and its cause: `Chat save refused before writing` for a deliberate check (a held or unreadable queue journal, content UAM cannot store, an ownership or identity check) and `Chat save failed` for anything else, with a short reason code or the atomic writer's step and OS error text, never a path. Runtime diagnostics are not data authority, audit acceptance or durable delivery receipts. Keep development commands/results in `.UAM/AINotes/`, and factual implementation and acceptance disposition on the GitHub PR or issue.
