# Compute Pools

Compute Pools limit how many chats may use a provider or model at the same time, for hosts that can only serve a few turns at once. Per-computer limits are separate: see [Host limits](#host-limits). With no pools configured, nothing changes: every turn is sent as soon as it is ready. A pool has a name, a limit from 1 to 64 and one or more provider-and-model members; a member with All models covers every model of that provider. Pools are global and cover every computer a chat runs on.

A turn is checked when UAM is about to send it, after its provider is ready, and it counts for every pool it matches: chat turns, sub-agents, goal iterations and automation chats alike. A chat on its provider's default model matches a model-specific member only once the provider has reported that model, and some providers never report one, so a pool meant to cover default-model chats needs All models. It runs only when every matching pool has room; otherwise it stays in its chat with the visible status “Waiting for <pool> slot (n/m in use)”, where n counts slots running or promised to older waiters, and starts by itself when a slot frees. A turn never takes a slot an older waiter could claim, so a turn in overlapping pools can wait behind an older one even while its own pool has room, and a chat's queued input stays in order behind its held turn. A held turn whose provider process restarts rejoins the line at the back. Stop removes a held turn from the line without contacting its provider, and the status disappears as soon as the turn is admitted.

Slots are counted from running turns each time, so a turn that completes, fails or is cancelled, a provider process that dies and a deleted chat all free their slot with no separate release. An unstopped turn on a remote computer keeps its slot while UAM reconnects to it, because it is still running there; pressing Stop frees it. A chat waiting in `agent_wait` for its own child does not hold a slot, otherwise a pool shared by parent and child could never progress; the parent can briefly take the count over the limit when its child is still running and it resumes. A turn waiting for a permission answer keeps its slot. Time spent held does not count against a turn's inactivity limit or a sub-agent's 30-minute run limit.

Steer needs a turn that has reached the provider, so a held turn refuses Steer and the composer sends a new message to the queue instead. A steer that interrupts a running turn starts a new turn, which waits in line like any other. Managed sub-agent results delivered to a parent, manual compaction, native mid-turn steering and the first turn of a Codex native goal are not held, because they continue work already running, and they take no place in the line. A native steer joins a turn that already holds its slot; the others count towards use, even when that takes a pool over its limit.

The Compute Pools page lists each pool with its members and its current in-use and waiting counts. Machine-wide pools and a per-chat pool picker are deferred. A wait on this computer is not restored across an app restart: the held message, with any input queued behind it, stays in its chat unsent for Retry, as any undelivered message does; nothing sends it by itself, and Retry checks it again like a new turn, so it is sent once. A held turn of an SSH chat is kept as prepared remote input instead and, like any undelivered remote prompt, is checked at the gate again and sent by itself after the restart. David [kept this behaviour](../documentation-review.md#compute-pool-wait-after-a-restart) on 2026-11-23; automatic rejoin after a restart is a later slice. CLI View input is typed straight into the provider's terminal and is not held.

## Host limits

Every process start asks host admission for its computer first, so automatic routing and explicit choices never overload a machine. Work has three classes in priority order: a user's own chat turns and CLI Views; agent work (sub-agents, goal iterations, automation chats); and background work (model discovery, memory workers, history import, version and repository checks). Each computer has a slot limit shared by user turns and agents and a separate small background budget (default 2, at most 4). This computer's limit defaults to its processor count minus two and is set here; it is not an automatic routing candidate. A remote computer uses its routing slot count, or the remote default (8) when routing has none. Pools still apply after host admission.

A chat's provider process is admitted before it starts, for any launch (a queued turn, a direct send, a retry, a model list), and holds its slot for up to 30 seconds until its turn is admitted again before its prompt is sent; explicit and automatic chats alike; an automatic chat that cannot move waits in its computer's line like an explicit one. A turn that a compute pool holds keeps no host slot or place, and asks the host again once the pool admits it. A held start or turn shows one line in its chat, for example “Waiting for host A (8/8)”, and a user's own turn also offers Run anyway, which starts that one turn over the limit; Stop withdraws it. Agents never get Run anyway. Waiters are served first come, first served per computer and class, user turns before agents, and an agent that has waited two minutes is served like a user turn so it cannot starve. A waiter that stops asking holds no place after five seconds and loses its ticket after a minute. A CLI View takes a slot while it is open; at the limit its launch waits with the same line and Run anyway, asks again about once a second (as does a launch routing holds), and starts by itself when a slot frees. A provider process kept idle between turns takes none.

Health is Ready, Degraded, Overloaded or Unreachable. Over the soft limit (CPU above 70 % or free memory below 15 %) a computer is Degraded and background work waits. Over the hard limit (CPU above 90 % for 10 seconds, or free memory below 10 %) it is Overloaded: new agent and background work waits, user turns wait with Run anyway, and automatic routing places no new work there. Each state is held for a back-off of 10 seconds after its last over-limit reading, doubling up to five minutes when it returns within five minutes; an Overloaded computer that stays only over the soft limit falls back to Degraded when its hard back-off ends. Health is rechecked about once a second. A computer whose health check failed is Unreachable: agent and background work waits for it. Unknown load (no reading yet, an older helper, a stale or failed read) uses the slot counts only and never counts as idle. The thresholds and limits are set in the Host limits section, which also lists each computer's running, background and waiting counts and its health.

Implementation notes: the live load reading comes from the host load signal (separate work, `v5/feat-routing-load-signal`); until it is connected every load is unknown, only slots and budgets apply, and the page says so under the load fields. Background lanes keep their own existing caps as upper bounds; a memory scan held for one computer does not hold scans for others. A user-started history discovery or version recheck and the launch-time checkout check of a routed chat belong to the user's action and are not held as background work. Host admission waits are not restored after a restart.
