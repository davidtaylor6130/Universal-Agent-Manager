# Storage settings

## Application data folder

Settings should show the current application data folder and offer an explicit local-folder choice with a guarded transition on restart. An externally supplied `UAM_DATA_DIR` takes precedence; without an explicit folder choice, the existing OS app-data, temporary and final relative-data fallback order stays unchanged. The initial supported transition requires a separate empty destination, with no merge or overwrite. Selection, arming and stopped activation must reject destinations equal to, inside or above the original bootstrap/default root, any historical source or a retained passive copy, using directory identity and revalidation before transfer writes. Quiesce writers and retain exclusive ownership of both roots before publishing a verified destination and restart selection; preserve the source for rollback on failure. Chats, summary overlays, queued-input journals, memory and recovery/ownership receipts remain governed by their owning services, and external resource references do not authorize copying their targets or replaying retained work.

Settings → Storage distinguishes the current folder from a saved pending choice, offers the native directory picker and permits cancellation of a confirmed pending choice. The original external override is captured before UAM exports its effective root. Folder-choice publication has its own native revision and acknowledgement; an unconfirmed choice stays visible across Settings navigation, blocks further changes and requires observation of its specific native action before reconciliation. Keyboard search must respect the same busy and confirmation guards as other Settings exits; status and error text remain legible without relying on colour. A separate restart confirmation is connected to native readiness; unconfirmed restart requests remain held through Settings navigation until the application reopens. Restart does not apply an unverified pending choice.

**Implementation: Partial.** Verified only with disposable fixtures: connected desktop selection, durable pending preference, stopped transaction, source/destination locks, independent-writer freezes and acknowledged receipts, supervised restart activation and passive rollback are implemented in source and covered by isolated fixtures. Production root-lock acquisition never rewrites existing marker contents; profile IO handles must match their retained directory witnesses, and restored-source startup, arming and independent writers require the exact acknowledged receipt for the final transaction. A proven first plain cancellation alone may remain receipt-free. Copying must preserve exact owner-significant file modification times, including summary-overlay freshness and queue-journal base revisions, or refuse activation. Unsettled remote delivery and retained interaction responses block transfer even when process flags are false; root and bootstrap primary/acknowledgement validation retains both file and parent-directory witnesses through admission. Supported legacy pending-response fields follow the owning decoder's fallback precedence and remain held when unresolved. Any queued managed-turn marker, including null or malformed identity, remains unresolved until its owner settles it in the source. Durable root fences precede staging publication, and cancelling an armed follow-up preserves consistent current-root writer authority without admitting retained roots. Invalid or duplicate-key structured records refuse before copying so parser precedence cannot change saved authority. Interrupted publication or unknown/malformed acknowledgement remains held, and unsupported internal references or unsettled execution ownership refuse transfer. The original profile stays retained; subsequent choices retain every earlier source owner. Live restart-to-apply remains disabled until native/CEF/platform verification is adequate. Desktop/Windows runtime, scoped Claude review and user acceptance remain open; disposable component rendering does not establish installed-app acceptance. See the [handoff contract](../reference/data-folder-transition.md).

## Storage Cleanup

Storage Cleanup configures independent retention for managed worktrees, backup logs and HTTP cache. Worktree cleanup removes eligible old working directories only after ownership/safety checks while retaining branches and commits; it must preserve active or unresolved work. Backup-log retention keeps the current log and uses zero to retain backups without age expiry. Periodic HTTP cache clearing preserves profiles/sign-in data, starts its interval without an immediate purge and can be disabled. Worktree and log/cache groups retain their own Save/Discard state and failed-save drafts; neither is permission to delete chats, provider histories or user-owned workspace files.
