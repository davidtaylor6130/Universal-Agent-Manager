# Remote Hosts settings

Remote Hosts configures execution environments using existing SSH aliases and a compatible installed UAM helper. Saved installation/startup preferences are distinct from observed connection, version and startup registration state. Installation and updates must respect active provider work and show failed or uncertain activation honestly; selecting a host does not authorize silently replaying a prompt or changing a chat’s workspace.

The page lists configured hosts as identity and status rows. Each host opens its own sub-page with its status, helper actions and host options, Back to hosts returns focus to that host's Open button (or to Add a host once it is removed), and leaving with unsaved host options asks first. These follow the [settings list agreement](../ui/settings.md#copy-and-lists).

[SSH execution](../remote-environments/ssh.md) · [Routing](../remote-environments/routing.md).

Host options separately configure start-at-login, supported CLI updates with elevated privileges and host-specific instructions (inline guidance or the legacy instruction file). These settings must not elevate ordinary chat execution. Preview the helper install location/command, retain active-work/version guards and distinguish removing the saved host from uninstalling remote helper files. Helper setup runs on its own native worker so other app requests keep completing; cancelling the setup request or closing UAM stops its SSH steps promptly. A rollback already under way, and the bounded helper handshake, still finish first; an interrupted install keeps its saved fence until setup is retried to reconcile it. Once an install passes its busy-work checks, it stops that host's background history scan at its current export and the scan restarts from the beginning afterwards; selected imports and running chats still refuse the install without touching the scan. A chat whose provider process is only kept alive between turns does not refuse the install: under the same rule as the idle shutdown, without its delay, the install stops that process through the confirmed remote stop and waits for it; and a process still reattaching with no turn is waited for until it is idle or gone. Saved process authority that UAM cannot reach, with no turn, stop, pending input or pending continuation (for example an old chat whose reattach keeps failing), does not refuse it either. A pending reattach is first retried once during the wait, because a process that only lost its connection could not be reached once a newer helper is committed; only if that attempt fails is the record set aside: its saved fields are kept, a reattach already retrying waits only while this computer holds that host's helper install (or a startup-option save) and then resumes, and a chat with no runtime settles its saved fields at its next launch or restart. A turn, queued or unsent input, a goal continuation waiting to run, a usage-limit continuation that is waiting, claimed or belongs to a live process, background tasks, input still being saved, routed, prepared or delegated, a restart, a stop that is in flight or was never confirmed (including a saved stop cleanup), a terminal, a CLI update, an import or a Git operation still refuses the install; the refusal names the chat or work and how to clear it, and ends with its fixed reason code. Only a failed first SSH contact (the platform probe), or a request that never got an answer, suggests checking the SSH connection; a connection lost later in setup reports its own error without that hint.

Host instructions apply only to chats on that SSH host, never to local chats or another host. Saved inline guidance replaces the legacy file: once inline guidance is saved, even empty, UAM does not read the file. A missing or unreadable legacy file stops the chat turn or provider launch with an error instead of falling back to other instructions. In structured Chat, user prompts UAM sends from the composer or queue start with the host instructions between `--- BEGIN HOST INSTRUCTIONS ---` and `--- END HOST INSTRUCTIONS ---`, then, on a turn's first prompt with memory on, recalled remote project memories, then the message; this does not depend on Central Setup. Chat and CLI View launch instructions also carry them when [Central Setup](central-setup/central-setup.md) applies to the launch: it is on globally or switched on for that provider on that host, and not switched off there. While Central Setup is off globally, a launch to which UAM attaches its own tool servers, such as UAM tools in Claude chats, also carries them, without central text or files and ignoring the per-provider switches; in Antigravity Chat, tool servers alone add no launch instructions. They are combined in this order: central instruction text and files in their saved order (only when Central Setup applies), the selected agent's instructions, the agent and skill index, inline host guidance, the workspace root's AGENTS.md, then the legacy host file; for Claude, any existing appended system prompt such as provider-handoff context follows. Codex loads the workspace AGENTS.md itself, so UAM leaves it out of the Codex launch file. UAM sets no precedence beyond this order; each provider weighs the combined text and discovers nested project instruction files by its own rules.

Implementation note: a structured chat whose launch instructions include host instructions receives them twice, at launch and at the start of each prompt. CLI View receives host instructions only through launch instructions, so a CLI View launch without them gets none. Claude Code prompts with images, mid-turn steers, managed agent-result prompts and Codex native goal turns are sent without the prompt prefix.
