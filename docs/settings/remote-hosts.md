# Remote Hosts settings

Remote Hosts configures execution environments using existing SSH aliases and a compatible installed UAM helper. Saved installation/startup preferences are distinct from observed connection, version and startup registration state. Installation and updates must respect active provider work and show failed or uncertain activation honestly; selecting a host does not authorize silently replaying a prompt or changing a chat’s workspace.

The page lists configured hosts as identity and status rows. Each host opens its own sub-page with its status, helper actions and host options, Back to hosts returns focus to that host's Open button (or to Add a host once it is removed), and leaving with unsaved host options asks first. These follow the [settings list agreement](../ui/settings.md#copy-and-lists).

[SSH execution](../remote-environments/ssh.md) · [Routing](../remote-environments/routing.md).

Host options separately configure start-at-login, supported CLI updates with elevated privileges and host-specific instructions (inline guidance or the legacy instruction file). These settings must not elevate ordinary chat execution. Preview the helper install location/command, retain active-work/version guards and distinguish removing the saved host from uninstalling remote helper files. Helper setup runs on its own native worker so other app requests keep completing; cancelling the setup request or closing UAM stops its SSH steps promptly. A rollback already under way, and the bounded helper handshake, still finish first; an interrupted install keeps its saved fence until setup is retried to reconcile it. Once an install passes its busy-work checks, it stops that host's background history scan at its current export and the scan restarts from the beginning afterwards; selected imports and running chats still refuse the install without touching the scan. A chat whose provider process is only kept alive between turns does not refuse the install: under the same rule as the idle shutdown, without its delay, the install stops that process through the confirmed remote stop and waits for it; and a process still reattaching with no turn is waited for until it is idle or gone. Saved process authority that UAM cannot reach, with no turn, stop, pending input or pending continuation (for example an old chat whose reattach keeps failing), does not refuse it either. A pending reattach is first retried once during the wait, because a process that only lost its connection could not be reached once a newer helper is committed; only if that attempt fails is the record set aside: its saved fields are kept, a reattach already retrying waits only while this computer holds that host's helper install (or a startup-option save) and then resumes, and a chat with no runtime settles its saved fields at its next launch or restart. A turn, queued or unsent input, a goal continuation waiting to run, a usage-limit continuation that is waiting, claimed or belongs to a live process, background tasks, input still being saved, routed, prepared or delegated, a restart, a stop that is in flight or was never confirmed (including a saved stop cleanup), a terminal, a CLI update, an import or a Git operation still refuses the install (a Git status, diff or commit-message read only while it runs, a commit and worktree preparation from the moment they are queued); a queued Git read that would start during the install is refused with a retry message instead of running against the helper being replaced; the refusal names the chat or work and how to clear it, and ends with its fixed reason code. Only a failed first SSH contact (the platform probe), or a request that never got an answer, suggests checking the SSH connection; a connection lost later in setup reports its own error without that hint.

Host instructions apply only to chats on that SSH host, never to local chats or another host. Saved inline guidance replaces the legacy file: once inline guidance is saved, even empty, UAM does not read the file. A missing or unreadable legacy file stops the chat turn or provider launch with an error instead of falling back to other instructions. Every Chat and CLI View launch on the host carries the host instructions as launch instructions, whether or not [Central Setup](central-setup/central-setup.md) applies, and UAM no longer adds them to every prompt. Gemini Chat is the exception: Gemini loads launch instructions only in a folder it trusts and never asks in Chat, so UAM instead puts the host instructions between `--- BEGIN HOST INSTRUCTIONS ---` and `--- END HOST INSTRUCTIONS ---` at the start of the next prompt whenever that native session has not yet received the current text, so a new session gets them once, a resumed one is not sent them again, and a saved change reaches it once. Launch instructions are provider setup rather than conversation messages, so a native session has them once: resuming or reconnecting does not repeat them, and a new launch after a provider switch or fresh session carries them again. Everything sent to that running provider has them in force without further delivery, including prompts with images, mid-turn steers, agent results and goal turns. UAM refuses to save changed host instructions while the host has running work, so a change reaches a chat at its next launch; a legacy file edited directly on the host is likewise read at the next launch. The helper keeps this launch setup in its own private folder on the host, outside the workspace, so a workspace reached through a symbolic link or one this account cannot write to still launches with the instructions. With Central Setup off and no UAM tool servers attached, the instructions never appear in the workspace. When Central Setup applies or UAM tool servers attach, setup stays in the workspace's `.UAM` folder when it can, so agents can read its files there, and moves to the helper's folder only when the workspace cannot hold it. A saved conversation carried into CLI View after a provider switch likewise moves to the helper's folder when the workspace cannot hold it.

On a turn's first prompt with memory on, recalled remote project memories come before the message; this does not depend on Central Setup. Launch instructions are combined in this order: central instruction text and files in their saved order (only when Central Setup applies, globally or switched on for that provider on that host, and not switched off there), the selected agent's instructions, the agent and skill index, inline host guidance, the workspace root's AGENTS.md, then the legacy host file; for Claude, any existing appended system prompt such as provider-handoff context follows. While Central Setup is off globally, a launch to which UAM attaches its own tool servers, such as UAM tools in Claude chats, also uses this order, without central text or files and ignoring the per-provider switches; in Antigravity Chat, tool servers alone add no launch instructions. Without Central Setup or that tool-server case, the launch carries only the inline guidance or the legacy host file, and a helper too old to support that must be updated first. Codex loads the workspace AGENTS.md itself, so UAM leaves it out of the Codex launch file; Codex CLI View passes launch instructions on its command line, so instructions beyond the operating system's limit stop that launch with an error, and UAM sets Codex's developer instructions without merging any value from the host's own Codex configuration. UAM sets no precedence beyond this order; each provider weighs the combined text and discovers nested project instruction files by its own rules.
