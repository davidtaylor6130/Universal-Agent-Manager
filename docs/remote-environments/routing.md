# Execution routing

Routing chooses where work executes while retaining its provider, workspace and authored request. Automatic rules must respect availability and configured confirmation, and explicit choices must remain understandable rather than silently moving work after a failure. Changes to host identity or material configuration require revalidation. A disconnected or busy environment must not cause duplicate provider work or an unauthorized local fallback.

## Waiting and recovery

A chat that routing cannot start waits with its reason shown; no wait is permanent, and none needs the chat recreated. Once assigned, an automatic chat stays on its computer: a later configuration change never moves it. A helper update does not change a computer's identity and needs no new confirmation. When the computer's connection, instructions, MCP servers, extra flags or provider defaults change, the provider must be confirmed again in Routing settings; an assigned chat with no turn, delivery or pending answer then adopts the confirmed configuration at its next admission and continues by itself. A chat with work still running keeps its connection: it adopts changed provider settings, which apply at the next launch, but a changed connection waits until the turn is stopped, because the changed connection may be another machine.

A failed health check on the assigned computer does not stop an assigned chat from trying it, as an explicit SSH chat may; new work is still sent only to a computer last seen Ready. Routing starts the provider version check it depends on for each enabled computer and repeats a failed check with a growing delay of up to five minutes. A reservation left over from a quit or crash is settled by asking the computer whether the chat's provider process still exists: only the helper's own answer that it does not releases the reservation, an unreachable computer or an existing process keeps it, and Release reservation in the chat remains available.
Repository matching reads each computer on its own connection with its own 15-second budget, in parallel, and a read that times out keeps the last identity read for that folder: a timeout is not evidence that a checkout changed.

Automatic routing requires enabled candidate computers, capacity, current provider sign-in/configuration confirmation and valid local-to-remote folder/repository mappings. An explicit user destination is separate from the automatic candidate policy; changed connections/configurations invalidate old confirmations. No available route must remain an honest blocked/choice state rather than an unauthorized fallback.

The SSH routing page (and the New chat routing dialog) lists each computer as one collapsible row with its status box and Use this computer switch; expanding it shows concurrent sessions and provider sign-in confirmations. Folders are grouped by local workspace, with one row per computer the workspace is mapped to: the remote path, a Same repository (automatic repository match) or Chosen (manual override, which wins) tag, and any problem with that mapping inline (folder no longer exists, folder on another computer, workspace folder moved). These row problems use the same checks as the page validation that blocks Save, and every mapping that blocks Save has a row: a mapping whose local workspace no longer exists (deleted, or no longer a local workspace with a path) is its own problem group named from its saved path, offering only Remove, and a policy for a computer that is no longer a registered SSH computer is a Removed computer row in Computers (its internal ID shown muted) whose Remove drops that computer's routing from the draft. A broken chosen folder that also has a repository match offers Use repository match rather than Remove mapping; removing a chosen folder returns the workspace to repository matching, since Save replaces the whole list. Workspaces with a problem come first and start open, as do the first two groups; workspaces without a mapping share one Not mapped group, and the "N of M workspaces mapped" count includes only workspaces with at least one working mapping. Map folder… opens a chooser built like Import chats: pick a computer, filter, tick workspaces and choose a registered remote folder for each, then Map N. A row's Map… or Choose… opens it with that workspace and computer preselected; Choose… on a broken row replaces that workspace's mappings on the computer in place, keeping its position. Switching computers in the chooser carries ticks that have no remote folder yet over to the new computer, dropping only those the new computer would hide (already mapped there), so hidden picks never block Map N; ticks with a folder stay on their computer and the bar reads "N selected, +M on other computers". Choose… keeps a still-valid chosen folder preselected even when the row shows a stale-duplicate problem, so Map 1 only replaces the duplicate. Mapping a workspace to a computer that has no routing yet adds that computer with Use this computer off, so it routes only once that switch is turned on. Mapping only stages changes in the unsaved routing draft, so Save routing, Discard, validation and the unsaved-changes guard are unchanged. In the New chat routing dialog the chooser is an in-place step of the same panel: the routing list stays mounted but hidden, so expanded rows keep their state, and Escape returns to it. Escape inside an open remote-folder or computer menu closes only that menu, in both the dialog step and the Settings chooser. The chooser lists only folders already registered on that computer.
