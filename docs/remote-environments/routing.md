# Execution routing

Routing chooses where work executes while retaining its provider, workspace and authored request. Automatic rules must respect availability and configured confirmation, and explicit choices must remain understandable rather than silently moving work after a failure. Changes to host identity or material configuration require revalidation. A disconnected or busy environment must not cause duplicate provider work or an unauthorized local fallback.

## Waiting and recovery

A chat that routing cannot start waits with its reason shown. Most waits end by themselves or after one named step; the ones that can last until the user acts are listed at the end of this section. Once assigned, an automatic chat stays on its computer: a later configuration change never moves it.

A computer's connection is its SSH alias, platform, architecture and helper folder. Everything a launch there is given (MCP servers, extra flags, provider defaults and the host's instructions) is provider configuration. A helper update changes neither and needs no new confirmation. When either changes, the provider must be confirmed again in Routing settings. An assigned chat then adopts the confirmed configuration at its next admission and continues by itself, with two limits. A chat that will launch (a pending restart, queued input, a terminal being prepared) adopts nothing unconfirmed; only a chat reattaching to its own running turn, which launches nothing, follows changed provider settings without confirmation. A changed connection may be another machine, so it is adopted only when nothing of the chat is left on the old one: a running turn, or a provider process kept between turns, holds the chat on the old connection until the turn is stopped and the process has closed, or the previous SSH settings are restored.

Identities saved by earlier versions are carried forward and saved at the first start after the upgrade, without asking, when the configuration they name is unchanged; a configuration that really changed asks for confirmation as usual. An earlier identity whose helper was updated before that first start cannot be proven unchanged and cannot say whether the connection changed: such a chat asks only for the provider to be confirmed in Routing settings, a kept provider process does not hold it (that process belonged to the replaced helper), and a turn still running must be stopped first.

A failed health check on the assigned computer does not stop an assigned chat from trying it, as an explicit SSH chat may; new work is still sent only to a computer last seen Ready. Routing starts the provider version check it depends on for each enabled computer, in the background and without status text, and repeats a check that could not finish with a growing delay of up to five minutes; a check the user starts meanwhile runs right after it. A finished check that found no usable CLI is not repeated until the user updates or rechecks it.

A reservation left over from a quit or crash is settled by asking the computer whether the chat's provider process still exists. Automatic release is deliberately conservative: it happens only when the helper and connection are the ones the reservation was made on, and that helper itself answers that the process does not exist. The helper version is saved with the reservation, so a helper updated at any time since, even several restarts ago, ends automatic release, as does a reservation saved by an earlier version, which has no helper version. An unreachable computer, an existing process, a helper updated since, or an edited connection all keep the reservation, and Release reservation in the chat remains the way out. A helper that restarted cannot see a provider process that outlived it, so its answer is not proof the process is gone; the host-side check for such processes is separate work.

Repository matching reads each computer on its own connection with its own 15-second budget, in parallel. For choosing a computer, a read that could not finish keeps the identity last read for that folder for at most ten minutes. The launch check never relies on a kept identity: it reads both checkouts afresh, and a read that cannot finish stops the launch with "The assigned checkout could not be read before launch", after which sending again reads again. After a chat adopts a changed connection, the launch check looks the checkouts up again instead of comparing against the old connection.

Waits that last until the user acts: a reservation whose computer stays unreachable or still reports the process (Release reservation); a chat held on a previous connection by a kept provider process that can no longer be reached (restore the previous SSH settings); an assigned folder that was deleted or moved (restore it); and a changed configuration awaiting confirmation (Routing settings).

Automatic routing requires enabled candidate computers, capacity, current provider sign-in/configuration confirmation and valid local-to-remote folder/repository mappings. An explicit user destination is separate from the automatic candidate policy; changed connections/configurations invalidate old confirmations. No available route must remain an honest blocked/choice state rather than an unauthorized fallback.

The SSH routing page (and the New chat routing dialog) lists each computer as one collapsible row with its status box and Use this computer switch; expanding it shows concurrent sessions and provider sign-in confirmations. Folders and Map folder… stay available while repository matches are checked: a working row says the check is running, and one polite live region that stays mounted announces the check and its failure as its text changes; no check is requested while no local workspace has a path to match, so none holds a shared VCS-context slot for nothing; unmatched workspaces read "Checking repository…" rather than "No repository", and the mapped count waits for the result. A check with no answer after 30 seconds, or a failed check, is reported as unavailable with Retry, and manual mapping continues; the wait does not cancel the native read, so Retry waits on a check still running rather than starting another, and its answer still applies. Folders are grouped by local workspace, with one row per computer the workspace is mapped to: the remote path, a Same repository (automatic repository match) or Chosen (manual override, which wins) tag, and any problem with that mapping inline (folder no longer exists, folder on another computer, workspace folder moved). These row problems use the same checks as the page validation that blocks Save, and every mapping that blocks Save has a row: a mapping whose local workspace no longer exists (deleted, or no longer a local workspace with a path) is its own problem group named from its saved path, offering only Remove, and a policy for a computer that is no longer a registered SSH computer is a Removed computer row in Computers (its internal ID shown muted) whose Remove drops that computer's routing from the draft. A broken chosen folder that also has a repository match offers Use repository match rather than Remove mapping; removing a chosen folder returns the workspace to repository matching, since Save replaces the whole list. Workspaces with a problem come first and start open, as do the first two groups, decided once the repository check settles so late matches do not leave a group open or closed for the wrong reason, and a group the user opens or closes keeps that choice; workspaces without a mapping share one Not mapped group, and the "N of M workspaces mapped" count includes only workspaces with at least one working mapping. Map folder… opens a chooser built like Import chats: pick a computer, filter, tick workspaces and choose a registered remote folder for each, then Map N. A row's Map… or Choose… opens it with that workspace and computer preselected; Choose… on a broken row replaces that workspace's mappings on the computer in place, keeping its position. Switching computers in the chooser carries ticks that have no remote folder yet over to the new computer, dropping only those the new computer would hide (already mapped there), so hidden picks never block Map N; ticks with a folder stay on their computer and the bar reads "N selected, +M on other computers". Choose… keeps a still-valid chosen folder preselected even when the row shows a stale-duplicate problem, so Map 1 only replaces the duplicate. Mapping a workspace to a computer that has no routing yet adds that computer with Use this computer off, so it routes only once that switch is turned on. Mapping only stages changes in the unsaved routing draft, so Save routing, Discard, validation and the unsaved-changes guard are unchanged. In the New chat routing dialog the chooser is an in-place step of the same panel: the routing list stays mounted but hidden, so expanded rows keep their state, and Escape returns to it. Escape inside an open remote-folder or computer menu closes only that menu, in both the dialog step and the Settings chooser. The chooser lists only folders already registered on that computer.
