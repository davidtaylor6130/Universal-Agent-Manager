# SSH execution

SSH execution runs providers and workers through a verified UAM helper on a configured OpenSSH alias, keeping authentication and host verification with OpenSSH. Reconnect must recover the correct process and output without replaying delivered prompts. Instructions, skills, attachments and MCP configuration must be usable on that computer. Helper updates must respect active work and preserve recovery, and a kept activation leaves one current helper per host: older idle helpers stop and lose their start-at-login entries, on Linux and Windows alike, while a helper still running work is kept for a later activation to retire. A helper is busy only while it owns a process that has not exited or holds an exit or output a client has not yet received; a finished, delivered record does not keep it alive. Helpers already installed by older versions count finished records as busy and cannot be changed, so one that refuses to stop may be terminated, identified by its exact executable path inside UAM's own runner folder, only when the operating system's process table shows it has no live child and no terminal or bridge from that executable is running. Delivered output does not stay on disk for the length of a chat: the helper reclaims it progressively, never touching output a client has not acknowledged, and a read from before the reclaimed point fails rather than returning other bytes. Output folders left by a helper that was killed or lost to a reboot are removed at the next helper start when no running helper holds them, and a retired helper's folders are removed at activation; files still in use stay for a later attempt. An unattended helper must idle near zero CPU. An idle provider process kept alive between turns, or saved process authority UAM cannot reach, does not block a helper update; see [Remote hosts](../settings/remote-hosts.md). Local editor actions and remote desktop computer use are not implied by SSH support.

The official helper installation transaction must publish the installed binary's SHA-256 sidecar and source manifest under the same owned installation lock as activation. Hash and identity verification must succeed, and the manifest's source fingerprint must match the copied executable, and rollback or interrupted-transaction recovery must restore the prior binary and metadata, including prior absence. A refused or failed helper stop retains recovery files and reports rollback as unfinished. These installed-file facts do not establish the identity of a resident or loaded helper; active-work admission and runtime compatibility checks remain required.

Recovery journals must become authoritative atomically. Windows finite operations must validate their installation nonce while holding a target-side operation lock; guard expiry and successor recovery wait for that operation to finish, and late commands from an expired owner are refused. A successful handshake alone cannot make the host Ready: setup also requires a nonce-bound commit acknowledgement. An unknown commit leaves setup unavailable until guarded retry reconciles it; acknowledged commit with failed backup cleanup may report a warning.

Target-lock acquisition must pause before recovery or mutation until the owning controller durably saves the pending transaction nonce and artifact/target identity. Losing the controller before that acknowledgement leaves the prior transaction untouched; losing it afterward preserves an unavailable installation across reload. Failed mutation with unconfirmed rollback retains this durable fence and its binding rather than restoring a previous Ready claim. Settings reload, successful health probes and ordinary connection retries must preserve that fence; guarded setup is required to settle it. Ordinary transient connection errors remain reconnectable. Every ordinary saved-host client, including workspace validation and memory operations, must enforce installation admission before starting a bridge. Linux synchronous mutation commands retain operation ownership if their guard dies, while detached helpers inherit neither installation lock descriptor. Guard replies identify their operation; a timeout, disconnection or uncorrelated reply invalidates the stream and cannot confirm rollback.

**Implementation: Partial.** Linux x86-64/ARM64 and Windows x86-64 helper routes exist; transactional metadata publication is implemented for Linux and Windows with scoped native and injected filesystem checks passing on macOS; real platform execution acceptance remains pending. macOS remote-helper packaging and various live/provider combinations remain unverified. Commands UAM runs on a remote Windows host use built-in Windows PowerShell 5.1 (`powershell.exe`) and 5.1-compatible scripts; a per-host PowerShell choice is not implemented, and the [Editors](../settings/editors.md) Terminal shell choice applies only to terminal windows opened on a Windows controller. See [architecture](../architecture/execution-hosts.md), [provider checklists](../providers/providers.md#provider-checklists), [open gaps](../documentation-review.md#helper-metadata-publication) and [build flags](../build-flags.md).

**Windows as the SSH controller: Partial.** The Windows core test job runs the session proxy against a private helper service through a stand-in `ssh`: start, attach without starting or replaying a process, missing-session failure, detach and recovery through a new bridge, fragmented native frames, the acknowledged stop outcome through the helper service and through a direct bridge, and provider start in a drive-letter workspace and in a UNC workspace through the machine's administrative share, which hosted CI requires and a developer machine may skip. Drive-letter and UNC workspace strings are also checked in proxy specs and SSH terminal commands, and the MCP control line accepts them on Windows. Not tested from Windows: a live OpenSSH connection to a real host, the SSH arguments and remote bridge command (the stand-in ignores them and the proxy cases use the `linux` route), restart of the app itself (a new proxy stands in for it), the MCP relay end to end, a UNC workspace on another computer, and a provider launched through a `.cmd` shim in any workspace (the proxy cases launch an executable directly). See [issue #349](https://github.com/davidtaylor6130/Universal-Agent-Manager/issues/349).

## Bootstrap failures

Helper setup must distinguish SSH transport, command launch, cancellation, timeout, output-read and unavailable-working-directory failures from unsupported OS or CPU results. Only a successful probe with valid platform output can establish an unsupported target; empty or malformed output is a probe failure. A failed remote shell command can trigger the Windows fallback, while transport and local execution failures stop setup. Public probe errors preserve the failure category and command exit code where available without echoing raw probe output, SSH diagnostics, credentials or private paths.
