# SSH execution

SSH execution runs providers and workers through a verified UAM helper on a configured OpenSSH alias, keeping authentication and host verification with OpenSSH. Reconnect must recover the correct process and output without replaying delivered prompts. Instructions, skills, attachments and MCP configuration must be usable on that computer. Helper updates must respect active work and preserve recovery, and a kept activation leaves one current helper per host: older idle helpers stop and lose their start-at-login entries, on Linux and Windows alike, while a helper still running work is kept for a later activation to retire. A helper is busy only while it owns a process that has not exited, or holds an exit or output that has not reached a client (an exit counts as reached once the helper has written it out); a finished, delivered record does not keep it alive. A helper's refusal to stop is honoured. The only exception is a helper built before this rule, recognised because it does not answer `--stop-contract`: it counts finished records as busy and cannot be changed, so after it actually refuses, it may be terminated, identified by its exact executable path inside UAM's own runner folder, and only when the operating system's process table shows it has no live child and no terminal or bridge from that executable is running. A helper that could not be asked to stop is never terminated. Delivered output does not stay on disk for the length of a chat: the helper reclaims it progressively, never touching output a client has not acknowledged, and a read from before the reclaimed point fails rather than returning other bytes. Output folders left by a helper that was killed or lost to a reboot are removed at the next helper start when their owner lock shows no running helper holds them. At activation on Windows, output folders of retired or dead helper versions are removed only while no other helper that could own them is running; anything uncertain is kept, and files still in use stay for a later attempt. On Linux, output folders a helper left without its owner lock stay in the temporary folder for the system to clear. An unattended helper must idle near zero CPU. An idle provider process kept alive between turns, or saved process authority UAM cannot reach, does not block a helper update; see [Remote hosts](../settings/remote-hosts.md) and [stops the host has not confirmed](#stops-the-host-has-not-confirmed). Local editor actions and remote desktop computer use are not implied by SSH support.

The official helper installation transaction must publish the installed binary's SHA-256 sidecar and source manifest under the same owned installation lock as activation. Hash and identity verification must succeed, and the manifest's source fingerprint must match the copied executable, and rollback or interrupted-transaction recovery must restore the prior binary and metadata, including prior absence. A refused or failed helper stop retains recovery files and reports rollback as unfinished. These installed-file facts do not establish the identity of a resident or loaded helper; active-work admission and runtime compatibility checks remain required.

Recovery journals must become authoritative atomically. Windows finite operations must validate their installation nonce while holding a target-side operation lock; guard expiry and successor recovery wait for that operation to finish, and late commands from an expired owner are refused. A successful handshake alone cannot make the host Ready: setup also requires a nonce-bound commit acknowledgement. An unknown commit leaves setup unavailable until guarded retry reconciles it; acknowledged commit with failed backup cleanup may report a warning.

Target-lock acquisition must pause before recovery or mutation until the owning controller durably saves the pending transaction nonce and artifact/target identity. Losing the controller before that acknowledgement leaves the prior transaction untouched; losing it afterward preserves an unavailable installation across reload. Failed mutation with unconfirmed rollback retains this durable fence and its binding rather than restoring a previous Ready claim. Settings reload, successful health probes and ordinary connection retries must preserve that fence; guarded setup is required to settle it. Ordinary transient connection errors remain reconnectable: a failed health check is retried in the background with a growing delay of up to five minutes, and one successful helper contact restores Ready without a manual recheck. A controller that goes silent during an install (a sleeping laptop or lost network) cannot hold the target lock indefinitely: setup SSH commands, including the helper copy, send keepalives that end a step about 45 to 60 seconds after the connection goes silent (an existing shared SSH connection, such as a ControlMaster one, keeps its own settings), and the Linux target lock gives up after ten idle minutes and rolls back, as the Windows lock does after ten minutes. Every ordinary saved-host client, including workspace validation and memory operations, must enforce installation admission before starting a bridge. Linux synchronous mutation commands retain operation ownership if their guard dies, while detached helpers inherit neither installation lock descriptor. Guard replies identify their operation; a timeout, disconnection or uncorrelated reply invalidates the stream and cannot confirm rollback.

**Implementation: Partial.** Linux x86-64/ARM64 and Windows x86-64 helper routes exist; transactional metadata publication is implemented for Linux and Windows with scoped native and injected filesystem checks passing on macOS; real platform execution acceptance remains pending. macOS remote-helper packaging and various live/provider combinations remain unverified. Commands UAM runs on a remote Windows host use built-in Windows PowerShell 5.1 (`powershell.exe`) and 5.1-compatible scripts; a per-host PowerShell choice is not implemented, and the [Editors](../settings/editors.md) Terminal shell choice applies only to terminal windows opened on a Windows controller. See [architecture](../architecture/execution-hosts.md), [provider checklists](../providers/providers.md#provider-checklists), [open gaps](../documentation-review.md#helper-metadata-publication) and [build flags](../build-flags.md).

**Windows as the SSH controller: Partial.** The Windows core test job runs the session proxy against a private helper service through a stand-in `ssh`: start, attach without starting or replaying a process, missing-session failure, detach and recovery through a new bridge, fragmented native frames, the acknowledged stop outcome through the helper service and through a direct bridge, and provider start in a drive-letter workspace and in a UNC workspace through the machine's administrative share, which hosted CI requires and a developer machine may skip. Drive-letter and UNC workspace strings are also checked in proxy specs and SSH terminal commands, and the MCP control line accepts them on Windows. Not tested from Windows: a live OpenSSH connection to a real host, the SSH arguments and remote bridge command (the stand-in ignores them and the proxy cases use the `linux` route), restart of the app itself (a new proxy stands in for it), the MCP relay end to end, a UNC workspace on another computer, and a provider launched through a `.cmd` shim in any workspace (the proxy cases launch an executable directly). See [issue #349](https://github.com/davidtaylor6130/Universal-Agent-Manager/issues/349).

## Connection waits

Waiting on a remote host must never hold up the app. The first contact with a host covers the SSH connection, the remote shell and helper start, so it is allowed 45 seconds in total, including any retry. Each later request is allowed 15 seconds for its reply. A first contact the SSH server dropped before either side identified itself is tried again up to twice after a short random pause; only the handshake has been sent then, so no work can repeat. A refused login, a connection closed during authentication, an unreachable host or jump host, and a timeout are not retried.

Cancelling or stopping the work that is waiting interrupts the wait at once, including a first contact and a remote command that is still starting. A command that did not finish still asks the host to stop its worker, for no more than five seconds, and the helper reclaims an abandoned worker itself. If the command's start was never confirmed and the host could not be reached to stop it, the error says the command may still be running there; a start the helper refused reports only that refusal. A command that finished keeps its result even when the cancel or deadline arrives during its last acknowledgement.

While a remote turn waits for a question answer or a permission decision, UAM keeps the controlling machine awake for as long as the wait lasts, because sleep drops SSH and can lose the turn. A local wait stops holding the machine awake after 120 seconds without runtime activity, since the local process survives sleep.

Closing UAM must not wait on remote hosts. From the moment it starts closing, no new remote connection is started, and every remote wait already under way ends at the same instant two seconds later, however many there are; a connection that is already open is served until then.

When a connection closes, the error ends with the last line SSH or the helper reported, so an authentication failure, a rejected host key and a missing helper can be told apart. That line is reduced to at most 300 printable characters with accounts, host names, addresses and file paths masked, is not written to a separate log, and is never attached to a timeout or to a failure later in a connection that had started normally. Queued Git reads for a host that stopped answering after they were queued fail with that same error instead of each repeating the wait; a new request, or any successful connection, clears it.

**Implementation: Implemented**, with native tests against a stand-in bridge on macOS and Windows; not exercised against a live unreachable host or a live SSH server at its connection limit. Many first contacts to one host can still start at once; limiting them is not implemented.

## Stops the host has not confirmed

A remote stop is finished only when the host answers for the process. The helper answers by reporting the stop, or by reporting that the process no longer exists. A host UAM cannot reach, a timeout, a helper that reports the process alive or any other failure is not an answer: the stop stays unconfirmed and the chat never reports it as stopped. An answer clears the chat's saved process and stop records, whether the stop was requested in this session or saved by an earlier one.

What "no longer exists" proves differs by platform, because a helper only knows the processes it started itself. On Windows a helper's processes end with it, so the helper's answer stands, and when the helper cannot be started on a reachable host (its files were deleted, for example) the answer is that no helper of that version is running; a helper process UAM cannot identify, such as another account's, counts as running, and a helper of another version is not looked for. On Linux a process can outlive its helper and a restarted helper has no record of it, so neither the helper's "does not exist" nor a helper that cannot be started is accepted until the host's process table also shows no process of that chat. Hosts of any other platform have no process-table check: the helper's answer stands there and a helper that cannot start leaves the stop unconfirmed.

On Linux a process counts as the chat's when it carries the chat session's marker, which helpers from this version on set on everything they start, or when it carries no marker at all and is working in the chat's workspace folder or below it, which is how a process started by an older helper is found; a deleted workspace still matches the folder its processes were left in. A process marked for another chat is that chat's and is ignored. Any unmarked process working in the workspace, including your own shell, keeps the stop unconfirmed until it leaves, so a workspace that is the account's home folder stays unconfirmed for as long as anything of that account sits in it. The check gives no answer, leaving the stop unconfirmed, when the table cannot be read or when one of the account's processes hides its details from its own account, as a running `ssh-agent` does (the SSH connection's own server process and systemd's per-user PAM holder, `(sd-pam)`, which every systemd login runs, are the exceptions). It does not see a process that runs as another account, nor an unmarked one that works outside the workspace. A helper of the chat's version counts as running even after its files were deleted, or its folder renamed to a name that still contains the version.

An unconfirmed stop is retried when UAM restarts, when the chat is stopped again and at each helper update. A stop that still has a turn to recover, and the stop of a previous provider's process after a provider switch, also retry by themselves, waiting longer after each failure up to one minute; an idle stop does not. An ordinary chat never gives up on an unconfirmed stop. Background model discovery, which has no chat to protect, may give up after a bounded number of attempts once it has sent its stop to the host, and must not hold a helper update for good. A restart that was waiting for the stop is launched once the stop is confirmed, however many retries failed first. An unsent message in that chat can be removed whenever no stop is actually running.

A helper update asks the installed helper about every saved stop first; see [Remote hosts](../settings/remote-hosts.md). Each helper version has its own endpoint on the host, and a newer helper cannot see a process an older one still runs. So an update that changes the helper version or folder waits for an answer and refuses while it has none, saying what the host reported: a process still in the chat's folder, a helper that runs but does not answer, processes that could not be checked, or no contact. An update that reinstalls the same version into the same folder may proceed without one, because that install asks the same helper to stop: the helper refuses while it owns a process, and on Linux the install also refuses when a helper is running but does not answer. Saved process records with no stop requested are not covered by this rule: after a version change their process, if still alive under the older helper, is left to that helper.

**Implementation: Partial.** The Linux process-table check is tested against a process table laid out as files and was confirmed once on a real systemd Linux host. Giving up on background model discovery is not implemented here: its unconfirmed stop still refuses a helper update until the host answers.

## Bootstrap failures

Helper setup must distinguish SSH transport, command launch, cancellation, timeout, output-read and unavailable-working-directory failures from unsupported OS or CPU results. Only a successful probe with valid platform output can establish an unsupported target; empty or malformed output is a probe failure. A failed remote shell command can trigger the Windows fallback, while transport and local execution failures stop setup. Public probe errors preserve the failure category and command exit code where available without echoing raw probe output, SSH diagnostics, credentials or private paths.
