# Account allowances

Limits reads account allowances independently of chats, without creating a conversation or sending a model prompt. Show scoped cached values immediately and keep known values during transient refresh failures; changed provider commands must not inherit old account values, and authentication or entitlement failure clears them. Distinguish loading, unavailable feeds, errors and a ready account that reported no window. Every unknown allowance keeps the same row as a readable one, greyed, with an empty bar, ??% (… while reading) and Resets —; unsupported feeds and failed reads share that row, and only failed reads keep the warning mark, on the card's help line. Use provider-reported periods only; otherwise name an unknown window with the provider's known label or "Allowance", never an invented Primary/Secondary period. Freshness and reset labels advance on one shared local clock without requesting history, describe past resets according to provider evidence and never announce future resets as passed. Offer local Refresh allowances with visible cooldown feedback, initially show two model buckets with expansion for the rest, and format credits with grouped numbers and at most two decimals while retaining original text on hover. Remote feeds remain explicitly unavailable without a local Refresh control or repeated polling. Like a build-excluded provider, a provider disabled on a computer is not shown in that computer's Limits and no new account read starts there (a read already running finishes and is discarded); Settings is where it is turned back on.

Limits opens with a callout card answering which allowance to use first, so that allowance is not lost at its reset. It picks the soonest future reset among windows with at least 10% left, and on a tie the most left. A window with an unknown percent or no known future reset does not qualify, nor does a window from a provider reporting its spend or usage limit reached, or whose last settled read failed. A good read holds the recommendation for a minute past the 5 minutes after which its card says Cached snapshot, so an ordinary re-read does not interrupt it. Windows whose provider reports a length nest, so one that has under 10% left caps the others on that provider unless its own reset has passed; quotas with no reported length, such as model buckets and Copilot's chat and completions allowances, stand alone. The headline names the provider (Use Claude first) and the line under it names the window chosen and what would be lost (It has 34% of its weekly allowance left, resetting Mon 12:00 AM (in ~47h)); that row carries a quiet Use first marker and, for a model bucket, stays in view outside the collapsed list. Up to two provider stops or used-up windows follow as a short list, each with its provider logo and name, and they give the callout the error tone. With nothing eligible it never says first: a provider's own stop takes the headline (Codex has reached its usage limit), otherwise the most used window with a known future or unknown reset says that a provider is used up or close to its limit (from 80%), naming a model bucket (Gemini is used up on gemini-2.5-pro · REQUESTS), or that allowances have room with the highest use, each with its reset. When every readable window's reset has passed it says allowances are awaiting an update, and with nothing readable it says why in calm words. A window ahead of pace does not affect the headline and speaks on its own row. The selected period's token total sits on the callout's right. Its icon takes the warning or error tone of a used-up or nearly used window.

Under the callout, the section label Allowances · read on this computer sits beside the freshness of the newest snapshot and Refresh allowances, with a small key underneath: Used (the fill), Time passed in the window (the tick) and Run-out at this pace (the caret). Each provider turned on for the computer then has one always-open card in a fixed order (Codex, Claude, Gemini, OpenCode, Copilot, Antigravity), so positions never move with urgency; the callout carries the recommendation. The card header holds the logo, name, plan chip, the provider's tokens for the selected period (from the same history the Tokens tab reads, exact count and sessions in the tooltip) and Updated Nm ago, marked Cached snapshot when stale. Every window is a row: its name with the reset under it, the bar, then NN% used with the pace verdict and its icon. Model buckets beyond the first two wait behind an N more model allowances disclosure; a spend limit is its own bar row showing used of limit. The card footer holds credits, Spend limit reached, a failed refresh's message with Showing cached allowances, and a collapsed Context and tokens disclosure with the latest chat's context, token mix and counts.

Each window bar is the 10px ProgressFill meter: the track fills to the used share and a tick, cut out of the track in the surface colour, marks the share of the window's time already passed, counted back from the reset by the provider-reported window length. Weekly windows carry seven day notches so progress through the week can be read. Use is projected in a straight line from the window start, an average since then rather than recent use, so the date moves and a window stays ahead for a while after use stops; the verdict says Ahead with the conditional run-out time (would run out) when use leads the tick by at least 5 points (the projection then always lands before the reset), On pace within 5 points, Plenty left when well under, or Used up at 100%. An ahead bar also gets a caret under the track where the projection hits 100%, on the same time axis as the tick and labelled with the time (~9:35 AM at this pace); past about 60% of the track the label sits to the caret's left. Times within a day are relative (in ~2h 10m), later ones within a week a weekday and time, and a week or more away a date and time (27 Nov, 10:52 AM), because a weekday past that reads as the next one; the verdict names only the weekday or date for later run-outs, projected times carry ~, and in sentences a projected time beyond a day also says how far off it is (~Mon 9:40 AM (in ~2d)), in minutes only under 3 hours, whole hours under 48 and whole days rounded down from there. With no window length, no future reset or no time yet passed there is no tick, verdict or caret, only the reset. Fills stay neutral, never brand colours: warning when the window is projected to run out before its reset (or from 80% when no pace is known) and error from 95% or when used up; the percent, verdict and caret take the same tone, as text in `--warning-text` or `--error-text`. Each bar is a meter whose spoken value gives the percent used, the share of time passed, the verdict and the reset. While the first read runs and no share is known the bar sweeps and shows …. Fills grow from the left when they appear and settle at once under reduced motion or Motion Off.

A provider whose allowance cannot be read (nothing known and no read running) gets the same card greyed: a flatter surface with no shadow, a greyscale logo, no plan or freshness, its short reason in the header (Not signed in, Couldn't read, Needs access, Login expired, Not offered by the provider) and its tokens beside it. Its row keeps the window name (the provider's known name, otherwise Allowance), Resets —, an empty bar with no tick and ??%, with no status dot; its accessible text says the allowance is unknown and why. The footer's help line is the full native message, where failed reads keep the warning mark and unsupported feeds stay neutral. These cards sit after the readable ones, two to a row once there are two of them (one column in narrow windows). OpenCode stays as a greyed card rather than being hidden. A window the provider did not report beside a readable one keeps its row with Not reported by provider. When Codex reports a Pro plan without a secondary window, show the requested 5-hour Unlimited row; a reported secondary window takes precedence.

Allowances belong to accounts and only this computer reads them, so Limits has no machine headings: All machines shows the allowances read here once, with tokens summed across machines. Selecting a remote computer explains once that allowances are read on this computer only and shows that computer's tokens, and its cards stay greyed with ??% without repeating the reason in each header; the footer keeps the native message. The column matches the Cost and Tokens tabs.

**Implementation: Partial.** Independent local readers exist for Codex, Claude, Copilot and Antigravity; Gemini requires an eligible existing account and can report provider denial. OpenCode has no integrated independent account-quota reader. Custom commands and remote acquisition remain unavailable. Google account reads reuse valid existing access tokens; expired grants can refresh only when the same credential profile provides its OAuth registration, otherwise refresh the login in the provider CLI. UAM embeds no Google OAuth registration values. Existing credentials must not trigger interactive login, project trust, onboarding or expanded access. Antigravity reads its existing login from this computer's credential store: the macOS Keychain, Windows Credential Manager (read-only, never prompting) or, on Linux, the Secret Service through `secret-tool` when installed; when the store cannot be read the row says so in platform-neutral terms. The Windows and Linux readers have not yet been verified against real Antigravity installs. On macOS, automatic reads never show a Keychain dialog; when access needs approval the row asks for Refresh allowances, and only that explicit refresh may show the macOS permission prompt. A phone refresh may prompt only when [Phone Access settings](../settings/phone-access.md) allow Keychain prompts from the phone. Historical token accounting and per-chat context remain separate.
