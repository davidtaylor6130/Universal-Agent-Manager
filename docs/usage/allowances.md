# Account allowances

Limits reads account allowances independently of chats, without creating a conversation or sending a model prompt. Show scoped cached values immediately and keep known values during transient refresh failures; changed provider commands must not inherit old account values, and authentication or entitlement failure clears them. Distinguish loading, unavailable feeds, errors and a ready account that reported no window. Every unknown allowance keeps the same greyed row as a readable one, with an empty bar, ??% (… while reading) and reset —, and its short reason as muted text; unsupported feeds and failed reads share that row, and only failed reads keep the warning tone, in the row details. Use provider-reported periods only; otherwise name an unknown window with the provider's known label or "Allowance", never an invented Primary/Secondary period. Freshness and reset labels advance on one shared local clock without requesting history, describe past resets according to provider evidence and never announce future resets as passed. Offer local Refresh allowances with visible cooldown feedback, initially show two model buckets with expansion for the rest, and format credits with grouped numbers and at most two decimals while retaining original text on hover. Remote feeds remain explicitly unavailable without a local Refresh control or repeated polling. Like a build-excluded provider, a provider disabled on a computer is not shown in that computer's Limits and no new account read starts there (a read already running finishes and is discarded); Settings is where it is turned back on.

Limits opens with one sentence of what matters: the provider projected to run out first, with when and its reset (Claude will run out in ~8m, before its 5 hour window resets in 30m); otherwise the window closest to its limit (or the highest use when all have room) with its reset; or a calm explanation when no allowance is readable; followed by the selected period's token total. Below it, one Allowances card holds one compact row per provider: logo, name, plan, the provider's tokens for the selected period from the same history the Tokens tab reads, and its most pressing window (used up first, then the earliest projected run-out, then the highest use) as a bar with that window's name, its pace and percent used.

Each window is a horizontal bar: the track fills to the used share and a thin tick marks the share of the window's time already passed, counted back from the reset by the provider-reported window length. Use is projected in a straight line from the window start; the line beside the bar says Ahead of pace with the projected run-out time when use leads the tick by at least 5 points (the projection then always lands before the reset), On pace within 5 points, Plenty left when well under, or Used up at 100%, always followed by the reset. Times within a day are relative (in ~2h 10m), later ones a weekday and time; projected times carry ~. With no window length, no future reset or no time yet passed there is no tick and no verdict, only the reset. The fill is neutral, warning when the window is projected to run out before its reset (or from 80% when no pace is known) and error from 95% or when used up; the percent takes the same tone. Each expanded bar is a meter whose spoken value gives the percent used, the share of time passed and the verdict; the compact row's bar is decorative inside its button, whose text says the same. While the first read runs and no share is known the bar sweeps and shows ….

An unreadable allowance keeps the same row with an empty, greyed bar and no tick, its window name (the provider's known name, otherwise Allowance), ??% in place of the percentage and a short reason in muted text (Not signed in, Couldn't read, Needs access, Login expired, Not offered by the provider); it has no status dot. Its accessible text says the allowance is unknown and why. The full native message stays in its tooltip and in the row details, where failed reads keep the warning mark. Expanding a row shows freshness, the full message, every window as its own bar with tick and verdict (model buckets beyond the first two behind a further disclosure), spend limit as a bar, credits, the period token count and the latest chat's context and tokens, which stay collapsed. When Codex reports a Pro plan without a secondary window, show the requested 5-hour Unlimited row; a reported secondary window takes precedence.

Allowances belong to accounts and only this computer reads them, so Limits has no machine headings: All machines shows the allowances read here once, with tokens summed across machines. Selecting a remote computer explains once that allowances are read on this computer only and shows that computer's tokens, and its rows stay greyed with ??% without repeating the reason on each row. The column matches the Cost and Tokens tabs.

**Implementation: Partial.** Independent local readers exist for Codex, Claude, Copilot and Antigravity; Gemini requires an eligible existing account and can report provider denial. OpenCode has no integrated independent account-quota reader. Custom commands and remote acquisition remain unavailable. Google account reads reuse valid existing access tokens; expired grants can refresh only when the same credential profile provides its OAuth registration, otherwise refresh the login in the provider CLI. UAM embeds no Google OAuth registration values. Existing credentials must not trigger interactive login, project trust, onboarding or expanded access. On macOS, automatic reads never show a Keychain dialog; when access needs approval the row asks for Refresh allowances, and only that explicit refresh may show the macOS permission prompt. A phone refresh may prompt only when [Phone Access settings](../settings/phone-access.md) allow Keychain prompts from the phone. Historical token accounting and per-chat context remain separate.
