# Account allowances

Limits reads account allowances independently of chats, without creating a conversation or sending a model prompt. Show scoped cached values immediately and keep known values during transient refresh failures; changed provider commands must not inherit old account values, and authentication or entitlement failure clears them. Distinguish loading, unavailable feeds, errors and a ready account that reported no window. Use provider-reported periods only; otherwise retain Primary/Secondary labels and unknown percentages. Freshness and reset labels advance on one shared local clock without requesting history, describe past resets according to provider evidence and never announce future resets as passed. Offer local Refresh allowances with visible cooldown feedback, initially show two model buckets with expansion for the rest, and format credits with grouped numbers and at most two decimals while retaining original text on hover. Remote feeds remain explicitly unavailable without a local Refresh control or repeated polling.

Present each allowance window as a compact pace row using UAM colours, with a used track, reset time and a tick only when its provider-reported duration and reset time are known. Keep token details collapsed. When Codex reports a Pro plan without a secondary window, show the requested 5-hour Unlimited row; a reported secondary window takes precedence.

**Implementation: Partial.** Independent local readers exist for Codex, Claude, Copilot and Antigravity; Gemini requires an eligible existing account and can report provider denial. OpenCode has no integrated independent account-quota reader. Custom commands and remote acquisition remain unavailable. Google account reads reuse valid existing access tokens; expired grants can refresh only when the same credential profile provides its OAuth registration, otherwise refresh the login in the provider CLI. UAM embeds no Google OAuth registration values. Existing credentials must not trigger interactive login, project trust, onboarding or expanded access. On macOS, automatic reads never show a Keychain dialog; when access needs approval the row asks for Refresh allowances, and only that explicit refresh may show the macOS permission prompt. A phone refresh may prompt only when [Phone Access settings](../settings/phone-access.md) allow Keychain prompts from the phone. Historical token accounting and per-chat context remain separate.
