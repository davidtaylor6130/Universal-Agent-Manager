# Permission rules

Permission rules are the user's own allow, ask and deny list, checked locally and instantly for structured permission requests before any automatic approval or AI review. They run after the checks that already settle a request without UAM: provider-required decisions (including Plan exit and recognized non-action questions) and the Plan or captured read-ceiling rejection, and they never see approvals a provider answers itself, such as OpenCode V2's remembered “allow this exact action for this session” grants. Each rule names an action, what it applies to (a shell command matched by pattern, read-only work, file edits, web access, other tools or any request) and optionally one provider and one workspace folder given as a full path, which also covers everything inside it; a worktree chat matches rules for its source folder and the chat's own folder as well as the worktree. Deny wins over ask and ask over allow, whatever the list order. A deny answers once with the offered rejection (Cancel when none is offered). An ask leaves the request for the user under every permission level, YOLO included, and no AI review runs for it. A rule never grants a persistent or session-wide choice.

Rules only narrow. An allow rule takes effect only under [AI Review](ai-review.md), where it stands in for the reviewer's one-time approval and skips the model; it can approve only what the reviewer itself could have approved, so high-risk requests, Plan and [captured read restrictions](permissions.md#captured-read-restrictions), provider-required decisions, native reviewers, edits outside [Accept Edits' scope](auto-accept.md) and incomplete or sensitive-looking input still go to the user. Under Default and Accept Edits an allow rule does nothing, and YOLO already approves. Allow rules can target only commands, read-only work and workspace file edits, and an allow command pattern must start with a program name. Read-only work admitted by the literal read filter never skips review through a rule when it names something credential-like, such as `.env`, `.ssh` or a key file.

A command pattern is shell-quoted words matched from the program name: `*` and `?` match inside a word, `[...]` is a character class and `**` spans any number of words, so `git ** push ** --force*` also covers `git -C repo push origin main --force-with-lease`. An allow pattern matches only one plain command from its first word: chaining, pipes, redirection, substitution (`$( )`, backticks), variables (`$X`, `%X%`), globs, leading assignments and paths such as `./npm` never match, so `npm test; rm -rf /` cannot ride an allowed `npm test`. Because a provider may run commands through cmd.exe or PowerShell, which do not share POSIX quoting or comments, a command containing `;`, `&`, `|`, `<`, `>`, parentheses, `$`, a backtick, `%` or `!` anywhere, even quoted, never matches an allow rule. Deny and ask patterns look everywhere a program can start: after `;`, `&&`, `||` and pipes, inside substitutions and `bash -c`, `cmd /c` or `eval` strings, and behind wrappers such as `sudo`, `env`, `xargs`, `timeout` and `find -exec`, comparing the program name without its path, case or `.exe`/`.cmd`/`.bat`/`.ps1`, comparing arguments without case and with `\` read as `/`, and also reading the command with its quotes and escapes removed so operators that only POSIX quoting hides still count. `cmd /c`, PowerShell `-Command`, `iex` and `Invoke-Expression` strings are checked like the commands they run. An argument glob or brace list counts as matching when it could expand to a name the pattern matches (with the shell's rule that `*` does not match a leading dot), so `cat ~/.ss?/id_rsa` meets `** *.ssh/*`. A command whose program is only known at run time, such as `$TOOL`, `$(echo rm)`, `r* -rf` or `{rm,-rf,x}`, PowerShell `-EncodedCommand` and `Invoke-Command` script blocks, or one that does not parse or exceeds UAM's analysis limits (64 KiB, 128 words per command, 4,096 words or 512 program positions in all), is left for the user whenever any deny or ask command rule applies. A request without a typed command gives command rules nothing to read: they neither hold nor deny it, while any-request rules still apply. Rules match the typed native command and the provider's structured tool kind, never display text.

New installations and settings files written before rules existed start with defaults: read-only work is allowed (it skips AI review); deletion (`rm`, `rmdir`, `unlink`, `shred`, `find -delete`, `del`, `erase`, `rd`, `Remove-Item`, `ri`) and `.env` files always ask; and force pushes, SSH and AWS credential files, macOS keychain password reads, `git credential` and `gh auth token` are denied. Because ask outranks YOLO, a YOLO chat now asks for these commands, and for argument globs such as `cat *` that could reach a `.env` file; see the [open decision](../../documentation-review.md#permission-rule-defaults-under-yolo). Users can edit, disable or remove any default; an emptied list stays empty. A saved list that cannot be read falls back to the defaults, and invalid entries are dropped; both are reported as a settings load warning.

Under AI Review, requests no rule decides go to the reviewer only while **Ask the AI reviewer** is on; turned off, they wait for the user. Within one app run, an approve or deny verdict for a typed shell command is reused for a later call of the same command with the same reviewer provider and model, chat provider, ceiling, workspace and working directory, even though each call has its own request and tool-call ids; Codex requests, whose payload can carry grant roots or permission changes, and other tools are never reused. Uncertain and failed reviews are not reused, eligibility is checked again before every reuse and delivery, the cache is cleared when rules or the switch are saved and is never saved or logged, and a rule added while a review runs is applied instead of its verdict.

Rules apply on every structured route that delivers permission callbacks to UAM: Claude Code, Codex, Gemini, OpenCode V1 and V2, and Copilot. Antigravity's headless route answers its own prompts and gives UAM no callback, so rules cannot act on it; CLI View terminals remain provider-controlled.
