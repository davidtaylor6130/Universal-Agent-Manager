# Permission rules

Permission rules are the user's own allow, ask and deny list, checked locally and instantly for every structured permission request before any automatic approval or AI review. Each rule names an action, what it applies to (a shell command matched by pattern, read-only work, file edits, web access, other tools or any request) and optionally one provider and one workspace folder, which also covers everything inside it. Deny wins over ask and ask over allow, whatever the list order. A deny answers once with the offered rejection (Cancel when none is offered). An ask leaves the request for the user under every permission level, YOLO included, and no AI review runs for it. A rule never grants a persistent or session-wide choice.

Rules only narrow. An allow rule takes effect only under [AI Review](ai-review.md), where it stands in for the reviewer's one-time approval and skips the model; it can approve only what the reviewer itself could have approved, so high-risk requests, Plan and [captured read restrictions](permissions.md#captured-read-restrictions), provider-required decisions, native reviewers, edits outside [Accept Edits' scope](auto-accept.md) and incomplete or sensitive-looking input still go to the user. Under Default and Accept Edits an allow rule does nothing, and YOLO already approves. Allow rules can target only commands, read-only work and workspace file edits, and an allow command pattern must start with a program name. Read-only work admitted by the literal read filter never skips review through a rule when it names something credential-like, such as `.env`, `.ssh` or a key file.

A command pattern is shell-quoted words matched from the program name: `*` and `?` match inside a word, `[...]` is a character class and `**` spans any number of words, so `git ** push ** --force*` also covers `git -C repo push origin main --force-with-lease`. An allow pattern matches only one plain command from its first word: chaining, pipes, redirection, substitution (`$( )`, backticks), variables (`$X`, `%X%`), globs, leading assignments and paths such as `./npm` never match, so `npm test; rm -rf /` cannot ride an allowed `npm test`. Because a provider may run commands through cmd.exe or PowerShell, which do not share POSIX quoting or comments, a command containing `;`, `&`, `|`, `<`, `>`, parentheses, `$`, a backtick, `%` or `!` anywhere, even quoted, never matches an allow rule. Deny and ask patterns look everywhere a program can start: after `;`, `&&`, `||` and pipes, inside substitutions and `bash -c`, `cmd /c` or `eval` strings, and behind wrappers such as `sudo`, `env`, `xargs`, `timeout` and `find -exec`, comparing the program name without its path, case or `.exe`, and also reading the command with its quotes and escapes removed so operators that only POSIX quoting hides still count. A command whose program name is only known at run time, such as `$TOOL` or `$(echo rm)`, or that does not parse, is left for the user whenever any deny or ask command rule applies. Rules match the typed native command and the provider's structured tool kind, never display text.

New installations and settings files written before rules existed start with defaults: read-only work is allowed (it skips AI review), `rm` and `.env` files always ask, and force pushes, SSH and AWS credential files, macOS keychain password reads, `git credential` and `gh auth token` are denied. Users can edit, disable or remove any of them; an emptied list stays empty.

Under AI Review, requests no rule decides go to the reviewer only while **Ask the AI reviewer** is on; turned off, they wait for the user. Within one app run, an approve or deny verdict is reused for a later request whose reviewer input, reviewer provider and model, chat provider, ceiling and workspace are identical; the reviewer has no tools, so the same input is all it could judge. Uncertain and failed reviews are not reused, eligibility is checked again before every reuse and delivery, the cache is never saved or logged, and a rule added while a review runs wins over its verdict.

Rules apply on every structured route that delivers permission callbacks to UAM: Claude Code, Codex, Gemini, OpenCode V1 and V2, and Copilot. Antigravity's headless route answers its own prompts and gives UAM no callback, so rules cannot act on it; CLI View terminals remain provider-controlled.
