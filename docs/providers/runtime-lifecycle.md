# Runtime controls

Runtime state distinguishes startup, ready, working, waiting, stopping, stopped and failed or unknown activity. Cancelling a turn asks the current work to stop and [holds queued input](../chat/sending.md) rather than deleting or sending it; stopping a runtime owns process cleanup and is not permission to delete the conversation or replay input. Restart/resume must retain native identity and delivery evidence, and timeout or lost UI attachment alone must not prove the provider exited. Show pending or failed cleanup, preserve definitely unsent input and use explicit recovery choices when delivery is uncertain. Native terminal interrupt, detach and provider exit retain their own meanings.

Stopping a local runtime settles the chat for the user within a bounded time: the transcript and any held input are kept and visible, and the chat no longer shows a pending stop. This holds for a hung provider, an ignored cancel, a pending approval, a running tool, queued or held input, live native child tasks, an active goal and a failing history save. The stop closes the provider's input, then asks the platform to terminate and kill the owned process tree; UAM cannot guarantee that the operating system ends it. If the exit is still unobserved the tree is forced again, and about eight seconds later the chat is settled without that observation. From then until the exit is observed, UAM keeps forcing the process in the background and refuses everything that would start or depend on a new process for that chat (sending, timeout Restart and other retries, opening CLI View, switching branches, reusing a Codex thread, a fresh goal budget), saying that the previous process has not exited, that this clears by itself when it does and that quitting UAM also ends it. A second process is never started beside one that may be alive. A stop made for a workspace change stays cooperative: it is neither forced nor settled early. A pending or failing history save does not keep the chat stopping, because that save retries on its own. If held prompts cannot be recorded as interrupted rows, that Stop is refused and they stay held, unchanged; the next Stop retries once their saved state is current. An unsaved quota-wait cancellation is retried rather than refusing the stop.

Shutdown must preserve a saved, undispatched remote queue when an idle runtime has no corresponding queued input or active turn; an empty runtime queue does not prove that saved input was consumed. A retiring runtime and its late stop results must not overwrite a replacement chat's queue, authored state or delivery evidence. Failed stop-worker setup or pending remote-stop publication must retain the original process fields; the runtime switches from running to pending remote stop only after successful publication.

The chat header runtime control gives each state its own icon as well as its colour and text: the shared dashed working ring while a turn runs (still under reduced motion or Motion Off), the stop icon while live, a timer inside the shrinking idle ring once the post-grace countdown starts (warning tone in the final minute) and the shared failure cross with Failed when the runtime reports an error; a failed runtime stays stoppable from the control. Its tooltip and a visually hidden accessible description name the state; the Terminal View and phone countdown use the same timer icon, a `timer` role and an accessible name that includes the remaining time and the grace-period explanation.

**Implementation: Partial.** The shared runtime has shutdown projection and stop-handoff guards; independent cold Retry process lifetime and cleanup remain incomplete. Verification, review and acceptance are recorded in the [archived V5 change log](https://github.com/davidtaylor6130/Universal-Agent-Manager/blob/1d4865fcb/V5%20Improvement%20Change%20log.md).

## Stream watch

Every structured provider turn, local or SSH, feeds one shared stream watch with its assistant text, reasoning and tool calls. A **loop** is the same tool call (name, arguments and final result) or the same text or reasoning sentence of at least 40 characters recurring within the last eight items until it reaches the repeat limit (Off, 10, 20 or 50; default 20). A tool call that ran longer than 5 seconds, whose duration is unknown because it was first reported already finished, that recurs more than 60 seconds after its previous identical result, or that has neither arguments nor a result is never loop evidence; a changed result, such as re-reading a file after an edit, starts a new count, and history restored on reattach is not counted again. A **stall** is the [provider turn timeout](../settings/goal-loops.md) (default 30 minutes) passing with no output of any kind while the turn is running and not waiting for the user; text, reasoning, tool progress and any other provider message reset it, so slow but steady output or long reasoning is never a stall. Either detection stops the turn through the normal cancel path, keeps the transcript and queued prompts, never resends input, and writes one diagnostic line with the kind and count but not the content. A stall is the existing turn timeout stop with its **Restart with +15 min** notice; a loop uses the same notice with an example of the repeated content and **Restart**, which retries the message in place when the turn produced no output and otherwise reads **Continue in new chat** and re-runs it in a branch chat, leaving queued messages in the original chat. The notice appears once the stop's cancel has settled. The default repeat limit is an [open decision](../documentation-review.md#stream-loop-stop-default). CLI View turns retain only their existing busy-time limit. This work (#636) builds on the timeout notice work (#635).

### Open tool calls

A command inside one tool call, such as a long build, sends nothing until it finishes, so an open tool call (started, with no result yet) holds the stall clock. A shell tool call that declares its own timeout is not counted as silent until that timeout has passed since the call started; the provider turn timeout then counts from that point. A tool call that declares none gets the separate, longer [tool call limit](../settings/goal-loops.md) (default 2 hours) counted from its start; a call that waited for permission counts from the approval. With several tool calls open, the latest deadline applies, and the normal timer resumes when the result arrives. Output during a tool call still resets the clock as before, so an open call can only lengthen a turn and a tool call limit below the turn timeout has no effect. Calls a provider reports together share one start even when it runs them in turn. Every deadline is finite: a declared timeout is bounded by the longest supported limit, so a hung command still stops. A stop at the tool call limit uses the same cancel path and notice, says so ("a tool call exceeded its 120-minute limit") and its **Restart with +15 min** raises the tool call limit instead of the turn timeout. Permission and input waits keep their existing behaviour. The decision is shared: each provider's structured tool start and result feed one deadline on the session, locally and over SSH, and a tool call restored on reattach counts from the reattach. Which providers expose a declared timeout is recorded in each provider's `stream-watch` row; the rest use the tool call limit. The CLI View busy-time limit has no tool events and is unchanged, which is an [open decision](../documentation-review.md#cli-view-busy-limit-and-long-commands).
