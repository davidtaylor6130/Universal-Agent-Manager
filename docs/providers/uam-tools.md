# UAM tool connection

The built-in UAM MCP connection exposes approved UAM capabilities such as questions, skills and goals to compatible structured sessions. An enabled configuration, prepared resource bundle and actual observed connection are different states. Enabled pre-binding startup is setup in progress, not a missing connection or observed handshake; an unknown observation never establishes availability or failure. A ready or previously bound session with missing capability and a recorded setup failure remain actionable rather than being hidden by running work. Structured Chat hides its connection warning while the same chat is in CLI View and clears the old warning before a fresh observation when Chat returns; this does not establish native CLI tool availability. Missing/failed connection warnings offer Enable UAM connection, View settings or Continue without it; continuing dismisses the warning for the relevant session rather than pretending tools work. Enabling setup applies on the next provider start without interrupting current work. A stale response must not change another chat or host, and built-in Computer Use retains its separate enablement/target consent.

For managed children, the shared [active-turn result wait](../chat/subagents.md#active-turn-result-wait) reads one exact owned run through `agent_wait {runId}`. A completed result belongs to the original tool call; a bounded still-running outcome is explicit and permits another wait on that same run. It neither creates replacement work nor cancels the child, and it cannot resume an ended parent turn. Configuration, tool exposure and one observed invocation remain distinct from a provider's actual long-call deadline and live local/SSH support. Canonical runtime and provider-specific verification remain pending.

Delegation results additionally report `resultDelivery` as `cooperative-only`, `automatic-pending` or `held`, with a fixed reason. `automatic-pending` is a conditional same-live-parent route described in [parent result continuation](../chat/subagents.md#same-live-parent-result-continuation), not proof of native input acceptance or parent consumption. Delegation itself does not require YOLO or command approval: the child inherits the parent’s permission policy and cannot exceed the selected agent’s or any ancestor’s read-only ceiling. Approvals for commands, goals, cancellation and Computer Use retain their own guards; a delegation result, model-supplied option or saved record grants none of those permissions.

UAM marks its tools that change no workspace or UAM-managed work (`agent_list`, `agent_status`, `agent_wait`, `skill_list`, `skill_read`, `goal_get` and `user_question`, which only reads the user’s answer) with the standard MCP `readOnlyHint`, so a Plan or read-only session, including a Plan child, can use them without a permission prompt that its read-only ceiling would refuse. Delegation, cancellation, goal creation and Computer Use requests carry no hint, and the UAM server still enforces every ceiling. In 2026-10-26 provider probes, Claude Code Plan mode and Copilot Plan mode, through both ACP and the native SDK protocol UAM uses, skipped the prompt for hinted tools; Codex skipped it too, although UAM already approves its own tools for Codex; OpenCode `run` did not prompt for MCP tools; Antigravity Plan mode ignored the hint, which remains a provider limit; Gemini was not observed. OpenCode’s server mode still needs verification.
