# UAM tool connection

The built-in UAM MCP connection exposes approved UAM capabilities such as questions, skills and goals to compatible structured sessions. An enabled configuration, prepared resource bundle and actual observed connection are different states. Enabled pre-binding startup is setup in progress, not a missing connection or observed handshake; an unknown observation never establishes availability or failure. A ready or previously bound session with missing capability and a recorded setup failure remain actionable rather than being hidden by running work. Structured Chat hides its connection warning while the same chat is in CLI View and clears the old warning before a fresh observation when Chat returns; this does not establish native CLI tool availability. Missing/failed connection warnings offer Enable UAM connection, View settings or Continue without it; continuing dismisses the warning for the relevant session rather than pretending tools work. Enabling setup applies on the next provider start without interrupting current work. A stale response must not change another chat or host, and built-in Computer Use retains its separate enablement/target consent. Each session's connection signs its requests with a key UAM gives only to that session's tool server at launch; UAM refuses a request that is not signed with that key, so a program that only knows a chat's control folder cannot act through it. This is not isolation between programs running as the same user: one that can read the provider's process environment or its MCP configuration can still obtain the key.

For managed children, the shared [active-turn result wait](../chat/subagents.md#active-turn-result-wait) reads one exact owned run through `agent_wait {runId}`. A completed result belongs to the original tool call; a bounded still-running outcome is explicit and permits another wait on that same run. It neither creates replacement work nor cancels the child, and it cannot resume an ended parent turn. The child may run on a different execution host from the caller, and a child that changes during the wait is answered with an explicit error instead of silence. Configuration, tool exposure and one observed invocation remain distinct from a provider's actual long-call deadline and live local/SSH support. Canonical runtime and provider-specific verification remain pending.

Delegation results additionally report `resultDelivery` as `cooperative-only`, `automatic-pending` or `held`, with a fixed reason. `automatic-pending` is a conditional same-live-parent route described in [parent result continuation](../chat/subagents.md#same-live-parent-result-continuation), not proof of native input acceptance or parent consumption. `held` applies to the current request only; it is not a permanent state of the chat. Delegation itself does not require YOLO or command approval: the child inherits the parent’s permission policy and cannot exceed the selected agent’s or any ancestor’s read-only ceiling. A goal reviewer is under that ceiling for its whole session, so it cannot create goals or chats, cancel work, watch pull requests (a later wake would run under the chat's broader agent) or start a write-capable child. For a read-only caller, `agent_list` reports every agent as read-only and lists only the caller's own provider. A read-only caller also delegates only to its own provider, because providers enforce a read ceiling differently; a request naming another provider is refused. Approvals for commands, goals, cancellation and Computer Use retain their own guards; a delegation result, model-supplied option or saved record grants none of those permissions.

`chat_create {task, providerId?, modelId?, title?}` starts one separate top-level chat, not a child: it uses the caller's workspace and execution host, sends `task` as the first prompt and defaults to the caller's provider and model. Only providers eligible on that host in `agent_list` are accepted. The new chat copies the caller's approval mode and command-safety tier, so it is never more permissive, and always gets its own Git worktree: UAM refuses the request when Git or automatic worktrees are disabled, an SSH host lacks a protocol-3 helper, or a local SVN or plain-folder workspace may not be snapshotted, because the chat would otherwise share the caller's files ([workspaces](../workspaces/workspaces.md)). A YOLO caller starts it immediately; any other caller's request waits in the chat for an explicit Allow or Deny, and Plan mode, read-only agents and managed subagents are refused. A caller may start at most two chats per turn and eight in total. The eight counts chats that still exist and were started by the caller or any branch of it, so deleting a started chat frees a place; a CLI View caller has no structured turn, so its two-per-turn limit applies per tool connection. A chat started this way, and any branch of it, cannot start others. The tool replies only after the first prompt has been sent; if the send is refused, the still-empty chat is removed and an error is returned, so a failed start is never reported or reused. Retrying identical arguments returns the chat already started. The new chat records its creator and shows a **Started by** link back to it; that record is display provenance, not lineage, resume or permission authority. Creations use the shared request validation, replay protection and per-chat audit, and the diagnostic log records chat, caller, provider and host without the prompt. Its [open decisions](../documentation-review.md#chat-started-chats) are recorded separately.

`secret_request {label, reason, placeholder?, url?}` asks the user for one secret in a masked card and replies with only a read-once path on the computer where the agent runs, never the value ([secure secret entry](../chat/secrets.md)). It is a card request like `user_question`, shown in the root chat, refused to read-only agents, goal-review turns, side chats and automation chats, and gated by a one-time Allow in Plan mode; it carries no read-only hint.

`pr_watch {url}` or `pr_watch {repository, number}` makes the calling chat [watch a GitHub pull request](../chat/pull-request-watch.md), and `pr_unwatch` with the same arguments stops it while keeping the pull request linked. UAM then reads the pull request in the desktop app and sends the chat a message when it changes, so the agent ends its turn instead of polling; a merge or close brings one final message. Both tools act only on the chat that calls them: they change no workspace, start no other chat and wake no other chat, so they need no approval and work in every permission mode. Managed subagents and temporary side chats are refused, because their turn ends with their task; the chat that delegated to them watches instead. Only `github.com` pull requests are accepted, a chat links at most 20 pull requests, and the diagnostic log records the chat without the repository. The tools carry no read-only hint, so a provider in Plan mode may ask before calling them.

UAM marks its tools that change no workspace or UAM-managed work (`agent_list`, `agent_status`, `agent_wait`, `skill_list`, `skill_read`, `goal_get`, `user_question`, which only reads the user’s answer, and the [HTML view](../chat/html-views.md) tools `html_view_preview` and `html_view_publish`, which add at most a display card to the chat's own transcript and run the page once in a hidden no-network sandbox) with the standard MCP `readOnlyHint`, so a Plan or read-only session, including a Plan child, can use them without a permission prompt that its read-only ceiling would refuse. Delegation, cancellation, goal and chat creation and Computer Use requests carry no hint, and the UAM server still enforces every ceiling. When a turn stops (user Stop, inactivity timeout or a UAM-owned goal stop), the waiting `user_question`, Computer Use, goal or chat creation request from that session is declined with an error naming the cause, including while a remote stop is still being confirmed; requests from other sessions are unaffected. In 2026-10-26 provider probes, Claude Code Plan mode and Copilot Plan mode, through both ACP and the native SDK protocol UAM uses, skipped the prompt for hinted tools; Codex skipped it too, although UAM already approves its own tools for Codex; OpenCode `run` did not prompt for MCP tools; Antigravity Plan mode ignored the hint, which remains a provider limit; Gemini was not observed. OpenCode’s server mode still needs verification.

Tool definitions are part of every model request, so each session lists only the tools it can ever use, fixed for that session so the provider's prompt cache stays valid: Computer Use is not offered on SSH hosts or to read-only agents (an agent whose workspace access is missing or not `write` counts as read-only); CLI View omits `agent_wait` and the HTML view tools; `chat_create` is omitted for managed subagents, read-only agents and chats that may not start chats; read-only agents also lose `agent_cancel` and `goal_create`; a subagent with no permitted delegates gets no agent tools; subagents and temporary side chats are not offered `pr_watch` or `pr_unwatch`; `secret_request` is not offered to read-only agents, side chats or automation chats, which it refuses, but stays available in Plan mode behind its one-time Allow; a [goal reviewer](../chat/goals.md) session lists none at all. The server refuses a call to a tool its session does not list. Conditions that can change during a session, such as Plan mode or the global Computer Use switch, stay server-side refusals. Every tool carries a one-line description of what it does. `agent_list` returns `{agents, providerTargets}`, listing the host's provider targets and their models once rather than repeating them for every agent.

## Tool calls that cannot complete

A tool call ends with an answer or a clear error; it is not left for the provider's own timeout to end, and it never runs after its caller was told it failed. A call UAM does not answer within its budget (about 10 seconds for most tools) is withdrawn before the error is returned, so it cannot run later; if UAM had already accepted it, the caller waits a few seconds more for the real outcome and is otherwise told to check the effect before retrying. Retrying `agent_delegate` with the same arguments in the same turn after its reply was lost returns the run already started instead of starting a second child. A reply too large for the 64 KiB transport is returned as an error and the tool connection keeps serving; `agent_list` shortens its list to fit.

A question, approval, secret or Computer Use request shown as a card (`user_question`, `secret_request`, and `goal_create`, `chat_create` and `computer_use_request` when they need approval) has no time limit of its own. It waits until the user answers it, and the caller's turn stays blocked on it within the [tool call limit and turn timeout](../settings/goal-loops.md). It ends unanswered only when its turn stops or ends, its session ends, the provider cancels the call or the provider's tool connection closes or is replaced; the card is then removed, so an answer is never accepted for a caller that is no longer waiting. A turn that ends normally counts too, so a provider that gave up on the call without cancelling it cannot leave a card that would still create a goal or chat; a remote turn that is being reattached has not ended, and a card stays while background agents that share the turn's tool connection, such as Claude background tasks or Codex child threads, are still running. A provider's own tool deadline still applies. Where UAM sets it, for Codex and OpenCode, it is 2 hours, matching the default tool call limit (David chose this on 2026-11-11; it was 300 and 120 seconds); the other providers use their own default, which UAM does not set and has not measured. Local sessions end with the app, so their cards do not survive an app restart.

On an SSH host the tools reach the desktop through a relay. After the app reattaches to a provider that kept running, the relay serves the channel that provider was launched with, and the replacement tool connection is recorded as connected without a new handshake, so `agent_wait` and the connection status work as before. A relay that fails reconnects on its own, backing off to one attempt every 30 seconds. While the desktop is not connected, a new tool call is answered on the host at once with "UAM desktop is not connected", and a call already waiting is failed after 30 seconds of silence and can no longer reach the desktop; if the host helper does not confirm that, the shim asks again until it does or the desktop's tool server is replaced, which drops those calls anyway. A waiting card is the exception: it survives a silent desktop, such as a sleeping laptop, and is answered when the connection returns. A card cannot follow an app restart, because the restarted app has a new tool connection: its call fails with a clear error and the agent may ask again. The host-side behaviour needs a helper of this version on the host; an older helper keeps the earlier plain pipe. A desktop relay that does not name its tool server to the helper, from before this behaviour, still has its unread failed calls dropped but is not locked out of the channel, since it could not reconnect past that.
