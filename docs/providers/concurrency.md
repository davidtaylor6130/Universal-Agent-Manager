# Concurrent provider instances

Users can run multiple chats and CLI instances at the same time, including multiple instances of one provider on local or configured remote computers. Input, output, approval decisions, cancellation and saved session identity belong to the correct chat; stopping or changing one must not affect another. Background work must remain visible through the sidebar and must not block ordinary interaction. Optional [Compute Pools](../settings/compute-pools.md) limit how many Chat turns may run at once for a provider or model; without a configured pool there is no limit.

Provider and helper processes that do not serve the user's own turn start at lowered scheduling priority, so many agents or a background sweep cannot starve the interface or the turn the user is waiting on. Agent work (managed sub-agents, goal iteration transcripts and automation chats) and background work (model discovery, memory workers, history import, provider version checks and repository discovery) run at utility QoS and nice 10 on macOS, below-normal priority on Windows and nice 10 on Linux, on a remote computer as on this one; the processes they start inherit it. A chat's own turns, its CLI view, the repository check before its launch and a provider install or update the user starts keep normal priority. A process keeps the class it started with, so a goal continued in the user's own chat keeps that chat's normal priority.
