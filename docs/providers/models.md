# Models

Model discovery and selection belong to the chosen provider and execution environment. Show real advertised or explicitly configured models, retain the selected model during refresh, and distinguish cached choices from confirmed availability. A selection must reach the running or next-started session as appropriate; unavailable models produce an actionable error instead of silently selecting another. Provider/model changes must not leak another chat’s selection. In an existing chat’s model picker, Refresh or Retry requests models for the provider and environment being viewed while retaining cached choices, the current selection and the search. Request acceptance does not establish a completed catalogue refresh. Older discovery replies must not replace the selector state of a changed chat or environment; retiring a selector does not cancel a request or authorize retrying input. Background discovery on an SSH host that cannot confirm its helper process stopped reattaches to stop it at most three times with increasing delay, then ends the discovery without sending a further stop, which may mean none was ever delivered. The helper itself ends that process: discovery starts under a 60-second lease that only a connected controller renews, and when it lapses the helper terminates the process and forgets its record. Until then the leftover process can run for up to a minute on that computer and counts as helper work there. A model request the UI makes by itself, such as opening a model menu with no listed models or showing a chat on the phone, is skipped while that environment's cached models are less than seven days old or were already refreshed in this run; when that earlier refresh failed, the skipped request shows its error instead of an empty list. Refresh and Retry always ask the provider. A CLI version already checked and known incompatible on that computer is refused from the recorded check, without starting a provider session, until the check changes.

Model picker rows show separate Context and Output token-capacity badges from the model's reported context-window and maximum-output limits, including an explicit reported zero. Missing or invalid limits show nothing: no badge, placeholder or accessible text, and a row with neither limit has no capacity area; defaults, configured choices and unavailable favourites must not borrow another model's limits. Favourites use the same provider, execution-host and workspace scope as ordinary rows. Compact counts retain exact token values in the row's tooltip and accessible text without repeating capacities in the focused tooltip's accessible description; disabled choices retain descriptions and exact limits in their accessible label and native hover label, with no simultaneous shared Tooltip, when narrow rows hide descriptions. Token capacity is separate from physical model size or parameter count: UAM does not display physical size and never infers it from capacity, model names or identifiers. Settings → Appearance → Display → **Model token limits** (on by default) turns every capacity badge, tooltip line and accessible capacity text off; the choice is stored with the other appearance preferences on this device and applies the next time a picker opens.

## Account refusals

Some refusals answer for the signed-in account on a computer rather than for the workspace UAM asked about, for example Google telling Gemini CLI that Gemini Code Assist for individuals no longer supports this client. When a provider's `initialize`, `session/new`, `session/load` or `session/resume` reply carries the JSON-RPC server error `-32000` together with one of a short list of phrases naming the client or the account (a client that is unsupported or no longer supported, an account that is not eligible or not entitled, no active subscription, or authentication required), UAM records one account refusal for that provider and computer instead of a failure per workspace. Similar model, plan or workspace messages stay scoped to their workspace, as do other methods and codes, and a refusal the provider's own error handling recovers from is not recorded. While it lasts, startup discovery and automatic model requests skip the provider on that computer, and the provider shows one plain line, such as "Google no longer supports this Gemini client for personal accounts.", wherever its model refresh error appears. A client or entitlement refusal also holds chat launches, and the chat that met it shows the same line before the provider's message; an authentication refusal never holds a chat launch, because signing in, for example in CLI View, fixes it at once. The refusal lasts 24 hours, or one hour for authentication, and survives a restart. Refresh or Retry in the model menu asks the provider at once and also releases startup scopes held back, which otherwise ask again once it expires, and any later successful model answer on that computer lifts it. Its notice stays after it expires until the next attempt on that computer starts or fails for its own reason; an authentication refusal also gives way as soon as a chat launch it let through fails for another reason. The provider stays in scope and enabled; only its availability on that computer changes. The diagnostic log records the classification with a bounded copy of the provider's message beside the error's existing ACP diagnostic. The phrase list lives in [the classifier](../../src/common/provider/provider_account_refusal.cpp). Coverage follows the shared ACP response path: Gemini and OpenCode (ACP and native V2 setup requests) have their setup replies classified; Codex replies pass through it, but only its `initialize` is a classified method, since its sessions start with `thread/start`; Copilot's SDK route (`session.create`), Claude Code's stream-json route and Antigravity's native route are not classified yet.

## Queued setting preparation

Before dispatch, UAM prepares the admitted input’s effective model and mode in that input’s own idle runtime. Its matching raw queue must not make that preparation reject itself; saved choices may be deferred, but manual mutation of a busy native session remains blocked. Foreign queues, active native turns, permission waits and pending setting negotiations remain barriers, and captured read-only policy continues to limit the turn. Reasoning still follows the provider’s existing per-turn or restart requirement. For launch-configured native models, selecting Default removes an earlier explicit launch override at the next idle admission; a reported resolved default model is not an explicit launch selection. A named selection is compared with the captured launch choice, not the resolved name the provider reports (Claude reports `claude-opus-5-5` for `opus`), so a matching alias does not restart every turn; each settings restart records a `restart` diagnostic naming the reason and both models. If a reattached launch choice cannot be confirmed, queued input remains retained through an owned idle restart. Local and remote settings restarts retain both runtime and durable raw input throughout teardown; a preparation or replacement-launch refusal restores the raw head and holds the queue for recovery. Native streams that obtain their session identity from the first input retain that supported startup route. Existing internal continuation controls retain their separate invocation ownership and future user queue; they do not acquire ordinary raw-queue admission.
