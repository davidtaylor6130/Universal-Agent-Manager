# OpenCode CLI

OpenCode CLI uses V1 ACP or the checked V2 native API adapter for the [verified V2 range](#version-compatibility). Common behaviour is defined once in the [provider agreements](../providers.md); this checklist only records delivery and known limits. Native capabilities depend on the installed CLI, selected model and execution environment; shared UAM routes do not imply that every native variant is supported.

**Assessment:** source routes and retained automated evidence only; V1 assessment 2026-10-17, local V2 source continuation 2026-10-23 and the V2 range live protocol smoke 2026-11-12. Implemented is not live verification or David’s acceptance. Consult the [status definitions](../../documentation-rules.md#agreements-and-implementation) and the [archived V5 change log](https://github.com/davidtaylor6130/Universal-Agent-Manager/blob/1d4865fcb/V5%20Improvement%20Change%20log.md).

## Version compatibility

OpenCode V1 and V2 require separately verified launch and native-service integration. A fresh structured launch must distinguish installation minimums from protocol compatibility and use the checked executing host's version; an installation change does not revoke reconnection to an existing owned remote process. Refusing an incompatible launch retains saved session identity and authored input. Full V2 support includes startup, configuration, MCP, sessions, history, permissions and cancellation.

**Implementation:** ordinary local PATH `opencode` Chat launches use a successful, supported version check for the executing host; a confirmed missing or unsupported CLI blocks. When the local check fails or times out, Chat still launches on the V1 ACP path and stops before input unless the running process reports 1.15.13 or newer and below 2.0. V2 versions from 2.1.2 through 2.2.7 form one verified protocol contract, defined once in source and shared by Chat, model refresh, text workers, history import and the CLI version check; other V2 versions, pre-release or build suffixes and fresh SSH V2 launches are refused with a message naming the installed and verified versions. Text workers have no such handshake, so unchecked, failed or mismatched-host worker checks hold the request with an explicit Settings check/retry action; application startup already queues local checks. V1 `run` workers retry provider usage or rate-limit errors without exiting, so UAM requests error-level logs, stops the worker locally or through the SSH runner once a model request has failed twice (OpenCode's own retry still gets past a single failure), and drops those log lines before reading the reply; other installed versions report the installed and supported versions instead of starting a worker. V1 retains ACP; a verified V2 version selects a UAM-owned headless bridge to `serve --stdio --hostname 127.0.0.1 --port 0`, with private authentication, an stdin lifetime lease and an HTTP/SSE adapter. The bridge verifies the running service's `/api/info` version against the same range, permission-plugin load proof against the captured session workspace, exact session/workspace and replaced session rules before input. Unconfirmed cancellation or owned transport failure retires the bridge and durably holds queued input for explicit recovery; shared timeout handling must not restart or drain it automatically. Its process-local evaluation hook forces UAM decisions after saved native grants; native agent denials remain restrictive, native replies use once/reject, and remembered exact-action grants stay in UAM's process state and expire when captured restrictions change. Native child delegation remains denied pending a verified child policy contract. Shared UAM permission modes and captured read restrictions remain authoritative.

Configuration preserves captured instructions and actual MCP definitions; the saved `opencode-progressive-mcp` preference is neither a V2 server nor proof of native discovery support. Native create/load, streamed text/reasoning/tools, questions, model/effort selection, token usage and cancellation feed UAM's existing lifecycle. Checked local V2 text workers select their private route before isolation setup, omit V1 worker configuration/flags, consume bounded finite preloaded input through the platform service, deny all tool permissions and publish text only after confirmed completion. Windows uses its private regular-file stdin route; structured bridge input retains the nonblocking pipe-only reader. Confirmed cancellation records validated completed-step token usage exactly once before shared cancellation settlement. Local history probes generation and uses V2 nested session export and flat-message normalization; V1 commands, decorated version-output parsing, the full native history command budget and the existing guarded history publication are preserved. Imported V2 tool text renders as text while non-text content retains its data fallback. Stop waits for the exact owned inbox cancellation or delivery event before deciding whether interruption is needed; HTTP acknowledgement alone proves neither. Lost transport, malformed events or ambiguous admission/cancellation holds input with an explicit error and no automatic HTTP replay; a lost or invalid prompt-admission receipt retains the original request correlation until shared retirement durably holds the queue. The [pinned protocol assessment](../../reference/opencode-v2-protocol-assessment.md) records exact contracts, reference credit and remaining limits.

**Verification boundaries:** focused mocked-native engine/transport checks, safe linked runtime/version/history/recovery cases and independent source review cover the V2 route; a scripted session replaying the bridge's routes, permission plugin and readbacks ran against real OpenCode 2.2.6 and an isolated 2.2.7 on macOS with a free model (session create, model and variant switch, streamed reply, forced native approval and rejection, idle interrupt, list/export); evidence and qualified follow-ups are in the [protocol assessment](../../reference/opencode-v2-protocol-assessment.md). The compiled UAM bridge against real OpenCode, Windows, CEF, SSH/helper delivery, installed-app workflows and David’s acceptance remain unverified. Fresh SSH V2 remains refused until its executing helper carries a verified native adapter; existing owned remote recovery retains its path. Unknown V2 versions, custom executable identity, imported V1 native-agent policies, V2 saved-image Retry, native children, advanced native forms and V2 compaction coverage remain explicit gaps. Custom commands and CLI View retain their existing paths; V2 CLI View companion observation is not established. The historical V2.1.2 DESCRIPTION failure and local V1.19.4 downgrade workaround remain recorded; no installation change is part of this implementation.

## History export

OpenCode 1.19.4 can exit successfully before a piped standard output drains, cutting a large `export` at 128 or 192 KiB; this was reproduced on a Linux SSH host, while a Windows 1.19.4 host and local 2.1.4 returned complete output. On POSIX executing hosts, local and SSH V1 history export writes native output to a private temporary file, unlinked as soon as it is open, and streams it after the native process exits, preserving the export's exit status and reporting a missing CLI explicitly. Discovery reports UAM's own adapter refusal, such as an unverified V2 version, instead of a generic list failure, and per-session failures name the provider, native session and SSH host. Windows hosts and local V2 export keep their direct routes. Import of the previously failing remote sessions on an installed build remains unverified.

## Progressive MCP discovery

The [provider setting](../../settings/providers.md) currently governs UAM's automatic native V1 Code Mode hint for OpenCode on one execution host. The inspected route admits checked versions 1.17.20 and 1.18.35 only; enabling the preference does not qualify 1.19.4, V2 or another version. Explicit executing-host or launch environment values retain precedence, and older format-1 helpers may ignore the optional hint and keep eager discovery. V2 session/location MCP registration is independent of this preference; neither the V1 environment flag nor reserved-server deadline metadata establishes a V2 discovery capability. An upstream per-server V2 Code Mode schema field is a [capability lead requiring separate verification](../../reference/central-configuration.md), with no current preference wiring. Saving the preference does not restart warm processes or reconfigure recovered processes. Live provider and platform verification, Claude GUI review and user acceptance remain pending; historical discovery/Umami activation failures remain unresolved by this settings addition. Each launch logs whether the hint applied, without server addresses or credentials.

## Workspace identity

OpenCode structured permissions and native Terminal View bind to the same owned workspace and exact native session identities. For an SSH Windows host, ordinary absolute DOS paths may differ only in corresponding slash/backslash separator spelling while drive case, component bytes, component order and separator positions stay exact. This rule does not expand aliases, case, dot components, device or UNC paths; byte-identical paths retain their existing admission. Local roots are first compared by canonical path. On every other non-Windows comparison, the paths match byte for byte after trailing `/` separators are removed (never the root `/`). This includes SSH roots and child-session ancestry, so a stored `/workspace/` matches OpenCode's reported `/workspace`. Windows trailing-separator differences remain rejected. Source implements this spelling comparison; matching desktop/helper delivery and Windows live acceptance remain pending.

## UAM tool deadline

For checked OpenCode 1.19.3 launches with enabled UAM control, UAM's private process profile gives its reserved `uam-control` server a 2-hour tool-call budget when no explicit inline reserved definition exists, so a [question or approval card](../uam-tools.md#tool-calls-that-cannot-complete) can wait for the user (David chose this on 2026-11-11; it was 120 seconds before). This per-server policy takes precedence over native experimental fallback, including a larger fallback; other servers and global settings are unchanged. Explicit inline reserved settings, including shorter or larger budgets, are retained; a conflicting injected owned server refuses setup. Effective native precedence and long-call execution remain unverified. SSH coverage requires a newly matching deployed helper: older helpers can ignore this optional setup hint, so a desktop update alone does not establish remote coverage or acceptance.

## Turn timeout

OpenCode's provider request timeout (`provider.<id>.options.timeout`) bounds a whole provider request, while UAM's Provider turn timeout bounds time without provider activity. So that OpenCode cannot end a long turn before UAM's limit, shared launch setup gives the launch model's provider the turn timeout as its request timeout, locally and over SSH. A value at or below OpenCode's 5-minute default is never sent, and a larger value or `false` already in the launch environment's inline `OPENCODE_CONFIG_CONTENT` is kept. Because inline configuration takes precedence over files, the value UAM sends replaces whatever the user's `opencode.json` files set for that provider, including a longer value or `false`, which are therefore lowered to the turn timeout. A running process launched with a different value restarts before its next turn, never during one. A prompt failure reporting `operation timed out` is presented as the OpenCode request timeout, with its value and Restart, only when the whole turn lasted at least that long (UAM sees the turn, not OpenCode's individual provider requests, so a long turn of several requests whose abort came from a different, shorter limit is still labelled as the OpenCode request timeout); an earlier one is shown as a provider timeout from OpenCode's own configuration, without a value or Restart.

The authenticated native companion treats a late answer from a busy server as slow rather than failed once it has a complete snapshot: new prompts wait with a visible "answering slowly" status, and consecutive late answers stop an in-flight turn only once they outlast the turn timeout, reported as a timeout stop. Late answers from an earlier turn are not carried forward; while idle, consecutive late answers are bounded by the provider setup timeout and then stop the provider as an observation failure, so a server that never answers cannot hold the next prompt indefinitely. Before the first complete snapshot, and for refused or rejected answers, the three-failure limit still applies. **Implementation: Partial** — a model switched mid-session to another OpenCode provider keeps that provider's own limit until relaunch, a model with no `provider/` prefix receives no request timeout, and a timed-out turn that already produced output, or that has queued messages after it, is not restarted (the action saves the value and asks for a follow-up). Live slow-model verification is pending.

## Repeated-call questions

The built-in `doom_loop` question is distinct from an MCP action whose generated name is also `doom_loop`. Recognition of the inspected OpenCode 1.18.35 question requires its native tool-and-input metadata; the authenticated child snapshot also needs matching tool patterns and no action tool link. Unknown or changed shapes retain denial or cancellation. This identifies a trusted producer shape, not origin attestation: plugins can imitate it, and ACP does not retain every native snapshot field. This distinction is implemented with protocol verification and scoped source review; recognizing this question grants no provider-native Task permission and does not relax captured read ceilings or broader native policy limits. Desktop, live-provider, Windows, SSH and user acceptance remain pending.
