# OpenCode CLI

OpenCode CLI uses V1 ACP or the checked V2 native API adapter. Common behaviour is defined once in the [provider agreements](../providers.md); this checklist only records delivery and known limits. Native capabilities depend on the installed CLI, selected model and execution environment; shared UAM routes do not imply that every native variant is supported.

## Version compatibility

OpenCode V1 and V2 require separately verified launch and native-service integration. A fresh structured launch must distinguish installation minimums from protocol compatibility and use the checked executing host's version; an installation change does not revoke reconnection to an existing owned remote process. Refusing an incompatible launch retains saved session identity and authored input. Full V2 support includes startup, configuration, MCP, sessions, history, permissions and cancellation.

**Implementation:** ordinary local PATH `opencode` Chat and text-worker launches require a successful, supported version check for the executing host. Unchecked, failed or mismatched-host worker checks hold the request with an explicit Settings check/retry action; application startup already queues local checks. V1 retains ACP; exact V2.1.2 selects a UAM-owned headless bridge to `serve --stdio --hostname 127.0.0.1 --port 0`, with private authentication, an stdin lifetime lease and an HTTP/SSE adapter. The bridge verifies the running version, permission-plugin load proof against the captured session workspace, exact session/workspace and replaced session rules before input. Unconfirmed cancellation or owned transport failure retires the bridge and durably holds queued input for explicit recovery; shared timeout handling must not restart or drain it automatically. Its process-local evaluation hook forces UAM decisions after saved native grants; native agent denials remain restrictive, native replies use once/reject, and remembered exact-action grants stay in UAM's process state and expire when captured restrictions change. Native child delegation remains denied pending a verified child policy contract. Shared UAM permission modes and captured read restrictions remain authoritative.

Configuration preserves captured instructions and actual MCP definitions; the saved `opencode-progressive-mcp` preference is neither a V2 server nor proof of native discovery support. Native create/load, streamed text/reasoning/tools, questions, model/effort selection, token usage and cancellation feed UAM's existing lifecycle. Checked local V2 text workers select their private route before isolation setup, omit V1 worker configuration/flags, consume bounded finite preloaded input through the platform service, deny all tool permissions and publish text only after confirmed completion. Windows uses its private regular-file stdin route; structured bridge input retains the nonblocking pipe-only reader. Confirmed cancellation records validated completed-step token usage exactly once before shared cancellation settlement. Local history probes generation and uses V2 nested session export and flat-message normalization; V1 commands, decorated version-output parsing, the full native history command budget and the existing guarded history publication are preserved. Imported V2 tool text renders as text while non-text content retains its data fallback. Stop waits for the exact owned inbox cancellation or delivery event before deciding whether interruption is needed; HTTP acknowledgement alone proves neither. Lost transport, malformed events or ambiguous admission/cancellation holds input with an explicit error and no automatic HTTP replay; a lost or invalid prompt-admission receipt retains the original request correlation until shared retirement durably holds the queue. The [pinned protocol assessment](../../reference/opencode-v2-protocol-assessment.md) records exact contracts, reference credit and remaining limits.

**Verification boundaries:** focused mocked-native engine/transport checks and 17 safe linked runtime/version/history/recovery cases pass with all six providers enabled. Independent Codex R7 full source review passed after confirming the authentic R1/R5/R6 finding corrections; historical failures and their qualified follow-ups remain in the [protocol assessment](../../reference/opencode-v2-protocol-assessment.md). Subsequent documentation edits record proof only; reviewed code and fixtures remain unchanged. Actual OpenCode/Effect, Windows, CEF, SSH/helper delivery, installed-app workflows and David’s acceptance remain unverified. Fresh SSH V2 remains refused until its executing helper carries a verified native adapter; existing owned remote recovery retains its path. Unknown V2 versions, custom executable identity, imported V1 native-agent policies, V2 saved-image Retry, native children, advanced native forms and V2 compaction coverage remain explicit gaps. Custom commands and CLI View retain their existing paths; V2 CLI View companion observation is not established. The historical V2.1.2 DESCRIPTION failure and local V1.19.4 downgrade workaround remain recorded; no installation change is part of this implementation.

## Progressive MCP discovery

The [provider setting](../../settings/providers.md) currently governs UAM's automatic native V1 Code Mode hint for OpenCode on one execution host. The inspected route admits checked versions 1.17.20 and 1.18.35 only; enabling the preference does not qualify 1.19.4, V2 or another version. Explicit executing-host or launch environment values retain precedence, and older format-1 helpers may ignore the optional hint and keep eager discovery. V2 session/location MCP registration is independent of this preference; neither the V1 environment flag nor reserved-server deadline metadata establishes a V2 discovery capability. An upstream per-server V2 Code Mode schema field is a [capability lead requiring separate verification](../../reference/central-configuration.md), with no current preference wiring. Saving the preference does not restart warm processes or reconfigure recovered processes. Live provider and platform verification, Claude GUI review and user acceptance remain pending; historical discovery/Umami activation failures remain unresolved by this settings addition.

## Workspace identity

OpenCode structured permissions and native Terminal View bind to the same owned workspace and exact native session identities. For an SSH Windows host, ordinary absolute DOS paths may differ only in corresponding slash/backslash separator spelling while drive case, component bytes, component order and separator positions stay exact. This rule does not expand aliases, case, dot components, device or UNC paths; byte-identical paths retain their existing admission. Local canonical checks and other hosts retain their existing comparison. Source implements this spelling comparison; matching desktop/helper delivery and Windows live acceptance remain pending.

## UAM tool deadline

For checked OpenCode 1.19.3 launches with enabled UAM control, UAM's private process profile gives its reserved `uam-control` server a 120-second tool-call budget when no explicit inline reserved definition exists. This per-server policy takes precedence over native experimental fallback, including a larger fallback; other servers and global settings are unchanged. Explicit inline reserved settings, including shorter or larger budgets, are retained; a conflicting injected owned server refuses setup. Effective native precedence and long-call execution remain unverified. SSH coverage requires a newly matching deployed helper: older helpers can ignore this optional setup hint, so a desktop update alone does not establish remote coverage or acceptance.

## Repeated-call questions

The built-in `doom_loop` question is distinct from an MCP action whose generated name is also `doom_loop`. Recognition of the inspected OpenCode 1.18.35 question requires its native tool-and-input metadata; the authenticated child snapshot also needs matching tool patterns and no action tool link. Unknown or changed shapes retain denial or cancellation. This identifies a trusted producer shape, not origin attestation: plugins can imitate it, and ACP does not retain every native snapshot field. This distinction is implemented with protocol verification and scoped source review; recognizing this question grants no provider-native Task permission and does not relax captured read ceilings or broader native policy limits. Desktop, live-provider, Windows, SSH and user acceptance remain pending.
